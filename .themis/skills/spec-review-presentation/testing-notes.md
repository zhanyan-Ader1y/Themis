# 测试记录 — spec-review-presentation

本文件记录该 Skill 的 RED-GREEN-REFACTOR 过程。**该 Skill 的第一版是先写后测的，违反了"没有失败的测试就不写 Skill"**——本记录同时是那次违规的补救与证据。

## 失败类型分类

**这不是纪律型失败，是输出形状失败。**

分类依据：写第一份 R3 投影时，`rules.md` §3（评审投影的低负担要求）已在上下文里且被完整遵守——投影确实只含本层增量、没有粘贴下层完整内容。**规则被遵守了，输出仍然不可读。**

这个分类决定了 Skill 的形态：**用正面配方（说清成品是什么形状），不用禁令清单**。禁令在竞争性激励下会被协商掉；配方没有可协商的东西——输出要么符合所述形状，要么不符合。

## RED：无引导基线

同一份 R3 事实，只给 `rules.md` §3，不给任何呈现引导。两次独立采样。

**两次均失败，且失败形态高度一致：**

| 症状 | rep 1 | rep 2 |
| --- | --- | --- |
| 裸用编号（`T-D1`–`T-D6`、`SPEC-WSCLEAN-006`、`2026-08-26-workspace-cleanup`） | 全部未展开 | 全部未展开 |
| 裁定点位置 | 第 4 节 | 第 3 节 |
| 首节内容 | 「本层增量」元话语 | 「本层新增了什么」元话语 |
| 规模数字当内容（45 份、六条、三份） | 有 | 有 |
| 独立的「本次批准不覆盖什么」收尾 | 无 | 无 |

**关键观察**：rep 2 的文笔明显优于 rep 1（有 ASCII 依赖图、有"若选 B 需一并给出边界"这类严谨补充），**但结构失败完全相同**。方差集中在文笔，不在结构——说明这不是采样噪声，是缺少引导时的稳定形态。

两次都以任务表或元话语开场，把评审者唯一必须做的事（裁定）压在中段。

## GREEN：带 Skill

同一份事实，附 Skill 全文。两次独立采样。

**两次均通过，且收敛到同一形状：**

- 节序完全一致，裁定点均在第二节
- 零编号泄漏——`T-Dx`、`SPEC-WSCLEAN-xxx`、`2026-08-26-workspace-cleanup` 一个都没出现在成品里
- 均自发补出"判错的后果不对称"这一层（Skill 只要求写后果，未要求比较后果）
- 末节「本次批准不覆盖」均齐备

**收敛本身是信号**：两次采样给出同一形状，而不是五种解读，说明引导是有约束力的。

**Skill 未明写、Agent 自行补出的增益**（记录以备后续判断是否该写进 Skill）：

- rep 1：主动把"你也可以选择让我按规则退回"作为第三个选项交还评审者
- rep 2：把 §6 的程序违规单独提为一个裁定层；并给出缺口的补救路径（"如果你想收掉这个风险，可以在本次批准里加一句要求……但那需要你现在明示"），同时不擅自改上一轮裁定

## REFACTOR：测出来的两处缺陷

**缺陷 1 —— 「其余要点」节的契约不清（真实方差）**

rep 1 在该节把六条任务完整复述了一遍，与 §3「不重复下层细节」有张力；rep 2 则明显克制。**同一份引导产生两种详略，说明该节缺少约束。**

修法**不是**加一句"不要复述任务清单"——那是禁令，会被协商。改为给该节一条**契约**：

> 只放影响批准与否、但不需要裁定的事实。判断标准只有一条：这条事实如果去掉，评审者的批准/不批准会改变吗？

并明写执行次序、任务清单、判据列表通常不属于这一节。

**缺陷 2 —— 形态与失败类型不匹配**

第一版以「五条规则」开场、以「反面清单」（八条禁令表）收尾，是禁令主导的形态——与"输出形状失败"不匹配。「反面清单」改写为「交付前自检」，每行从"不许出现什么"改为"通过的样子是什么"。

**一处经测试确认不必改的地方**：规则 4 要求删掉规模数字，但两次 GREEN 采样都保留了"实际发生 7 次、4 次"。人工读原文后确认**保留正确**——那两个数字用在"这三节写作约束的护栏价值"语境，是判断依据而非工作量计量，正落在规则 4 的例外条款内。例外条款有效，不需收紧。

## 边界

本 Skill 只管呈现，不管判定。某节点能否进入下一步见 `.themis/spec/flow.md`；某条判据是否满足、谁有权判见 `rules.md`。

**投影可读性不是判据**——评审者不因投影写得好而批准。本 Skill 的作用是让他看得清内容本身。

**为什么仍然写入**：它来自 `2026-08-26-authorization-traceability` 实例的实证——该实例走查发现，此前五次"评审者只答一半"的实发中，至少三次的成因是把授权与附带裁定合并提问（`docs/plan/spec-replay/drift-log.md`「人工验收」条目）。新增内容治的是该成因。

**为什么不补测就写入**：补测需要构造"投影含并列裁定项"的场景并多次采样，成本高于本次改动本身；而该实例的 R3 评审者裁定接受"如实标注"这一处置（见 `.themis/workspace/spec/2026-08-26-authorization-traceability/step1/task/review.md`「结论」）。

**因此本节存在的意义是防止误读**：读者不应因这两行与已测内容同处一份文件，就认为它们同样经过验证。**补测仍是敞开的**——若将来有含并列裁定项的实例，那正是它的天然测试场景。

**一处值得记的观察**：该实例自身的 R3 评审**恰好就有一个并列裁定项**，而评审者首答只给了"批准"、未就该项表态。这是新增内容所针对的形态的一次真实出现，**但它发生在新增内容落地之前**，不构成对它的测试。

## 2026-08-27 第三次扩充：裁定点必须给推荐

所有者要求：输出做法时给出推荐哪一项，并说明原因。

**证据基础**：本会话共呈现约十个裁定点，Agent 在其中多数已自发给出推荐
（"我的看法是……"、"我推荐 (a)，理由是……"），而 Skill 从未要求这么做。
**又是"先有自发实践、后固化"**——与「录入说明」固化为 `rules.md` §11、
「上轮已确认的不重复呈现」固化为规则 8 同型，这是本项目第三次。

**为什么该固化而不是任其自发**：自发意味着不稳定。同一份投影里，Agent
可能对 A 项给了推荐、对 B 项只列了选项，而评审者无从知道后者是"没有
倾向"还是"忘了写"。固化后两者可区分——依据不足时须明说依据不足。

**同时写入两条约束，防止推荐变成代替决定**：

- 推荐必须给**依据**（实测数据、已有先例、与现有机制的冲突），不写"我觉得"。
- 备选项要照实写全、代价照实写，不得为了让推荐显得正确而弱化其他选项；
  **推荐若与某条已有记录相悖，必须标出那条记录**——评审者有权知道他推翻
  的是什么。

第二条来自本会话的一次真实教训：Agent 曾向所有者建议"只限判定依据的
数字、叙述里的不算"，而该项的原始记录末句明写"区分主张性数字与辅助数字
没有意义，两类要一视同仁"——**建议与记录直接相悖，而 Agent 当时没读全
原文、也没标出这一点**。所有者最终裁定"一视同仁"，与原始记录一致。

**未测试，如实标注**：与前两次扩充一样，本条未经 RED-GREEN-REFACTOR。
补测的天然场景是下一个 spec 的四次评审——届时若投影仍出现"只列选项不给
推荐"或"推荐无依据"，说明规则无效。
