# spec-review-presentation

## 这个 Skill 解决什么

`.themis/spec/rules.md` §3 规定了投影的**抽象层边界**——只含该层增量、不重复下层细节。它没有规定**可读性**：一份完全符合 §3 的投影，仍然可能让评审者读不懂、找不到重点、无法在不翻工件的情况下做出判定。

本 Skill 补的正是这一层。**它不改变任何判据**——某节点是否收敛、评审是否通过，判定规则全部在 `rules.md`，本 Skill 无权改动，只管这些内容"怎么呈现给人看"。

## 核心原则：默认读者零上下文

**写投影时假设评审者没有读过任何工件、不记得任何专有名词、不知道上文发生过什么。**

评审者是决策者，不是流程的参与者。他要在一屏之内判断"这个方向对不对"，而不是先做一轮考古。凡是需要他回头查证才能理解的东西，都是投影的缺陷，不是他的问题。

一个可操作的自检：**把这份投影单独发给一个从未参与本项目的人，他能不能做出同样的判定？** 不能，就还没写完。

## 五条规则

### 1. 自上而下：先意图，后事实，最后细节

固定顺序，不可颠倒：

1. **这一步要达成什么**（一到两句，用人话，不含专有名词）
2. **需要你裁定什么**（如果有，放最前面——这是评审者唯一必须做的事）
3. **发现了什么改变原定方向的事**（如果有）
4. **其余供参考的事实**

**最容易偏离意图的项排在最前面。** 判断标准是"若此处判错，下游返工最大"——通常是范围边界、授权归属、与原定方向的偏离，而不是技术细节。

### 2. 专有名词首次出现即展开

**任何项目内部的标识符——spec-id、任务编号、条目编号、文件代号——首次出现时必须带一句说明它是什么。**

```text
不合格：core-removal 的 verify/detail 零漂移
合格：  上一个需求（删除旧的 core/ 目录）在独立验证环节没有发生偏差
```

```text
不合格：T-D3 无判据覆盖
合格：  第三个任务（把两份入口文件和一份写作规范迁到新位置）没有任何验收判据能检查它做对了没有
```

编号本身对评审者没有意义。**编号是给执行者用的，不是给决策者用的。** 投影里可以保留编号作为索引，但必须紧跟一句人话。

### 3. 事实要具体到可核对，但只给结论所需的那部分

评审者判断需要事实支撑，但不需要完整证据链。

- **给具体路径**：`AGENTS.md` 第 48–52 行那一节，而不是"某处文档"。
- **给内容摘要**：那一节写的是"安装包源在 templates/ 下、安装动作由 CLI 承担"——而不是只给行号让他自己去看。
- **不给完整原文**：粘贴整段是把核对工作推给评审者。

标准是：**读到这一条，他能判断"这个说法成立吗"，而不需要打开文件。**

### 4. 删掉规模数字，除非它改变判断

**"删除 45 个文件"、"改动 7 处文本"、"三份齐备"这类计量对评审者没有意义。** 他不关心工作量，关心的是方向对不对、边界在哪、有没有动到不该动的东西。

规模数字只在一种情况下保留：**它本身就是判断依据**。例如"这个改动会碰到 26 份属于另一个模块的文件"——此时数字说明的是越界范围，不是工作量。

同理删掉：
- 工件小节是否齐备（那是执行者的自检，不是评审内容）
- 命令跑了几条、输出多少行
- 「四节齐备」「五条判据均已产出」这类完备性陈述

### 5. 每条都要有前因后果

**孤立的结论无法判定。** 每一条呈现给评审者的项，都要能回答三个问题：

- **为什么会有这一条**（起因）
- **现在的处置是什么**（决定）
- **如果判错会怎样**（后果）

三者可以压缩在两三句里，但不能缺。缺了起因，评审者不知道这是不是必要的；缺了后果，他不知道该多认真对待。

```text
不合格：basic 段为空，判定成立。

合格：  这一步没有"内部准备工作"——每个任务都直接改变仓库里
        看得见的东西。原本的设计稿建议把前两步归为准备工作，
        但那不符合规则里"准备工作必须自己不产生可见改动"这
        一条。若照原稿分类，这一步会带着一个不成立的分段进入
        实现，实现完才会发现分错。
```

## 结构模板

```markdown
## 这一步要做什么
（一到两句人话，零专有名词）

## 需要你裁定
（有则列出，每条：起因 → 两种选择 → 各自后果。没有则写"无"）

## 改变了原定方向的发现
（有则列出，每条说清：原本打算怎么做 → 核实到什么 → 现在改成怎么做）

## 其余要点
（供参考，不需裁定的事实）

## 我知道但还没解决的
（已知缺口、无判据覆盖的部分、留待后续的开放项）
```

**最后一节不可省略。** 评审者有权知道这次批准**没有**覆盖什么。

## 反面清单

投影里出现以下任何一项，即为不合格：

| 症状 | 为什么不行 |
| --- | --- |
| 未展开的 spec-id、任务编号、条目编号 | 评审者需要考古才能读懂 |
| 「X 份齐备」「Y 节完整」 | 执行者的自检，不是决策依据 |
| 文件数、行数、命令条数 | 工作量不是判断依据 |
| 粘贴工件原文超过三行 | 把核对工作推给评审者 |
| 「详见 `某文件`」而无内容摘要 | 等于没说 |
| 结论没有起因 | 无法判断是否必要 |
| 裁定点埋在正文中段 | 评审者唯一必须做的事应当最先看到 |
| 复述上一层已批准的内容 | 违反 `rules.md` §3 |

## 与判定规则的边界

**本 Skill 只管呈现，不管判定。**

- 某节点能否进入下一步 → `.themis/spec/flow.md`
- 某条判据是否满足、谁有权判 → `.themis/spec/rules.md`
- 工件有哪些小节 → `.themis/spec/template.md`

**投影可读性不是判据。** 评审者不会因为投影写得好就批准，也不该因为写得差就驳回——他驳回的是内容本身。本 Skill 的作用是让他**看得清内容本身**，不是让内容显得更好。

**尤其不得为了"呈现清晰"而修改事实**：不得省略不利的发现、不得把不确定写成确定、不得把越界描述成常规。如实呈现与清晰呈现冲突时，**如实优先**——但绝大多数情况下两者一致，冲突往往说明结论本身还没想清楚。
