# .themis/spec/rules.md

本文件只回答一个问题：**这一步怎么判过不过**。流程走向（现在能不能走到下一步）在 `flow.md`，产物结构（长什么样、放在哪）在 `template.md`。

每节固定四项：**适用节点 / 判据 / 拒绝条件 / 判定者**。第四项是教训换来的——孤儿阻断当初没写判定者，三份文档各指了一个互斥的角色，闸门退化成没人能合法勾上的框。**任何判据没有判定者就不是闸门。** 每节写成自足形态，读一节不需读另一节；这也是将来按节拆分时留的缝，抽出时整节搬走、原处留一行索引即可。拆分退出条件见 `README.md`。

## §1 来源与分层事实源

- **适用节点**：Intake、追问、抽象设计、详细设计 + 任务、impl/basic、impl/detail、verify/basic、verify/detail。
- **判据**：每个进入 current-request 的 claim 显式记录来源引用并写入工件文件，格式为 `<类型>#<定位>`，例如 `用户确认#<内容>`、`知识库#<记录>`、`代码#<路径>:<符号或行>`。按抽象层级施加事实源要求：意图、顶层设计、抽象设计等**抽象层**可以 Themico 或其他文档为事实；详细设计的实现依据、实现、验证等**具体实现层**必须以**代码**为事实源，文档仅作线索。
- **拒绝条件**：claim 无来源引用；引用不合 `<类型>#<定位>` 格式；具体实现层以文档而非代码为事实源；以 `spec` 作为事实源。
- **判定者**：Intake 与追问阶段由 Agent 自检并由 R1 评审者复核；抽象设计层由 R2 评审者判定；详细设计的实现依据由 R3 评审者在分类核查中一并判定是否以代码为事实源；impl、verify 节点的具体实现层由验证角色判定。

`spec` 在任何层都只作补充，不得作为事实源。`用户确认的内容`在任何层都是目标语义权威（`SPEC-INTAKE-002`、`SPEC-SOURCE-001`）。

## §2 意图收敛判据

- **适用节点**：追问 → R1 之间的收敛判定。
- **判据**：Why（为什么）、期望结果、核心链路三者均明确，且不存在未回答的问题。**提问资格**——一个问题有资格进入 `QA.md`，须是执行者**无法**从既有事实、已批准记录或先例中推出答案的；能推出的一律自己判，把判断与依据写进工件，在下一个人工闸门一并呈现。
- **拒绝条件**：三者任一不明确；存在未回答的问题；以"轮次已够"或"用户没再提问"代替三要素判定；**有依据却不判**（能从既有事实、已批准记录或先例推出答案，仍作为问题提出，把判断成本转嫁给评审者）；**依据没读全就提建议**（提出方案或推荐前未穷尽既有记录，包括既往教训记录与已闭合实例的裁定）；**目标层 claim 缺合法来源却不问**（只问执行细节，不问"这事该不该做"本身）。
- **判定者**：Agent 提出收敛主张，R1 评审者是唯一有权确认收敛的角色。**提问资格同样由 Agent 自检、R1 评审者复核**——`QA.md` 里每个问题都该能回答"若不问，我会判错什么"。

**后三条拒绝条件的方向不同，须一并读。** 前两条收紧提问，第三条放宽——**它是用来抵消前两条的收紧倾向的，不可只取前两条**。

**第三条的实发依据**：某次追问第 1 轮四个问题全部是"怎么做"层面（触发条件、引用怎么处理、包源分歧、范围），**没有一个问到"是否真的要做这件事"本身**，而那恰恰是唯一缺合法来源的 claim；是评审读「来源引用」小节时才发现，追加了一轮确认，不是追问机制自己捕捉到的。**执行者依三要素去想问题，天然会问执行细节，容易漏掉看起来"设计已定"因而不会主动怀疑的目标本身。**

**第二条的实发依据**：某次 Agent 提出的范围建议被所有者推翻，而**正确答案早已写在既有的教训记录里**，Agent 未读全原文即提方案。**若只要求"能推出的自己判"而不要求先读全，第一条会退化成第二条**——从"多问一次"变成"自己判错"。

**松紧的裁定依据（所有者裁定，按可恢复性排序）**：多问一次的成本是评审者的时间，**不留痕迹、事后无法发现和纠正**；不问而判错的成本是返工，**但会留在工件里被下一个人工闸门复核依据时发现**。**故宁可判错，不可多问。**

多轮追问的每轮问答形成不可变记录，追加写入 `QA.md`，不覆盖既有轮次（`SPEC-QUESTION-001`、`SPEC-QUESTION-002`）。

## §3 评审投影的低负担要求

- **适用节点**：R1、R2、R3。
- **判据**：投影由抽象到具体渐进呈现，只包含该抽象层的增量，不重复下层细节。R2 投影含架构或时序 Overview。
- **拒绝条件**：投影粘贴完整下层内容；同一细节在多层投影中重复出现；投影缺少该层增量而只有背景复述。
- **判定者**：该次评审的人类评审者。

低负担不等于少评审——三个评审节点各自存在，每次呈现降低理解成本，越早拦截越省返工（`SPEC-REVIEW-LOWBURDEN`）。

## §4 basic/detail 判定

- **适用节点**：详细设计 + 任务（分类必须在 R3 之前完成）。
- **判据**：basic 任务必须**同时**满足两条——"被本 step 其他任务依赖"与"单独不产生外部可观测行为"。两条同时满足才是 basic，判定依据必须写入 basic 任务工件。不满足则属 detail。
- **拒绝条件**：只满足一条即归入 basic；判定依据未写入工件；basic 任务无任何 detail 任务依赖它（孤儿，见 §8）。
- **判定者**：任务作者提出分类，R3 评审者在 `task/review.md` 的分类核查中判定。

两段恒定存在，**允许为空**。空段不产生落地调用，也不改变流程走向，不构成路径分支（`SPEC-IMPL-002`、`SPEC-IMPL-003`）。

结构改动存在层次（如 schema → 接口契约 → 行为）时，不因层次增设第三段：多层结构改动仍同属 basic，在 `task/basic.md` 内部按依赖顺序排列，不产生额外闸门（`SPEC-IMPL-002`）。

## §5 [basic] 标识

- **适用节点**：抽象设计（specify.md 撰写）。
- **判据**：**对外契约性基础**（字段进入 API 响应或对外数据契约）可观测但不构成行为，属契约存在性条目，出现在 `specify.md` 中并标 `[basic]`，验收方式是结构性断言。**纯内部基础**（数据库列、内部类型、私有签名）不进 specify，只出现在 `design.md` 与 `task/basic.md`。
- **拒绝条件**：把纯内部基础写进 specify；`[basic]` 标识用于描述行为而非契约存在性；标了 `[basic]` 却用行为断言验收。
- **判定者**：specify 作者标注，R2 评审者判定标注是否成立。

`[basic]` 的含义是"该条目为契约存在性、由基础落地承担"，**不是**"这是一条基础行为"。specify 只写外部可观测行为，而 basic 按定义不产生行为——这条规则处理两者的交集，使 specify 定位不被破坏。

## §6 结构决策归属

- **适用节点**：详细设计 + 任务、impl/basic。
- **判据**：结构决策（字段、类型、签名、迁移方向、配置项）一律以 `design.md` 为准。任务文件只做分解与依赖声明，实现只落地已定结构。
- **拒绝条件**：`task/basic.md` 或实现引入 `design.md` 未定的字段、类型、签名、迁移方向或配置项；实现期临时决定结构而不回填 design.md。
- **判定者**：R3 评审者在分类核查中判定任务是否越界；verify/basic 的验证角色判定实现是否引入未定结构。

发现越界时停在 R3 已证闸门，由重规划处理——不得在实现期就地补决策（`SPEC-IMPL-003/AC3`）。

## §7 验证：身份独立、basic 三项、detail 断言范围

- **适用节点**：verify/basic、verify/detail。
- **判据**：验证角色必须独立于实现者——两份工件的**执行身份**小节一比即得。basic 段只判三项：结构存在、可构建、既有测试（若有）无回归；"结构存在"必须由实际读取实现或运行命令得出。detail 段须逐条对照 `specify.md` 的验收判据分别给出断言，依据实际实现与证据判定 `passed`/`failed`，不得只覆盖其中一部分条目。
- **拒绝条件**：impl 与 verify 的执行身份相同；basic 验证声称交付了外部行为（此刻行为尚未实现，任何行为结论都是假的）；以文档、Agent 自述或文件存在判定通过；basic 结论写入实现者所有的工件；detail 验证脱离实际实现与证据、仅凭 specify.md 条目字面或 basic 段的结构性证据判定 `passed`；**basic 段为空时把结论写成 `passed` 或 `failed`**（三项判据无断言对象，两值皆为伪）；**以上游工件自述判空而未自行做代码层断言**。
- **判定者**：验证角色本人给出结论并对结论负责；人工验收节点复核身份独立性是否成立。

两次验证均**无人工节点**（`SPEC-VERIFY-001`、`SPEC-VERIFY-002`、`SPEC-VERIFY-003`）。

**验证角色怎么来：派发一个独立子代理。** 本要求自 `2026-08-28` 修订起适用——**在此之前的实例不因本条被判违反**，其工件中如实记录的"身份独立不成立"是当时控制面未给出路径的结果，不是绕过。

**交接的最小集，四项缺一不可**：

1. **验哪些判据**——`specify.md` 的条目编号，以及本次要给出结论的是哪个节点。
2. **工件在哪**——实例目录与本 step 的路径。
3. **在哪个工作树或分支上操作**。
4. **结论写进哪个文件**。

**这四项从一次实际事故反推**：曾有子代理把提交打到 `main` 而非工作树，**缺的正是第三项**。**四项不是穷举**——子代理冷启动，拿不到实现者的推理过程，只能读工件与代码；交接不足时它会验错对象、写错地方，或如上例把改动落到错误的分支。

**这不是机器强制**：派发是执行者可直接做到的动作，不依赖任何未实现的 CLI 能力。**soft 执行器下同样适用。**

**verify/basic 在 basic 段为空时结论取 `不适用`**——它既不解锁下游，也不是失败、不触发 fail-closed。取值条件、后果与它不适用于 verify/detail 的理由见 `flow.md`「verify/basic」节。

## §8 孤儿阻断

- **适用节点**：verify/detail、人工验收（前置核查）。
- **判据**：不存在"已落地但无消费者"的 basic 改动。每个 basic 任务都能指出被哪些 detail 任务依赖，且该依赖关系的消费者在实际代码中存在。
- **拒绝条件**：verify/detail 未对 basic 任务的被依赖关系做代码层断言即判定通过；存在无消费者的 basic 改动而进入人工验收；以"将来会用到"作为消费者；以删除记录代替显式重规划处理。
- **判定者**：**detail 段验证角色**在 `verify/detail.md` 中依据代码断言每个 basic 任务的消费者存在，做出孤儿判定并写入结论；**验收节点的人类验收者**在 `acceptance.md` 的阻断核查中引用该结论据以阻断，不重新做代码层判定。

存在孤儿时不得进入人工验收，必须由重规划显式处理（复用或删除）后才解除。失效级联作用于工件；已落地的 basic 代码不被自动失效，改由本条阻断处理（`SPEC-ACCEPT-002`、`SPEC-INVALIDATION-001`）。

判定发生在有代码证据的 detail 段验证——验证角色实际读取 task/basic.md 声明的依赖关系并在代码中核实消费者存在；人工验收不重复这项代码层核实，只在阻断核查中引用 `verify/detail.md` 的结论并据以阻断。这与 §7 的分工一致：验证角色对代码证据负责，人工节点对交付放行负责。

## §9 工件阐述方式

- **适用节点**：全部产出工件的节点。
- **判据**：每个工件文件必须**同时**承载可核验的控制事实（绑定了什么上游、执行身份、结论、证据）与人类语义（说明、理由），缺一不可。
- **拒绝条件**：工件只有结论没有证据；只有叙述没有可核验事实；控制事实与人类语义混在同一小节而无法分辨哪部分可核验。
- **判定者**：该工件所属节点的下一个评审或验证角色；链尾工件（摘要）在产出时由摘要作者自检，并在下一次被引用时（例如新 Intake 的来源引用，或后续评审引用既往交付）由引用方复核。

本条约束的是**工件文件内的阐述方式**，**不要求**把工件拆成两个物理文件。`template.md` 的小节划分即按此配比：控制事实与人类语义各有落点（`SPEC-ARTIFACT-001`）。

本节是贯穿**全部产出工件节点**的通用规则，不依附任何单一节点，因此不由 `flow.md` 某个节点专门引用；它的落地形态就是 `template.md` 里每份工件固定包含的控制事实小节与人类语义小节的配比划分——读 `template.md` 即读到本节的落点。

## §10 失败：fail-closed，不预算不学习

- **适用节点**：全部节点。
- **判据**：节点失败（工具错误、验证不过、依赖缺失）时停在 last proven gate，等待人类或 Agent 决定。各节点的具体停靠点见 `flow.md` 每个节点的"失败去向"。
- **拒绝条件**：进行失败次数预算；把失败转为经验学习；自动重试后声称通过；跳过失败节点继续下游；以"稍后修复"推进闸门。
- **判定者**：遇到失败的执行角色必须立即停止并声明；下一个人类节点复核是否真的停在了已证闸门。

失败预算与失败→经验学习属外部知识治理的范畴，**不在 spec 流程内实现**（`SPEC-FAIL-001`）——本流程遇失败只 fail-closed 停下，不计数、不学习。

## §11 人工闸门结论的来源

- **适用节点**：R1、R2、R3、人工验收。
- **判据**：结论必须记录**答复与结论的对应关系**——评审者的哪一句答复构成了这个结论。答复不完整而经追问补齐的，须一并记明追问经过（问了什么、评审者答了什么）。评审者的逐字原话记入该工件的「用户原话」小节（小节划分见 `template.md`）。
- **拒绝条件**：评审者未就该结论表态即写入任何取值；结论缺对应关系记录；记录所引答复不支持该结论；以转述、润色或概括代替逐字原话；**把非授权答复写成授权取值**（评审者只授权继续、未就内容表态时写入 `approved` 或 `accepted`，或自创取值表以外的取值）。

**最后一条与前四条的分工**：前四条管**记录是否齐备自洽**，本条管**取值本身选得对不对**。两者可以互不相干地失效——一处记录齐备、原话逐字、对应关系清楚，取值却选错了，前四条一条也拦不住。取值表以外的取值见 `flow.md`（该表另有 `已授权代行` 供此情形使用）。
- **判定者**：**下一次引用该结论的角色**，在引用发生时判定——判两件事：对应关系记录是否齐备，所引原话是否支持该结论。判不过则不得引用，须回到该结论的评审者处澄清。

本节判定的是**记录是否齐备且自洽**，不是"结论是否由执行体推断补足"——后者在工件文本上与真授权同形，无人可判。**推断补足会在此留下可见痕迹**：要么缺对应关系记录，要么记录所引原话与结论对不上。

**本节的固有弱点，如实写明**：结论若从未被引用，本节的判定永不发生。**本节只保证被引用的结论可被复核**，不保证全部结论都被复核。该弱点无法在当前强制水平下消除——引用与否取决于后续是否真有需求引用它，不是任何角色能决定的。

**本节不由机器执行。** 当前强制水平见 `README.md`；本节的判定全部由人类角色在引用时完成。

## §12 追溯链检出

- **适用节点**：verify/detail（环 2、3）、人工验收（环 4）。
- **判据**：追溯链四环中，环 2、3 用**引用集合包含**检出——上游编号集合须被下游引用到的编号集合完全包含（即"上游有、下游没有"的差集为空）；环 4 检出验收的阻断核查是否引用了验证断言的结论；环 1 只检出 `specify.md` 每个条目是否声明了它来自 `Intent.md` 哪一节。四处落点见 `template.md`。
- **拒绝条件**：差集非空而判通过；未实际运行扫描命令即声称链完好；以"下游没写但意思在那里"代替引用；把环 1 的"有无指向"读作"数量对齐"；把"上游数量 = 下游不同编号数"当作环 2、3 的判据（数量相等不能证明每条上游编号都被引用，二者可能靠不相干的多余编号相互抵消）。
- **判定者**：**verify/detail 的验证角色**在验证时判环 2、3，结论写入该节点工件；**人工验收的验收者**在验收时判环 4。

环 2 的扫描形态分两步——**先展开，再取差集**。上游取 `specify.md` 的 `### SPEC-` 条目编号集合；下游取 `task/detail.md` 中出现的编号，按下列三种写法**展开为完整编号集合**后，用前者减去后者（`comm -23`，两侧先排序去重）为空则通。**环 3 适用同一套识别与展开规则**：上游取 `task/detail.md` 的 `### T-D` 条目编号集合，下游取 `verify/detail.md` 中出现的 `T-D` 编号，同样先展开三种写法再以差集为空判通。

**三种写法**（`SPEC-` 与 `T-D` 编号同适用）：

| 写法 | 形态 | 展开为 |
| --- | --- | --- |
| **完整** | `SPEC-CLAIMCLI-002` | 该编号本身 |
| **逗号并列** | `SPEC-CLAIMCLI-002、004` | `002` 与 `004`，裸数字继承前面的主题前缀 |
| **区间** | `SPEC-CLAIMFORM-001 至 005` | 闭区间内全部编号，即 `001`–`005` |

**三种写法的书写要求见 `template.md`「编号引用写法」**——那一节规定怎么写，本节规定据此怎么展开。其中裸数字与完整编号的位置关系是把"编号"与散文里的普通数字分开的唯一依据：`task/detail.md` 里大量存在"第 1、2 条""六条任务"这类数字，缺了它，扫描会把它们当作编号命中，**从而把误报换成漏报**。**漏报比误报危险：误报会被人发现，漏报不会。**

**不采用"放宽比对"**（即下游只要出现过该数字就算命中），理由同上——放宽正是上面所说的把误报换成漏报。

**三种写法不是新发明**：`grep -rnE 'SPEC-[A-Z]+-[0-9]+(、[0-9]+)+|SPEC-[A-Z]+-[0-9]+ 至 [0-9]+' .themis/workspace/spec/*/step*/task/detail.md | wc -l` → `4`，三个已完成实例自发在用，控制面此前零规定。**写法的规定见 `template.md`「编号引用写法」。**

**横切保护判据与 `[横切]` 标识**——有一类判据验证的**不是本 step 的产出，而是本 step 不该扰动的既有东西**。它按定义不映射到任何任务，因而"上游有、下游没有"对它是正确状态，不是漏引。

- **判定方法**（一问即可）：这条判据验的东西，是本 step 做出来的，还是本 step 之外、只要求"别弄坏"的？**后者才是横切。**
- **标注形态**：`### SPEC-<主题>-<序号> [横切]`，与 `[basic]`（§5）同形，不引入第二种标注方式。
- **扫描处置**：带 `[横切]` 的条目**不计入上游集合**，因而不参与差集。
- **判定者**：条目作者标注，**R2 评审者判定标注是否成立**——与 §5 同构。标错了要在落地前发现；留到 verify/detail 时任务已按错误分类写完。
- **拒绝条件**：拿 `[横切]` 规避映射义务（本可由任务承担却标成横切）；标了 `[横切]` 却验证本 step 自己的产出；**以"落地前就已满足"作为判横切的依据**。

**最后一条拒绝条件须单独说明，它是本边界最易被定歪的方向。** 反例：`SPEC-CLAIMCLI-005`（"CLI 缺席或不可用时流程不得被阻塞"）落地前后同样满足，**但它不属横切**——它约束的是本 step 自己能产出什么（不得引入与降级冲突的条款），因而可以、也确实映射到了任务。**"落地前是否已满足"是表象，"验证对象归谁"才是分界。**

**本标识的边界经既有判据检验**：`grep -h '^### SPEC-' .themis/workspace/spec/*/step*/specify.md | grep -v 'TRACESCAN' | wc -l` → `24`，逐条按上述方法分类，横切仅 `1` 条（`SPEC-WSCLEAN-005`——它验 Go 构建与既有测试，而该 step 只删 Markdown）。**规则的正确性由这 24 条的分类结果背书**，那 24 条来自四个已完成需求，非为本规则而写。

**本节的能力边界，如实写明**：集合包含只能发现**漏引**——下游少引了上游某条。它发现不了**引错**：引了一个存在的编号，但那条任务其实没有承担该条目。发现引错需要逐条读语义，不在本节能力内。**下游出现上游没有的编号，本身不判失败**——那可能是合法写法（例如记录"某项无判据覆盖"而借用编号空间说明），检出只看上游是否被下游覆盖；但这类多出的编号**不得被用来凑数**，即不得以"下游编号总数 ≥ 上游条目数"代替差集为空的判定。

**环 1 的精度低于其余三环**：`Intent.md` 的诉求不编号（那会让 Intake 变成填表），因此环 1 只能查"有没有指向"，不能查"数量对不对"。

**环 4 不取集合或计数形态，如实写明原因**：`acceptance.md` 的阻断核查按 §8 是**引用**`verify/detail.md` 的结论，不逐条重做断言（分工见 §8）；对环 4 做计数或集合对齐会要求阻断核查逐条复述验证断言，与该分工冲突，因此环 4 只检出"是否引用"，不检出"引用是否覆盖全部断言"。
