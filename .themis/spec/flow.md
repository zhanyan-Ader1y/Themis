# .themis/spec/flow.md

本文件只回答一个问题：**现在能不能走到下一步**。判定规则（这一步怎么判过不过）一律不在此处给出，指向 `rules.md` 的对应小节。

本文件永久单文件。流程契约本质是一张图，闸门的前置是上游节点的产出，失效级联跨节点波及，价值在于能被一次读完。拆成 `nodes/*.md` 后，读某一节点的人看不到"它的失效会波及谁"，而漏读上下游关系正是失效级联最易出错处。**这条与体量无关**：长到五百行也不拆，只在内部分节。

## 节点序列

```text
Intake（不可变来源 + 来源绑定 claims）
→ 追问（多轮，未答不得判收敛）
→ R1 意图评审 ────────────── 人工（确认需求本身 + step 分解）
┌─ 每个 step 各走一遍以下十一个节点 ────────────────
│ → step 定界（scope.md，无闸门）
│ → 抽象设计（specify）
│ → R2 抽象设计评审 ──────── 人工
│ → 详细设计 + 任务（分 basic / detail 两组）
│ → R3 详细方案评审 ──────── 人工
│ → impl/basic
│ → verify/basic ─────────── 机器判，无人工节点
│ → impl/detail
│ → verify/detail ────────── 机器判，无人工节点
│ → 人工验收 ─────────────── 人工
│ → 摘要
└────────────────────────────────────────────────
全部 step 的摘要产出后，`Intent.md`「step 分解」所载需求达成。
```

人工节点固定四处——R1、R2、R3、验收；两次验证均无人工节点。**R1 在 spec 级只发生一次**（它确认的是完整需求与分解方式）；**R2、R3、验收每个 step 各一次**。step 定界节点无闸门——`scope.md` 的合法性由 R1 已批准的 step 分解背书。

## 通用失败去向

任一节点失败时 **fail-closed**，停在 last proven gate（最近已证闸门）。系统**不得**进行失败次数预算，也**不得**把失败转为经验学习（`SPEC-FAIL-001`）。何为失败、停靠后由谁决定，判定见 `rules.md` §10。

每个节点完成后，执行者必须更新实例 `state.md` 的当前节点、该节点闸门结论、当前性三项（小节定义见 `template.md`）；`state.md` 是 soft 执行器（`SPEC-ENFORCE-001`）下判定"停在 last proven gate"的依据。

**闸门结论取值按节点类型固定，不得跨类混用：**

| 节点类型 | 合法取值 |
| --- | --- |
| 人工评审（R1/R2/R3） | `approved` / `驳回` / `已授权代行` |
| 人工验收 | `accepted` / `退回` / `已授权代行` |
| 验证（verify/basic、verify/detail） | `passed` / `failed`；verify/basic 另有 `不适用`（见该节） |
| 其余节点（Intake、追问、step 定界、抽象设计、详细设计 + 任务、impl/basic、impl/detail、摘要） | `已走完` / `进行中` / `未开始` |

**`已授权代行` 的含义与限制**——评审者授权执行者继续推进，但**未就本节点的方案内容表态**。它把"授权"与"表态"分开：授权确实存在，表态确实没有。

- **它不等于通过。** 取该值的节点**未获内容层面的批准**。
- **下游节点不得据它开始。** 取该值时**停在本节点**；要往下走，须评审者就内容另行表态，届时改写为该节点类型的正式取值。
- **不得据它解锁**——这一条没有例外，也不留解释余地。**一个表示"未表态"的取值若能让下一节点开工，等于流程唯一的人类闸门由执行体自行放行。**

**取该值时，工件须记明评审者的逐字答复与"未就内容表态"这一判断的依据**（`rules.md` §11）。

`已走完` 只表示**该节点已产出其规定工件**，不含任何"判据是否满足"的结论——那属于下游验证或评审节点。实现节点在空段下同样取 `已走完`，其含义仍是"本节点已走完、零落地调用"，不表示有改动落地。**不得**用 `已走完` 表示验证通过，也**不得**给验证节点写 `已走完`。

**闸门强制通则**：任一节点在其前置闸门未满足时**不得开始**；已开始的须停止并退回该前置所在节点。各节点的前置闸门见其自身小节，本条不复述。

**前置的可查形态**：每个节点开始时，须能从实例 `state.md`「各闸门」读出其前置闸门的结论。**这把"前置是否满足"从执行者的记忆变成可查记录**——某节点有结论而其上游没有，即是跳过留下的缺口。

**判定者**：该节点自身在开始前自查；**下一个人工闸门在其评审或验收时复核**——人工闸门本就要读 `state.md`，复核"上游各闸门是否都有结论"不增加负担（`SPEC-GATE-001`）。**链尾兜底**：摘要是链尾节点，之后没有下游人工闸门可复核；其自身前置闸门（验收结论为 accepted）由摘要作者在产出时自检，并在下一次被引用时（例如后续 step 的 Intake 来源引用本次交付，或后续评审引用既往 summary）由引用方复核——与 `rules.md` §9 对链尾工件的处理一致。

**本条的边界，如实写明**：它**阻止不了**不自觉的执行体跳过前置——当前强制水平下没有拦截点（见 `README.md`）。它能做到的是让跳过在 `state.md` 留下可查缺口，由下一个人工闸门发现。

## Intake

- **前置闸门**：收到新用户请求。
- **产出**：不可变来源记录；`Intent.md` 的来源引用小节获得初始条目。
- **失效波及**：本节点是链首，无上游可失效；其自身变更使全部下游工件 stale。
- **失败去向**：无 last proven gate，停在链首等待重新提交请求。

用户确认 source-bound claims 之前，不得进入任何设计或实现节点（`SPEC-INTAKE-001`）。claims 的来源引用格式与分层事实源规则见 `rules.md` §1。

## 追问

- **前置闸门**：Intake 已产出不可变来源。
- **产出**：`QA.md` 追加第 N 轮问答（追加写入，不覆盖）；`Intent.md` 的问题/期望结果/核心链路小节被更新。
- **失效波及**：`Intent.md` 变更使 R1 结论及其下游全部 stale。
- **失败去向**：停在 Intake 已证闸门。

多轮进行，每轮问答形成不可变记录。收敛判据见 `rules.md` §2——未回答的问题不得判定为"已收敛"。

## R1 意图评审（人工）

- **前置闸门**：意图已判定收敛（`rules.md` §2）。
- **产出**：`intent-review.md` 的投影 / 未解决反馈 / 结论三节。
- **失效波及**：结论为 approved 才解锁抽象设计；`Intent.md` 变更使本结论 stale，需重新评审（**例外见下**）。
- **失败去向**：未批准则停在追问节点，继续追问或修订 `Intent.md`。

投影必须由抽象到具体渐进呈现，只含该抽象层增量（`rules.md` §3）。未批准前抽象设计节点不得开始。

**本节点确认两件事**：用户的完整需求本身，以及它的 **step 分解**（`Intent.md`「step 分解」小节）——拆成哪几个 step、各自承担什么、全部完成才算需求达成。分解经本节点批准后，各 step 的 `scope.md` 即由它背书，不再单独评审。

**失效级联例外（`SPEC-INVALIDATION-001` 的唯一例外）**：仅新增或细化「step 分解」小节、且不改变任何已有 step 目标语义的 `Intent.md` 修订，**不使已 accepted 的 step 失效**，也不使本结论 stale——它没有改变那些 step 当初被批准时所依据的任何前提。此修订仍须经 R1 评审者确认新增的分解项。**超出这一范围的任何 `Intent.md` 变更照常触发完整级联**：改动已有 step 的目标语义、期望结果、核心链路或范围与非做，一律使下游全部 stale，已 accepted 的 step 亦然。

## step 定界（scope.md）

- **前置闸门**：R1 结论为 approved 且未 stale。
- **产出**：`step<N>/scope.md` 的承担的上层分解项 / 本 step 边界 / 与其他 step 的关系三节。
- **失效波及**：本文件变更使本 step 的 specify 及其下游全部 stale；不波及其他 step。
- **失败去向**：停在 R1 已证闸门。

**本节点不设闸门，也不产生新授权。** 它只把 R1 已批准的某一个分解项落到本 step，写明承担哪一块、边界到哪为止、与其他 step 如何划界。**不得在此引入 R1 分解项之外的目标**——那属于新增需求，须回到 `Intent.md` 走 R1 的分解修订（例外条款见 R1 节）。「承担的上层分解项」必须指向 `Intent.md`「step 分解」中的具体一项，指不到即为越界。

## 抽象设计（specify）

- **前置闸门**：R1 结论为 approved 且未 stale；本 step 的 `scope.md` 已产出。
- **产出**：`step<N>/specify.md` 的行为条目与来源覆盖两节。
- **失效波及**：本文件变更使 R2 结论、design.md、任务、验证、验收全部 stale。
- **失败去向**：停在 R1 已证闸门。

specify 即抽象设计——同一节点的两个叫法，不存在独立于抽象设计之外的第二份 specify 工件。行为条目用 EARS 句式表达使每条可判定通过/失败（`SPEC-EARS-001`）。`[basic]` 标识的含义见 `rules.md` §5，`[横切]` 见 §12。

## R2 抽象设计评审（人工）

- **前置闸门**：`specify.md` 成形。
- **产出**：`step<N>/design-review.md` 的投影 / 未解决反馈 / 结论三节。
- **失效波及**：结论 approved 才解锁详细设计；`specify.md` 变更使本结论 stale。
- **失败去向**：未批准则停在抽象设计节点。

投影须含架构或时序 Overview（`SPEC-REVIEW-R2`），低负担要求见 `rules.md` §3。

**本节点须核对判据与边界是否冲突。** R2 评审者核对本 step `specify.md` 的验收判据与该 step **已确认的边界**（含 `scope.md` 提出的、以及 R2 当场裁定的），**冲突即驳回或当场裁定处置**。

**实发依据**：某 step 的判据以 `go build`／`go test` 为主，而同一 step 的安全边界裁定只放行只读查询命令——**`go` 不在其中**。判据写在抽象设计节点、边界裁定在本节点，**两者都在落地之前，冲突在那一刻即可推出**；但没有任何节点负责交叉核对，直到 impl 跑起来才发现，该 step 的判据因此改由人工判定。

**这条不是重复 step 定界的职责**。边界的**暴露**属该节点（见其小节"边界到哪为止"），实践中也已有效——某实例的 `scope.md` 就在该节点提出了"本 CLI 会执行工件里写下的命令"这处安全边界并明写"不得默默实现"。**本条补的是缺失的交叉核对：边界暴露了、判据也写了，但没人把两者放在一起看。**

## 详细设计 + 任务

- **前置闸门**：R2 结论为 approved 且未 stale。
- **产出**：`step<N>/design.md`；`step<N>/task/basic.md` 与 `task/detail.md`（有序两组）。
- **失效波及**：design.md 变更使两份任务、两次实现、两次验证、验收全部 stale；单份任务变更只使其对应实现与验证 stale。
- **失败去向**：停在 R2 已证闸门。

任务必须在 R3 之前完成 basic/detail 分类（`SPEC-IMPL-002`），判定见 `rules.md` §4。结构决策归属见 `rules.md` §6——任务文件只做分解与依赖声明，不得引入 design.md 未定的结构。两段恒定存在，**允许为空**；空段不产生落地调用，也不构成路径分支。

## R3 详细方案评审（人工）

- **前置闸门**：design.md 与两份任务成形，且 basic/detail 分类已完成。
- **产出**：`step<N>/task/review.md` 的评审范围 / 分类核查 / 未解决反馈 / 结论四节。
- **失效波及**：结论 approved 才解锁实现；design.md 或任务变更使本结论 stale。
- **失败去向**：未批准则停在详细设计 + 任务节点。

一次评审同时覆盖 `task/basic.md` 与 `task/detail.md`，不拆成两次人工评审。未解决反馈必须为空才可批准（`SPEC-REVIEW-R3`）。本节点适用 `rules.md` §3（评审投影低负担）、§4（basic/detail 判定，分类核查在本节点完成）、§6（结构决策归属，任务是否越界在本节点判定）。

## impl/basic

- **前置闸门**：R3 结论为 approved 且未 stale。
- **产出**：`step<N>/impl/basic.md` 的执行身份 / 实际改动 / 与批准范围的偏差 / 命令记录四节，以及实际代码改动。
- **失效波及**：本节点产出变更使 verify/basic 结论 stale。
- **失败去向**：停在 R3 已证闸门。

实现必须在 R3 批准范围内——不得修改 current-request、plan 或验收要求，不得做无关重构（`SPEC-IMPL-001`）。basic 段为空时本节点不产生调用，直接进入 impl/detail。本节点适用 `rules.md` §1（来源与分层事实源）、§6（结构决策归属）。

## verify/basic

- **前置闸门**：impl/basic 完成。
- **产出**：`step<N>/verify/basic.md` 的执行身份 / 断言与实际结果 / 命令证据 / 结论 / 说明五节。
- **失效波及**：结论通过才解锁 impl/detail；impl/basic 变更使本结论 stale。
- **失败去向**：结论不通过则停在 R3 已证闸门，由重规划处理。

**无人工节点**——机器判。判据、判定者与断言范围见 `rules.md` §7。结论必须写入验证角色所有的工件，不得写入实现者所有的工件。

**验证角色由独立子代理承担。** 实现完成后派发一个新的子代理执行本节点，交接内容见 `rules.md` §7。**未由独立子代理承担时，本节点不得给出结论**——`state.md` 该行取 `进行中`，流程停在 impl 节点。**不设"记明理由即可放行"的出路。**

**拦截点在动作发生前，不在结论写出后。** 判"已写出的结论无效"拦不住任何东西：**由实现者写出的结论，在文本上与独立验证者写出的无从区分。**

**结论取三值：`passed` / `failed` / `不适用`。** `不适用` 仅在 basic 段为空时成立——三项判据没有断言对象，既非通过也非不通过。取该值时：本节点不解锁 impl/detail（impl/detail 此时的前置闸门另有取值，见该节），**不触发失败去向、不构成 fail-closed 停靠**（`SPEC-FAIL-001` 管的是节点失败，`不适用` 不是失败）。取该值必须在工件「结论」小节写明它由空段导致，并附本节点自行做出的空段代码层断言——不得仅凭上游工件自述判空。

`不适用` 是本节点独有的取值，不适用于 verify/detail：detail 段为空意味着本 step 没有任何落地产物，那是 R3 分类判定的问题，不由验证节点吸收。

## impl/detail

- **前置闸门**：verify/basic 结论通过；basic 段为空时前置闸门为 R3 approved。
- **产出**：`step<N>/impl/detail.md` 的四节，以及实际代码改动。
- **失效波及**：本节点产出变更使 verify/detail 结论 stale。
- **失败去向**：停在 verify/basic 已证闸门；basic 段为空时停在 R3 已证闸门。

**basic 段非空时**，其通过结构性验证前 detail 段不得开始（`SPEC-IMPL-002`）；**basic 段为空时本句不适用**——空段没有可验证的落地产物，verify/basic 的结论为「不适用」，此时前置闸门取本节所列的 R3 approved。本节点适用 `rules.md` §1（来源与分层事实源）。

## verify/detail

- **前置闸门**：impl/detail 完成。
- **产出**：`step<N>/verify/detail.md` 的五节。
- **失效波及**：结论通过才解锁人工验收；impl/detail 变更使本结论 stale。
- **失败去向**：结论不通过则停在 verify/basic 已证闸门。

**无人工节点**——机器判。不得依据文档、Agent 自述或文件存在判定通过（`SPEC-VERIFY-002`）。验证者身份必须独立于实现者，判据与判定见 `rules.md` §7。

**验证角色由独立子代理承担**，交接内容见 `rules.md` §7。**未由独立子代理承担时，本节点不得给出结论**——`state.md` 该行取 `进行中`，流程停在 impl/detail 节点。**不设"记明理由即可放行"的出路。**

孤儿阻断的判定同样在本节点完成，结论写入本节点工件 `verify/detail.md`；判据、拒绝条件与判定者见 `rules.md` §8。

追溯链环 2、3 的检出在本节点完成，判据与判定者见 `rules.md` §12。

## 人工验收（人工）

- **前置闸门**：verify/detail 结论为 `passed`，且孤儿阻断核查通过（`rules.md` §8）。
- **产出**：`step<N>/acceptance.md` 的交付视图 / 阻断核查 / 用户原话 / 结论四节。
- **失效波及**：结论 accepted 才解锁摘要；任一上游变更使本结论 stale。
- **失败去向**：未接受则停在 verify/detail 已证闸门。

存在已落地但无消费者的 basic 改动时不得进入本节点，解除条件见 `rules.md` §8（`SPEC-ACCEPT-002`）。人工验收在 step 末尾**只有一次**，不因落地分两段而分两次。本节点适用 `rules.md` §7（验证身份独立）、§8（孤儿阻断，在本节点据结论阻断）、§12（追溯链环 4 的检出在本节点完成）。verify 提供的是证据，不构成授权——人工验收是流程中唯一的授权点。

## 摘要

- **前置闸门**：验收结论为 accepted。
- **产出**：`step<N>/summary.md`，绑定实际交付。
- **失效波及**：本节点是链尾。
- **失败去向**：停在验收已证闸门。

仅当验收 accepted 后 lifecycle 才可标记完成（`SPEC-SUMMARY-001`）。摘要产出中性工件——不含任何外部知识库的概念，不以其存在为前提。是否把它喂给某个知识库由可选 adapter 决定，该决定在本流程之外（`SPEC-THEMICO-002`）。
