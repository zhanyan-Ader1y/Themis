## 结构决策

### 一、改名用 `git mv`，不用删建

**决策**：八个目录逐个 `git mv`。

**为什么**：`git mv` 保留文件历史，`git log --follow` 可跨改名追踪。删除再新建会使每份工件的历史断在今天——**而工件的价值有一半在于"它当初是怎么写的"**。

### 二、引用替换按"路径优先、裸名其次"分两轮

**决策**：先替换 `workspace/spec/<旧 id>` 这种带路径前缀的，再替换剩余的裸 id。

**为什么分两轮**：裸 id（如文中提到"`core-removal` 那次"）与路径里的 id 形态不同，一轮全局替换会把两处例外一并改掉。**分两轮可在第二轮逐处确认。**

**已知代价**：第二轮须逐处看，无法全自动。**八个 id 的裸名出现处数不小，这是本 step 最耗时的部分。**

### 三、两处例外加"脉络注"，不改原文

**决策**：各加一句形如"该实例现名 `<新 id>`"的说明，**紧邻原文但不替换它**。

**为什么**：追问第 2 轮已裁定——改了会使记录所陈述的事实变化。**加注则两件事都在**：当初写的是什么、现在它叫什么。

**注的位置须紧邻**：隔远了读者读到原文时不会看到注，等于没加。

### 四、日期取 git 首次提交日，不取今天

**决策**：八个实例各取其 `git log --diff-filter=A` 的最早日期，已在 `Intent.md` 列出。

**为什么不统一取今天**：那会使八个实例的前缀全部相同，**排序功能完全失效**——而排序正是加前缀的理由。

## 取舍

**取**：`git mv`（保历史）、分两轮替换（可控但耗时）、加注不改原文（两件事都在）、按 git 日期（排序有效）。

**舍**：删建（快但断历史）、一轮全局替换（快但会误改例外）、改原文（整洁但篡改记录）、统一取今天（省事但排序失效）。
