### SPEC-SPECID-003

指向旧 id 的引用必须同步更新，**两处例外除外**。

**验收判据**：

`grep -rl 'spec/core-removal' .themis/workspace/spec/2026-08-19-core-removal .themis/workspace/spec/2026-08-26-workspace-cleanup docs/plan | wc -l` → `0`

**本条判据被本 step 的批量替换改坏，订正两次，如实记明**：

1. **第一次**：替换把 `'workspace/spec/core-removal'` 改成 `'workspace/spec/2026-08-19-core-removal'`——**而那个路径现在确实存在，判据因此永远无法证明"旧引用已清零"**，它验的东西正好反了。
2. **第二次**：改回查旧路径后实跑得 `1` 而非 `0`——**命中的是本判据自己**。判据的搜索串写在本文件里，全树扫描必然扫到它自身。**这是一条自指判据，按原样无法证伪。**

**改为只扫不含本判据的目录**：两个引用量最大的实例目录加 `docs/plan`。**该取法的弱点如实标出**——它不覆盖全树，**verify 节点须另跑一次排除本文件的全树扫描**。

**语义部分由 R2 判定**：两处例外是否确实未被改动，且各加了指向新 id 的说明。

**依据**：R1 裁定引用同步更新；追问第 2 轮裁定两处例外不改。

### SPEC-SPECID-004

两处例外必须保持原文，并各加一句指向新 id 的说明。

**验收判据**：

`grep -c '不合格：core-removal 的 verify/detail 零漂移' .themis/skills/spec-review-presentation/SKILL.md` → `1`

**本条判据落地后两次订正，如实记明**：

1. **初稿写作 `grep -c 'core-removal' …` → `1`，落地后实跑得 `2`**——因为本 step 按 R2 批准的做法给该文件加了脉络注，注里也提到了 `core-removal`。**判据的意图是"示例原文未被改动"，而初稿测的是"该词全文出现几次"**：加注使后者变化，前者未变。
2. **更要紧的一处**：本 step 的批量替换**把这条判据自己也改了**——`'core-removal'` 被替换成 `'2026-08-19-core-removal'`，于是判据变成"查新 id 出现几次"，**与它要验的事完全无关**。

**改为直接断言示例原文那一行仍在**，两个问题一并解决。

**第 2 处值得单独记**：**批量替换会改到描述替换本身的文字**——本 step 的判据、`Intent.md` 的现状描述与测量表都被改到，逐处订正回原文。**这是"改名"这类需求的固有风险，`design.md` 未预见。** 第 `29` 次同型实发。

**依据**：追问第 2 轮裁定。**改了它们会使记录所陈述的事实发生变化**——历史计划记的是"当时规定用这个名字"，`SKILL.md` 记的是一个反面示例当初演示的东西。

## 本节点标出、须 R2 判定的一处

**判据 003 的取法只查了 `2026-08-19-core-removal` 一个 id，不是八个。**

**理由**：八个 id 逐个写判据会使本节冗长，而 `2026-08-19-core-removal` 是引用最多的一个（`29` 份文件）——**它归零，其余七个大概率也归零，但那是推测不是证明**。

**本节点如实标出该弱点**：判据 003 **不足以证明全部引用都已更新**。verify 节点须补跑其余七个，**判据本身不因此改写**——改写会使本节膨胀到八条同形判据，可读性代价大于收益。

**若 R2 认为该弱点不可接受**，判据 003 应改为覆盖八个 id 的形态。
