## 第 1 轮

**本轮只提一个问题。** 另两项候选经核实后自行判定，理由记于末节。

### 问 1（范围）既有八个实例要不要改名？

**背景**：所有者的指示是"每个 spec-id 需要在前面加上 `yyyy-MM-dd`"。**"每个"字面上包含既有八个**，但改名的代价是本节点实测出来的、指示发出时双方都未必知道的。

**实测**：八个实例被其他文件引用合计 `133` 处，**引用嵌在已闭合工件的正文里**——包括其他实例的 `Intent.md`、`design-review.md`、以及带 `accepted` 结论的 `acceptance.md`。

**两条路**：

- **(a) 只规定新建，既有不改**。既有工件一字不动。**代价**：两种格式长期并存；"按创建顺序排序"对既有八个不成立。
- **(b) 既有一并改名**，同时批量更新 `133` 处引用。**代价**：动已验收工件的正文——**而「不改证据去迎合判据」正是三次裁定确立的原则**。

**这一条与 `gate-value-integrity` 那次不同，须说明**：那次改的是**合同未定义的无效取值**，所有者据此裁定"该原则不保护无效状态"。**本次不同——`core-removal` 这个 id 在当时完全合法**，它不是无效状态，只是不符合新格式。**照那次的边界，本次属该原则禁止的范围。**

**执行者倾向 (a)**，但**不构成推荐**：所有者的原话是"每个"，而执行者无权把"每个"读成"每个新建的"——**那正是推断补足**。

**答**：「改名」——取 (b)，与执行者倾向相反。

**裁定内容**：既有八个实例一并改名为 `yyyy-MM-dd-<主题>`，`133` 处跨文件引用同步更新。

**该裁定推翻了执行者的倾向**，并**再次划定「不改证据去迎合判据」的边界**：上一次（`gate-value-integrity`）确立的是"不保护合同未定义的无效状态"；**本次进一步确立——该原则保护的是记录的内容真实性，不保护标识符的字面形态**。改 id 与更新指向它的引用，不改变任何记录所陈述的事实。

**来源**：用户确认#本次指示（"每个 spec-id"）；代码#本节点实测的 `133` 处引用；代码#`gate-value-integrity/intent-review.md`（「不改证据」边界的既有裁定）。

## 自行判定、未提出的两项

### 一、格式取 `yyyy-MM-dd-<主题>`——自行判定

**依据**：所有者已明确指示"在前面加上 `yyyy-MM-dd`"，**格式本身无选择余地**。`docs/adr/AGENTS.md` 的既有做法同形（`YYYY-MM-DD-<主题>.md`），沿用不引入新概念。

### 二、日期取哪一天——自行判定为**实例创建日**

**依据**：`docs/adr/AGENTS.md` 明写其日期前缀是"该决策**被裁定的日期**，不是文件创建日期"。**ADR 与 spec 实例的性质不同**：ADR 记的是一个时点的决定，而 spec 实例是一段跨越多日的流程——**没有单一的"被裁定日"**（R1、R2、R3、验收各有其日）。

**故取创建日**，即 Intake 产出之日。**它可从 git 取得，不需任何人记忆或约定**——八个既有实例的创建日已在 `Intent.md` 逐个列出。

## 第 2 轮

### 问 2（范围）两处例外与路径断言怎么处置？

**背景**：step 定界暴露两处 R1 未预见的情形——(a) 两处引用改了会篡改记录内容（历史计划的"spec-id 固定为 `core-removal`"、`SKILL.md` 的反面示例）；(b) 改名后既有工件里的路径断言会失效。

**执行者把具体后果摆出后提问**：改历史计划那句会变成"固定为 `2026-08-19-core-removal`"，而当时实际规定的就是前者；改 `SKILL.md` 示例则该示例演示的"读者不知道这代表什么"不再是当初那件事。

**答**：「改路径断言，两处例外不改」。

**裁定内容**：

1. **既有工件里的路径断言跟着改名更新**——否则一批工件永远报执行失败。
2. **历史计划与 `SKILL.md` 反面示例保持原样**，各加一句说明指向新 id。

**该裁定与 R1 的效力边界一致**：R1 明写"凡改动会使记录所陈述的事实发生变化的，仍属该原则禁止"——**这两处正是后者，路径断言不是**。

**来源**：用户确认#第 2 轮；代码#`scope.md` 事实（2）、（3）。
