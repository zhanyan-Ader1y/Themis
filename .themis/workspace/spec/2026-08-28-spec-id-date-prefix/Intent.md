# Intent.md — 2026-08-28-spec-id-date-prefix

> 本文件是 Intake 节点的实例工件。本节点的前置闸门与产出见 `flow.md`「Intake」节。以上只指向位置，本文件不复述其文字。

## 触发

所有者指示：**优化 spec-id 的格式，每个 spec-id 需要在前面加上 `yyyy-MM-dd`。**

**本实例自身即按新格式命名**——`2026-08-28-spec-id-date-prefix`，是该格式的第一个使用者。

## 现状

`template.md` 第 `5`、`10` 行以 `<spec-id>` 指代实例目录名，**但控制面从未规定 spec-id 的形态**——不规定字符集、不规定长度、不规定是否带日期。

八个既有实例当时全部是纯主题名（`core-removal`、`workspace-cleanup` 等，**此处保留改名前的原名**——本节记的是改名前的现状，写成新名会使本句自相矛盾），**按创建先后无从排序**：目录列表按字母序排，与实际发生顺序无关。

**同一问题在本项目已有先例并已解决**：`docs/adr/AGENTS.md` 规定 ADR 文件名为 `YYYY-MM-DD-<主题>.md`，并写明理由——**不使用序号**，因为序号需要维护"下一个用几"这个状态，而日期前缀天然有序、可从内容自证、无需任何人维护计数。

**本需求是把该既有做法推广到 spec 实例。**

**但引用嵌在已闭合工件里**——抽样 `2026-08-19-core-removal`，引用它的文件包括其他实例的 `Intent.md`、`QA.md`、`design-review.md`、`verify/basic.md` 以及带 `accepted` 结论的 `acceptance.md`。

**这直接触及「不改证据去迎合判据」**（三次裁定确立）：改名意味着批量修改已验收工件的正文。

## 收敛主张

**新建实例一律用 `yyyy-MM-dd-<主题>` 格式，写进控制面。**

**既有八个实例是否改名，是本需求的真问题**，两条路各有代价：

- **改名**：目录与引用全部一致，代价是动 `133` 处已闭合工件正文。
- **不改名**：既有工件一字不动，代价是两种格式长期并存，且"按创建顺序排序"这一好处对既有实例不成立。

## 拟定的 step 分解

**待 R1 确认。** 拟为**一个 step**：

- **把 spec-id 格式写进控制面，并处置既有八个实例。** 格式规定与既有处置不可分——只规定格式而不说既有怎么办，下一个人会自行决定，产生第三种状态。

## 来源引用

本节全部数字与存在性断言均按 `template.md`「断言形态」记法书写，由本节点当场跑出。

- **ADR 已有同类规定**：`grep -c 'YYYY-MM-DD' docs/adr/AGENTS.md` → `2`

**本条初稿两处错，均由 `themis verify` 与实跑抓到，如实记明**：

1. **搜索模式里带尖括号，被工具拒绝执行**——它把模式内的 `>` 当成输出重定向。**这与 `2026-08-28-gate-value-integrity` 报出的 `\|` 三义缺陷同族**：工具无法区分 shell 语法与被搜索的字面文本。**规避方式是模式里不写尖括号**，同样未写入控制面。
2. **改用不含尖括号的模式后，实跑得 `2` 而非初稿写的 `1`**——`YYYY-MM-DD` 在该文件出现两处（命名规定一处、结构小节示例一处）。**本项目第 28 次同型实发。**
- **ADR 明写不用序号的理由**：`grep -c '序号一旦与实际顺序脱节' docs/adr/AGENTS.md` → `1`
- **控制面对 spec-id 形态的规定处数**：`grep -c 'spec-id' .themis/spec/template.md` → `2`（两处均只作占位符使用，不规定形态）
- **跨实例引用合计**：`133` 处（八个实例逐个 `grep -rl` 后相加，取法：排除该实例自身目录）
