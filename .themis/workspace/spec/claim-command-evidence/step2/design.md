## 结构决策

### 1. 解析：按行扫描，用反引号段数分辨两种记法

断言形态规定"单个断言写在一行内"，因此**逐行扫描即可**，不需要 Markdown 解析器。

一行中若含 `` ` `` 包裹的段落且以 `→` 分隔：**两段为两段式、三段为三段式**（`design.md` 与 `template.md` 已定的分辨规则）。

**不解析的行直接跳过**——工件里绝大多数行不是断言。**这一点决定了 CLI 的失败模式是"漏检"而非"误报"**：写得不合形态的断言会被静默跳过，而不是报错。

**该取舍如实标出**：漏检意味着"没按形态写"的断言逃过校验。**但反过来（对每行都要求合形态）会让 CLI 对所有散文报错，不可用。** 形态合规性由验证角色判（step1 已定），CLI 只管合形态的那些。

### 2. 白名单：命令首词匹配，默认拒绝

取**首词**（第一个空白之前的部分）与白名单比对，不在名单内即拒绝并报错。

**初始名单**：`grep`、`wc`、`find`、`ls`、`git`、`awk`、`sed`、`test`、`cat`、`head`、`tail`、`comm`、`sort`、`uniq`、`diff`。

**三处必须说明的限制**：

- **`git` 整体放行，未限定子命令。** `git log` 只读，但 `git` 也能改仓库。**收窄到 `git log`/`git diff`/`git show` 等子命令更严**，但会让 `git rev-parse` 这类常用查询失效。**取整体放行，如实记为已知宽口。**
- **`sed`/`awk` 可写文件**（`sed -i`、`awk > file`）。它们在本项目断言里几乎全用于只读取值，但**名单无法从首词区分只读与写入**。
- **管道与重定向**：断言里的命令常含 `|`。**若用 shell 执行，白名单就形同虚设**——`grep x | rm -rf y` 的首词是 `grep`。**因此本设计不经 shell 执行**，见第 3 条。

### 3. 执行：不经 shell，管道由 CLI 自己串联

**关键决策**：用 `exec.Command` 直接执行，**不传给 `sh -c`**。

含管道的断言由 CLI 自行按 `|` 切分，**逐段都过白名单**，再用 `io.Pipe` 串联。

**理由**：经 shell 执行会让白名单失效（第 2 条末），而白名单是所有者裁定的安全边界。**不经 shell 是让白名单真正生效的唯一方式。**

**代价如实标出**：CLI 支持的语法因此是"管道串联的白名单命令"这一子集——**重定向、`&&`、`$()`、变量展开一律不支持**。断言里若用了这些，CLI 会拒绝执行并报错，须人改写断言或人工核验。

### 4. 比对：字符串精确比对，两端去空白

两段式比对命令真实输出与断言值；三段式比对真实输出与中段。**两端去空白后精确比对**，不做数值解析——`` `131` `` 与 `` `131 ` `` 视为相同，`` `131` `` 与 `` `0131` `` 视为不同。

**不做数值宽松比对**：那需要判断"这个断言值是不是数字"，而断言值可以是文件名列表、`GONE`、`BUILD_OK` 等任意字符串。**统一按字符串处理，规则单一可预期。**

### 5. 降级：CLI 只做校验，不做闸门

CLI 提供的是一个可运行的校验命令，**不写进任何控制面条款作为节点前置**。

**这直接满足 `SPEC-ENFORCE-003`**——CLI 缺席时流程照常，因为没有任何节点以"CLI 通过"为前置。

**本 step 因此不改控制面任何条款**（判据 005 验的正是这个"没做什么"）。

## 取舍

1. **不经 shell vs 经 shell。** 取前者。代价是语法子集受限（第 3 条），收益是白名单真正生效。**若经 shell，白名单只是装饰**——这一点决定性。

2. **漏检 vs 误报。** 取漏检（第 1 条）。不合形态的断言被静默跳过。代价是覆盖不全，收益是 CLI 可用；形态合规性另有判定者（验证角色，step1 已定）。

3. **`git` 整体放行。** 取宽口，如实记录。收窄到子命令更严但会误伤常用查询。**这是本设计已知最宽的一处，须 R2 知情。**

4. **字符串精确比对 vs 数值宽松比对。** 取前者，规则单一可预期。代价是 `` `131` `` 与 `` `131.0` `` 视为不同——但断言值本就该逐字抄自输出，不同即应报出。
