# Intent.md — 2026-08-28-verify-identity-dispatch

> 本文件是 Intake 节点的实例工件。本节点的前置闸门与产出见 `flow.md`「Intake」节。以上只指向位置，本文件不复述其文字。

## 触发

`docs/review/2026-08-28-spec-flow-intent-audit.md` 报出本项目至今最严重的一处实践偏离：**验证身份独立在 `11` 次中失效 `10` 次，且十次全部通过了验收**。

所有者就此裁定：**恢复条款效力**——验证须由独立子代理承担，而非认可现状去改 AC1。

## 现状

`2026-08-07` MVP spec 的 `SPEC-VERIFY-001` 原文：验证必须由独立于实现者的角色进行；**AC1：同一执行身份既 impl 又 verify → 拒绝**。

`rules.md` §7 已把它落成拒绝条件（"impl 与 verify 的执行身份相同"），**判定者写明"人工验收节点复核身份独立性是否成立"**。

**条款是完整的。缺的是别的东西。**

## Intake 实测：缺的是机制，不是条款

**本节点当场核实控制面是否规定过"验证怎么获得独立身份"**：

| 文件 | 提及派发/子代理的处数 |
| --- | --- |
| `flow.md` | `0` |
| `rules.md` | `0` |

**零。** 控制面从头到尾没有一处说明验证角色**从哪来**。

**十次失效的自承里，有 `4` 次逐字写着"soft 执行器下无派发层"**——执行者每次都读到了 §7 的要求，**每次都找不到履行它的办法，于是如实记录后继续**。

**这解释了为什么十次都"有记录地绕过"**：不是执行者想绕，是条款要求了一件控制面没给出路径的事。

**唯一成立的那次**（`2026-08-19-core-removal/step1`）是靠**流程之外**的 SDD 派发机制做到的——那次实现与验证分别是 SDD 任务 6 与 6b 的两个子代理，**而 SDD 是 `superpowers` 的技能，不是 Themis 控制面的一部分**。

## 收敛主张

**控制面须规定验证角色的获得方式，使 §7 的要求可被履行。**

**须同时处理的一处张力**：`README.md` 明写当前是 soft 执行器、机器强制 `unavailable`。**而"派一个子代理"不是机器强制**——它是执行者可以自己做到的动作，**不依赖任何未实现的 CLI 能力**。

**这一点是本需求成立的关键**：`core-removal` 那次证明了 soft 执行器下身份独立**做得到**。十次失效不是能力不足，**是控制面没写该怎么做**。

## 拟定的 step 分解

**待 R1 确认。** 拟为**一个 step**：

- **在控制面写明验证角色的派发要求与交接内容。** 两者不可分——只说"要派"而不说"交接什么"，派出去的子代理仍验不了。

**本需求不追溯重验既有十次**——那属"不改证据"，且十次的记录本身是完整的。**如何处置既有十次，交 R2 判定。**
