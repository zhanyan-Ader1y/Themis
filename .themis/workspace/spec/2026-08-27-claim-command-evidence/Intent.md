## 问题

**工件里的数字与存在性断言，写下时没人跑命令核对，事后也无人重跑——错了不会被发现。**

这是 `hard-enforcement-list.md` 第 1 项，全清单实发最高频的一类。它与 `rules.md` §1 管的**不是同一件事**：§1 要求 claim 的**来源类型**合规（实现层必须以代码为事实源，不得以文档冒充），但它**不管转录准确性**——命令 2 核实 §1 全节零处提及"转录/准确/重跑/实跑"。一个数字可以来源合规（确实来自某次真实运行的命令）却抄错。

**历史实发（来自 `hard-enforcement-list.md` 第 1 项）**：`docs/` 引用文件数报 36（实为随 grep 模式在 37–47 浮动）；判据命中行数记 14（实为 16）；`.gitignore` 行数写 10（实为 11，而同一文件紧邻处自己粘贴的原始输出就是 11 行）；`CHANGES.md` 的定性引用了一个当前并不存在的目录。

**本轮五次新增实发**（命令 1）：`2026-08-26-authorization-traceability` 实例四处判据缺陷——判据恒真无法证伪、正则区分不了声称与否定式陈述、`awk` 范围在首个空行即终止、判据关键词与条款措辞未对齐；以及 `trace-chain` 终审的 Critical——计数对齐判据在真实数据上放过了一次真实漏引。

**五次全部是同一形态**：写判据时没有实跑，直到落地或终审才暴露。

**这条自带一个必须正面回答的难题。** 该项原文写着：

> **提醒对这个盲区无效，必须是机器强制。**

依据是那次"刚把这条教训写进清单、立刻又犯两次且自查没抓到"。**而本项目没有 `themis` Go CLI**——`cmd/` 下只有 `themico`，`.themis/spec/README.md` 明写机器强制 unavailable。

若照该项原文的结论，本需求**不该现在做**；若要现在做，必须给出一个"不是提醒、也不是机器"的第三条路，否则就是在明知无效的情况下再写一条靠自觉的条款。

## 期望结果

**建一个 `themis` Go CLI，对工件中的数字与存在性断言做机器强制校验：逐条重跑其命令、比对真实输出与写下的断言值，不一致即拒绝。**

三项达成状态：

1. **`themis` CLI 存在且可运行**——提供一个校验入口，读取工件中结构化记录的「命令 + 断言值」对，逐条重跑并精确比对。
2. **工件形态支持机器读取**——`.themis/spec/template.md` 规定数字与存在性断言如何结构化携带其命令与断言值，使 CLI 能定位并重跑。
3. **不一致即拒绝**，且 CLI 缺席时流程不阻塞（`SPEC-ENFORCE-003` 要求自动降级回 soft）。

**三处经追问闭合的决定（`QA.md`）：**

- **取真机器强制，不取写作形态约束**（问 1 答"a"）。该项原文"提醒对这个盲区无效，必须是机器强制"因此得到正面回应，而非绕开。
- **逐条比对输出与断言值，不只检查"是否附了命令"**（问 2 答"逐条比对"）。依据是本项目已有反例：某次执行者在同一文件紧邻处粘贴了原始输出（11 行），结论里却写了 10——**命令在、输出也在，数字仍错**。只检查"附没附"挡不住这一类。
- **全部数字与存在性断言一视同仁**，不按"主张性/辅助性"或小节位置区分（问 3 答"一视同仁"）。依据是 `drift-log.md` 该条末句"区分主张性数字与辅助数字没有意义"——那次错的数字当时就写在叙述里，却直接导致后续判断错误。

**引入 CLI 已过设计约束检**：`docs/design/themis-design.md` 约束 1 规定"只有在不可避免的情况下才引入 Go CLI"，判断标准是"该功能必须由机器执行才成立"。本需求满足——靠条款 + 下游角色核查只能**发现**（已实测有效），不能**拦住**。

## 核心链路

从当前状态（数字与存在性断言可以无命令、无输出地写下，错了不可检出）到目标状态（断言结构化携带其命令与断言值，CLI 逐条重跑比对，不一致即拒绝）。

**本需求是本项目第一次引入机器强制**——此前三个需求都在 soft 执行器下补条款。它同时是 `SPEC-ENFORCE-002`（"当 `themis` Go CLI 可用时，系统必须以 hard 执行器强制同一份 flow 契约"）的第一次兑现，但**只兑现其中一小块**：本需求只做数字与存在性断言的校验，不做整份 flow 契约的强制。

**本需求与前两个的性质差别须先说清**：前两个（授权可追溯、追溯链检出）补的是**控制面没有的条款**；本需求要治的是**条款有了也照样违反的习惯**——`hard-enforcement-list.md` 第 1 项自己就是那个反例：它把教训写成文字之后，同一形态立刻又发生了两次。

**因此本需求的成败判据不同**：不是"条款写没写上"，而是"下一个实例还发不发生"。**引入 CLI 使这一点部分可验证**——CLI 能在本需求内跑通历史实例的已知错值（例如那次 10 vs 11），证明它确实拦得住；但"执行者会不会绕过它"仍只能留待后续实例检验。

## step 分解

**待 R1 确认。** 本需求拆为**两个大步骤**，全部完成才算需求达成：

- **step1 — 断言的结构化形态。** 规定数字与存在性断言在工件中如何携带其命令与断言值，使机器能定位、重跑、比对。**先做这个**：CLI 要读的东西必须先有形态，否则 CLI 无从设计。
- **step2 — `themis` CLI 的校验能力。** 建 `cmd/themis` 与 `internal/themis`，实现逐条重跑比对与不一致即拒绝，并保证 CLI 缺席时降级不阻塞。

**为什么拆两个而非一个**：两者的性质完全不同——step1 是 Markdown 条款改动（与前三个需求同类），step2 是本项目第一次写 Themis 的 Go 代码（有编译、测试、长期维护成本）。**合成一个 step 会让"形态定错"与"代码写错"在同一次验收里纠缠**，而形态一旦定错，代码全部白写。分开则 step1 的验收就是 step2 的输入契约。

**弱依赖方向单一**：step2 依赖 step1 的形态，反向不依赖。
