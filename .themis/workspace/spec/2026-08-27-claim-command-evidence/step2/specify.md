## 行为条目

### SPEC-CLAIMCLI-001

`themis` CLI 必须存在且可构建，入口形态与 `themico` 一致（薄 `main`，逻辑在 `internal/`）。

**验收判据**：

`go build ./...` → `构建通过，无输出`

`test -f cmd/themis/main.go && echo yes` → `yes`

**依据**：`scope.md` 第（1）条——沿用既有惯例使 `Run` 可被测试直接调用，而本 step 需要用已闭合实例作测试数据。

### SPEC-CLAIMCLI-002

CLI 必须能从工件中解析出「断言形态」的两段式与三段式记法。

**验收判据**：

`go test ./internal/themis/... -run TestParse -v | grep -c '^--- PASS'` → `≥2`

至少两条：两段式解析、三段式解析。

### SPEC-CLAIMCLI-003

CLI 必须重跑解析出的命令，并比对真实输出与断言值；不一致时以非零退出码拒绝。

**验收判据**：

`go test ./internal/themis/... -run TestVerify -v | grep -c '^--- PASS'` → `≥2`

至少两条：一致时通过、不一致时拒绝。

**这是本 step 的核心条目**——`Intent.md` 三项达成状态的第三项。

### SPEC-CLAIMCLI-004

CLI 必须只执行白名单内的只读命令，遇白名单外的命令拒绝并报错。

**验收判据**：

`go test ./internal/themis/... -run TestAllowlist -v | grep -c '^--- PASS'` → `≥2`

至少两条：白名单内放行、白名单外拒绝。

**依据**：`scope.md`「安全边界」——所有者裁定取白名单。**这是本项目第一个执行外来命令的产品代码组件**（核实证据见该节）。

### SPEC-CLAIMCLI-005

CLI 缺席或不可用时，流程不得被阻塞。

**验收判据**：

`grep -c 'unavailable' .themis/spec/README.md` → `1`

**语义部分由 R2 判定**：本条不是代码判据——它要求的是"不把 CLI 变成流程的运行前提"。**`SPEC-ENFORCE-003` 已规定该降级**，本 step 只需**不引入与之冲突的东西**：不在任何控制面条款里写"须先通过 CLI 校验才能进入下一节点"。

**本条的验收方式如实说明**：它验的是"没做什么"，而非"做了什么"。命令只能证明既有的 unavailable 声明未被改动；**是否引入了冲突条款须由 R2 逐条读本 step 的产出判定。**

## 本节点标出、须 R2 重点判定的两处

**一、白名单的具体内容未在本文件定死。**

`scope.md` 记的是"`grep`/`wc`/`find`/`ls`/`git log` 这类"，**"这类"不是可判定的边界**。判据 004 只要求"白名单内放行、白名单外拒绝"，不规定名单本身。

**须 R2 判定**：名单在 `design.md` 定是否可接受，还是须在本文件定死。**Agent 倾向前者**——名单是实现细节且会随实际用到的命令增补，写进抽象设计会让每次增补都要重走 R2；但这是判断，交 R2 定。

**二、判据 005 验的是"没做什么"，可证伪性弱于其余四条。**

其余四条都能通过"跑测试看它红"来证伪，005 不能——它的命令在落地前后都输出 `1`。**这是本 step 内已知的一处判据弱点**，本节点如实标出而非掩饰。**处置建议**：把它的判定明确交给 R2 逐条读产出，而非依赖命令。
