### 需要你裁定

**一、程序执行命令时，要不要经过系统的命令解释器（shell）？**

- **起因**：断言里的命令常带管道，例如 `grep -c x file | wc -l`。**若把整串交给 shell 执行，你刚定的白名单就形同虚设**——`grep x | rm -rf y` 这一串的首词是 `grep`，白名单会放行。
- **可选做法**：(a) 不经 shell，程序自己按管道切分、**每段都过白名单**、再串联；(b) 经 shell 执行，白名单只查首词。
- **推荐 (a)，依据**：白名单是你上一轮定的安全边界，**经 shell 执行会让它变成装饰**。这一点是决定性的。
- **判错的后果**：选 (a) 则程序只支持"管道串联的白名单命令"这个子集——**重定向、`&&`、`$()`、变量展开一律不支持**，断言里用了这些就得改写或人工核验；选 (b) 则白名单失效，一个写错或被篡改的断言可以让程序执行任意命令。

**二、`git` 整体放行，还是收窄到具体子命令？**

- **起因**：断言里常用 `git log`、`git diff`、`git rev-parse`，都是只读。**但 `git` 也能改仓库**（`git reset`、`git push`）。
- **可选做法**：(a) `git` 整体放行；(b) 只放行 `git log`/`diff`/`show` 等具体子命令。
- **推荐 (a)，但这是本设计已知最宽的一处，须你知情**：收窄更严，但会误伤 `git rev-parse` 这类常用查询——而每次补一个子命令都要改代码。
- **判错的后果**：选 (a) 则一条写着 `git reset --hard` 的断言会被执行；选 (b) 则常用查询可能被拒，执行者有动机绕过程序。

**三、程序遇到"没按新写法写"的断言，是跳过还是报错？**

- **起因**：工件里绝大多数行不是断言。**若要求每行都合形态，程序会对所有散文报错，不可用。**
- **可选做法**：(a) 静默跳过不合形态的行；(b) 报错。
- **推荐 (a)，依据**：(b) 不可用。
- **判错的后果**：选 (a) 意味着**"没按写法写"的断言逃过校验**——程序只管合形态的那些，形态合不合规仍由人判（上一步已定）。这是程序的**漏检**边界，不是它的缺陷。

1. **不经 shell 执行**——程序自行按管道切分，**每段都过白名单**，再串联。依据：经 shell 会让白名单变成装饰。**代价**：只支持"管道串联的白名单命令"子集，重定向、`&&`、`197609)`、变量展开一律不支持；断言里用了这些则 CLI 拒绝执行并报错，须人改写或人工核验。
