该缺陷属 `2026-08-28-citation-overlap-check` 交付的工具，不在报出它的那个 step 范围内。**所有者裁定先修工具，再做清单第 4 项。**

## 现状

`themis verify` 把命令按 `|` 切分成管道段，逐段过白名单后分别执行。**切分时不区分 `|` 出现在什么语境**：

| 语境 | 含义 | 工具怎么处理 |
| --- | --- | --- |
| 真管道 `a \| b` | 管道 | **正确** |
| Markdown 表格里的 `\|` | 表格转义，实为管道 | **按字面两字符处理，命令跑不通** |
| grep 正则的 `'a\|b'` | 或，不是管道 | **从模式中间切断命令** |

## 两个侧面的危险性不同，须分别记

**第一个侧面（表格转义）症状明显**：命令跑不通，报"白名单外"或"执行失败"。**极端情形会挂起**——`gate-value-integrity` 的 verify 首次触发：`grep -rl '…' <路径> \| wc -l` 中 `\|` 未被识别，`wc -l` 从不启动，而 `grep -r` 转为读标准输入，**一直等到超时**。

**第二个侧面（正则的或）无症状**：命令**照常返回一个数，只是数错了**。同一条 `grep -c '非授权答复\|未表态'`，bash 里得 `1`，经工具得 `0`。

**后者更危险**：**若判据恰好写成 `→ 0`，它会静默通过**——工具不但没抓到错，还给出了"通过"。

## 收敛主张

**`themis verify` 的命令切分须按语境判定 `\|`，而非一律按字面或一律按管道。**

三种语境的判定依据在工具可见的信息里：

- **表格行**：整行以 `|` 开头——**Markdown 表格的行首标志**。
- **正则内**：`\|` 出现在引号包裹的模式内部。
- **真管道**：其余情形。

## step 定界前的复核推翻了本文的核心诊断，如实记明

**本节点在写完上文后，按主张"先把依据读全"去逐层复现该缺陷，结果推翻了它。**

逐层实测（每层都跑了命令，不靠推断）：

| 层 | 结果 |
| --- | --- |
| `splitPipeline` 切分 | **正确**——引号内的 `\|` 未被当作管道边界 |
| `splitStage` 分词 | **正确**——argv 为 `["grep" "-c" "非授权答复\|未表态.*写成"]`，与 bash 传的一致 |
| 单支模式经 `runPipeline` | **正确**，得 `1` |
| 含 `\|` 但无 `*` 的两支 | **正确**，得 `1` |
| 含 `\|` 且分支内有 `*` | **得 `0`，bash 得 `1`** |
| **绕开本包、直接 `exec.Command` 传同样 argv** | **同样得 `0`** |

**最后一行是决定性的**：**本包的分词与切分都没问题**，同样的 argv 交给 Go 的 `os/exec` 直接执行也是 `0`。

**真正的原因**：Go 在 Windows 上把 argv 重新拼成命令行字符串交给进程，而 Git for Windows 的 `grep` 会**自行重解析该命令行**——`\|` 与 `*` 同时出现时被改写。**这与 `2026-08-27-claim-command-evidence` 记过的现象同源**（那次是 Windows `grep` 自行重解析引号，掩盖了本包分词的一处真缺陷）。

**因此本需求的前提不成立**：

- **"grep 正则的或会被从模式中间切断"——不成立。** `splitPipeline` 早已引号感知。
- **"表格转义会使命令挂起"——成立，但成因是 `\` 残留在段尾**，不是三义混淆。
- **本文所列的三种语境，工具其实只错认一种（表格转义），而非两种。**

**本节点已发现的这一事实使收敛主张需要重写**，`Intent.md` 的变更会使 R1 结论 stale（`flow.md` R1 节失效级联）。**本节点不自行改写已批准的意图**，交所有者决定：是修订本需求，还是就此退回。
