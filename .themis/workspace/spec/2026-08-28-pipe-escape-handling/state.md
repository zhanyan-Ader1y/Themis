## 本实例已确证的缺陷面

**由第 2 版 Intake 当场实测，探针经 Write 工具落盘、不经 shell 转义。**

| 类别 | 例 | 表现 |
| --- | --- | --- |
| 静默错值 | `x\?y`、`S\|P.*节`、`\(SPEC\)`、`S\{1\}PEC` | 照常返回一个数，只是数错了，**无任何信号** |
| 误拒 | `SPEC\>` | `\>` 是 grep 词尾锚，被 `verify.go` 第 `144` 行按子串判成重定向 |
| 正确 | `SPEC`、`\<SPEC`、`a\+b` | — |

**静默错值的危险性有一处直接坐实**：`\(SPEC\).*节` 的 bash 真值恰为 `0`、工具也返回 `0`，**两者一致，无从分辨工具是算对了还是坏了**。

**判别实验**：同一元字符写成 ERE（不带反斜杠）能正确通过，写成 BRE（带反斜杠）则坏；**但花括号两种写法都坏**。据此可断定问题与反斜杠及花括号有关，**机制本身未确证，属详细设计**。

## 本实例已犯过的同型错误，记明以防再犯

**该缺陷的诊断已错过三次，全部错在同一处——探针里的反斜杠被 shell 吃掉。**

1. 对话中说「`432` 处」——错。
2. 对话中改口「`3394` 处」——仍错。两次错因都是搜索模式里写了 `\|` 而 `grep` 当成正则的或。
3. 第 1 版断定"正则的或会被从模式中间切断"——错，`splitPipeline` 早已引号感知。

**第 2 版核查期间的第四次未遂**：一度据探针输出断定"分词器吃反斜杠"，**核字节后发现是 `printf` 把探针文件本身写坏了**，`splitWords` 逐字保留引号内容。**若不核字节即发布，这将是第四次误诊。**

**由此定下本实例的探针纪律**：**探针文件一律经 Write 工具落盘，不经 shell**；期望值取自变量展开的 bash 直跑，**不写进 `printf` 格式串**；**发布任何诊断前先 `cat -A` 核探针字节**。
