## 给评审者的呈现

### 这一步要做什么

把 Themis 的流程规则文件从"包源 + 副本"两份改成一份，然后删掉那个已经没用的旧目录。

现在 `templates/.themis/` 里装着两套东西：一套是**正在用的流程规则**（四份文件，也就是本次评审所依据的那套规则本身），另一套是**一个已废弃体系留下的空架子**。正在用的那套有个麻烦——它在仓库里存了两份，改一处必须记得手工同步另一处，本次会话每次改规则都要这么做一遍。这一步把它合并成一份，顺便把废弃的那套删掉。

### 需要你裁定

**一份文档里有一节描述的正是本次要取消的机制，具体是删掉整节还是改写，能不能等动手时再定？**

那一节在仓库根 `AGENTS.md` 第 48–52 行，标题是「安装包与项目工作区的边界」，内容是"`templates/` 下是安装包源"、"安装动作由 Themis Go CLI 承担，能力尚未实现"——描述的就是本次要取消的两份制。

- **起因**：规则要求所有结构决定在动手前定死，实现期不得临时决定，否则应停下回退。这一处我没定死。
- **两种选择**：允许推迟，动手时看实际文本定夺并记录理由；或者不允许，现在退回去先定死做法。
- **后果差别**：这一节无论删还是改，都不引入任何新结构，也不影响任何一条验收判据（判据只要求"不残留指向已删内容的引用"）。所以我认为可以推迟——**但这是规则的边界，该由你判，不该我自己放行**。

### 改变了原定方向的发现

**我推翻了自己在设计稿里写的任务分类，因为它不符合规则。**

- **原本打算**：把"改配置文件"和"把规则文件纳入版本管理"这两步归为**准备工作**，其余归为正式改动。理由是它们必须先做。
- **核实到**：规则要求准备工作**同时**满足两条——被其他任务依赖，**并且**自己不产生外部可见的改动。这两步满足第一条，但不满足第二条：它们都当场改变仓库里看得见的东西，而且验收判据里就有两条直接盯着它们看。规则明确写着"只满足一条就归为准备工作"是错的。
- **现在改成**：没有准备工作，全部是正式改动；执行次序改由任务之间的依赖声明保证。
- **若判错的后果**：这一步会带着一个不成立的分类进入实现阶段，实现完了才会在验证时发现分错。

**教训**：先后次序很容易被误当成"准备工作 vs 正式工作"的关系，但规则里那两条是并列的，不是满足其一即可。

### 其余要点

**执行次序有一处不能颠倒。** 必须先解除对规则文件的版本管理排除、把它纳入版本管理，然后才能删旧目录。反过来做的话，中间会有一段时间**仓库里根本没有这套流程规则**——工作区那份是被排除在版本管理外的，删掉包源就等于它不存在了，别人克隆下来拿不到。

**你上次批准的一处越界，落在一个具体任务上。** 另一个模块（Themico，一个有真实 Go 实现的知识库工具）的说明文档里有一行写着它的入口文件放在本次要删的目录下。不改，那行就指向不存在的路径。你已批准改这一行，范围仅限这一行。

### 我知道但还没解决的

**有三份文件的迁移，没有任何验收判据能检查它做对了没有。**

这三份是：Themis 的公共入口文件、Themico 的公共入口文件、以及一份规定"控制面该怎么写"的规范。你上次裁定不为它们补判据。

**后果**：验证环节无法判定它们是否迁到了正确位置、内容是否逐字保留。验证工件里会写明"这部分不在断言范围内"，**不会把它们判为通过**。它们的正确性最终只能由你在验收时看交付视图来把关。

**这份规范值得单说**：它有三节，每一节都是这次流程走查里付过代价才总结出来的教训——"引用只指向不复述"（同类问题实际发生 7 次）、"判据必须有判定者"（4 次）、"失败去向必须覆盖前置闸门的每个分支"（正是这次卡住流程、需要临时裁定才解开的那处矛盾的成因）。我最初判它可以直接删，理由是"这些约束已经写在别处了"——跑命令核实后发现**别处根本没有**，才改成迁移保留。

## 分类核查

`rules.md` §4 规定本节点是分类判定者。逐条核查如下。

### 1. basic 段为空，判定成立

§4 要求 basic 任务**同时**满足两条：被本 step 其他任务依赖，且单独不产生外部可观测行为。`task/basic.md` 逐个候选列出了判定，六个候选**无一同时满足**——每一个都直接改变仓库可观测状态，且五条判据中有四条正是直接观测这些改动（001/002/003/004 各锚定一组具体文件）。

**核查结论：空段成立。** 本 step 没有内部结构层（无 schema、无接口契约），不存在"暂时观测不到、等下游补齐才可见"的任务。

### 2. 任务作者推翻了 `design.md` 的分类建议——本节点确认该推翻正确

`design.md`「结构决策」第 1 条建议"改忽略规则+入库放 basic 段、删包源放 detail 段"。`task/basic.md` 拒绝了该建议，理由是：该建议**只考虑了次序，未逐条核对 §4 的第二条判据**；T-D1 与 T-D2 都产生当场可观测的改动（判据 002、003 直接观测），只满足"被依赖"一条。

**§4 明列的拒绝条件之一正是"只满足一条即归入 basic"。** 若按 `design.md` 的建议分类，本 step 会以一个不成立的 basic 段进入 R3。

**核查结论：推翻正确，采纳 `task/basic.md` 的判定。** 这一处值得单记——**次序依赖极易被误读成 basic/detail 关系**，而 §4 的两条判据是并列的，不是"满足其一即可"。次序改由 detail 段内部的依赖声明承担，§4 末段正为此写明不因层次增设第三段。

### 3. 无孤儿（§8）

basic 段 `### T-B` 条目数为 0，六条 detail 任务的依赖项均指向其他 detail 任务，无一指向 basic 任务。**无可判的孤儿。**

verify/detail 节点仍须自行数出该条目数，不得仅凭本行或 `task/basic.md` 的自述判空（§8 拒绝条件）。

### 4. 任务未替 `design.md` 引入新的结构决策（§6）

逐条核对六条任务的"出处"栏：T-D1/T-D2 出自「结构决策」第 1 条，T-D3 出自第 2 条，T-D4 出自「架构与边界」，T-D5 出自第 4 条，T-D6 出自第 3 条。**六条全部可回溯到 `design.md` 已有决定，无一条自创结构。**

**一处例外须标出**：T-D5 中 `AGENTS.md:48-52` 整节的具体做法（删除还是改写）**未在 `design.md` 定死**，任务文件写的是"具体做法在落地时依实际文本定，并在 impl 工件中如实记录所选做法"。这是把一个结构决定推迟到了实现期——**§6 的口径下，实现期定结构本该停下回退**。

本节点的处理：该节内容描述的是本 step 正在取消的两层模型，删除与改写的差别不影响任何判据（004 只要求不含指向已删内容的活引用），**且两种做法都不引入新结构**。故**允许其推迟**，但要求 impl 节点如实记录所选做法与理由。**此项须由 R3 评审者确认**——见「未解决反馈」第 1 条。

T-D3 迁移的三份文件**无任何判据覆盖**（R2 裁定 B 定为不补 SPEC-WSCLEAN-006）。本节点不改变该裁定，只如实标出其在任务层的后果：
