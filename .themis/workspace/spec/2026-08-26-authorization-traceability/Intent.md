# Intent.md — 2026-08-26-authorization-traceability

> 状态：追问第 1 轮四问全部获所有者答复并闭合（`QA.md`），无悬而未答项。Agent 依 `rules.md` §2 提出收敛主张——**确认权归 R1 评审者**，R1 批准前本文件仍为待评审状态。

## 问题

**流程唯一的授权点可以被 Agent 推断出来，而推断出的授权在工件文本上与真授权无法区分。**

`flow.md` 规定人工验收是整条流程唯一的授权点，评审闸门（R1/R2/R3）是仅有的放行判定。这些判定的记录形态是：工件的「结论」小节写 approved/accepted，「用户原话」小节写评审者原话。**两个小节都由执行体（Agent）写入**——控制面没有任何条款要求它们的内容必须来自评审者的真实答复。

后果：若执行体从一句不构成授权的话里"推断补足"出一个结论，产出的工件与真授权完全同形。事后无论谁读，都读不出那一步是补的。

**这不是假设，已实发五次**（来源见"来源引用"）：

- **两次在 `2026-08-19-core-removal` 实例**（replay 走查）：一次是把 Agent 自己的推论包装成 R2 评审者的要求——引用格式完全合规（"R2 批复第 2 条"），只是批复原话里根本没有那个章节名；一次是人工验收，所有者首条答复是单字母 `a`，只回了残留项选项、不含验收结论，而 `a` 恰好也能读成"同意"。
- **三次在 `2026-08-26-workspace-cleanup` 实例**：R2、R3、人工验收各一次，形态均为评审者给了结论未给并列的裁定项，或给了裁定项未给结论。

**五次全部由执行体自觉按住，未产生实际越权。** 但自觉不构成保障：五次中任何一次改为推断补足，本项目至今无人能从工件中发现。

**一处必须辨明的事实**：本项目**没有 `themis` Go CLI**（命令 1：`cmd/` 下只有 `themico`）。`.themis/spec/README.md`「当前强制水平」明写机器强制 unavailable、闸门靠 Agent 遵守。**因此本需求不可能实现"机器写入原话、执行体不可写"那一层**——那需要一个不存在的机器。

## 期望结果

**目标：使推断补足的授权从"不可检出"变为"可被发现"。** 所有者认可该强度（`QA.md` 问 4 答"认可"）——不追求 soft 执行器下不可能达到的"阻止"。

达成状态三项：

1. **`.themis/spec/` 控制面规定人工闸门结论的合法取值与来源要求**，且该规定**带判定者与判定时机**——判定者取"下一次引用该结论的角色"（`QA.md` 问 2 答）。
2. **`.themis/skills/spec-review-presentation/` 规定授权与附带裁定必须分开提问**，一次只问一个待决项（`QA.md` 问 3 答"纳入"）。
3. 上述两项均**不声称任何机器强制**。

**只做第三层**（`QA.md` 问 1 答）。前两层需要本项目不存在的 `themis` CLI，不在本需求范围；将来 CLI 可用时另行处理。

| 层 | 做法 | 本需求 |
| --- | --- | --- |
| 1 | 机器从答复通道原样落盘原话，执行体不可写入 | 不做（需 CLI） |
| 2 | 每处"所有者要求 X"携带定位，机器子串比对，追溯不到即拦 | 不做（需 CLI） |
| 3 | 闸门只接受受限取值；结论为空即未授权，不得推断补足 | **做** |

**两处知情接受的代价，须在设计中如实标出：**

- **第三层只覆盖五次实发中的四次。** "伪造引用"那一类不被覆盖——`2026-08-19-core-removal` 那次把 Agent 推论包装成"R2 批复第 2 条"，引用格式完全合规，只有逐字比对原话才能发现，而逐字比对需要第 2 层。
- **判定者有固有弱点：若无人引用，该判定永不发生。** 这与 `rules.md` §9 对链尾工件的兜底同型（"下一次被引用时由引用方复核"），弱点也同型。设计节点须处理这一点，不得回避。

## 核心链路

从当前状态（人工闸门的结论与原话两个小节由执行体自由写入，无任何来源约束）到目标状态（在不谎称机器强制的前提下，使"推断补足的授权"成为一种**可被下游发现**的越权，而不是不可检出）。

**本需求的性质须先说清**：它**不可能在 soft 执行器下真正阻止**推断补足——没有机器就没有拦截点。它能做到的是**改变失效形态**：从"不可检出"变为"可被发现"。具体机制待设计节点确定，但方向是让推断补足在工件上留下与真授权不同的痕迹。

**一条必须遵守的红线**：`docs/plan/README.md`「通用限制」明写"不得用 Prompt、README、template、policy 或 directory 的存在冒充 machine enforcement"。本需求若把第三层写成条款，**必须同时写明它由谁判、在何时判**——否则就是又一条没有判定者的判据，正是 `.themis/AGENTS.md`「判据必须有判定者」所禁止的形态。

## 范围与非做

**范围**：

- `.themis/spec/` 控制面中与人工闸门结论、用户原话相关的条款（判据层）。
- `.themis/skills/spec-review-presentation/`——授权与附带裁定的提问方式（呈现层，`QA.md` 问 3 答"纳入"）。

**非做**：

- **不实现 `themis` Go CLI**，也不为其预留接口或占位。CLI 是独立的大需求。
- **不声称任何机器强制**。本需求产出的一切都在 soft 执行器下由人与 Agent 遵守。
- 不改 `mvp.md` §2 已批准的行为契约条目。若本需求需要契约变更，须单独提出并经批准，不在本 spec 内擅自改动。
- 不动 `templates/.themico/` 与 Go 代码。
- 不改写 `docs/` 下任何历史记录，含五次实发的原始记载。

## 约束

- 遵循 `.themis/spec/` 控制面走完本 spec。
- 新增或修改的任何判据**必须带判定者与判定时机**（`.themis/AGENTS.md`「判据必须有判定者」）。
- 不引入版本概念、不建 compatibility/migration 路径。
- 本需求自身走流程时同样受它所要修的问题影响——**本 spec 的每一次评审与验收，都是该问题的又一次实测机会**，须如实记录。

## step 分解

**待 R1 确认。** 本需求拆为**一个大步骤**，全部完成才算需求达成：

- **step1 — 判据层与呈现层一并落地。** 承担全部三项达成状态：控制面规定人工闸门结论的合法取值、来源要求与判定者；呈现层规定授权与附带裁定分开提问。

**不拆成两个 step**：两层治的是同一个问题的两端——判据层管"结论怎么写才算数"，呈现层管"怎么问才不会逼出推断"。拆开会让其中一端先落地而另一端悬空，而单独任一端都不足以改变失效形态：只补判据不改提问，仍会系统性产出只答一半的回复；只改提问不补判据，答全了也仍无来源约束。
