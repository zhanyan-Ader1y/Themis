**不做**：`Intent.md`「范围与非做」所列各项，本文件不重复。

### 本节点核实到的三处事实，影响做法边界

**（1）`rules.md` 现为 103 行、十节，新增一节不触发拆分。**

`.themis/spec/README.md`「rules.md 拆分退出条件」列三条阈值：单节超全文三分之一、连续三次只改同一节、全文超 300 行。**当前 103 行，新增一节后仍远低于阈值**，因此本 step 不需要处理拆分问题。

**（2）人工闸门的结论取值已经是受限的——但受限的是取值，不是来源。**

`flow.md` 通用状态条款已规定：人工评审取 `approved`/`驳回`，人工验收取 `accepted`/`退回`。**强制清单第 3 项所说的"只接受受限取值"这一半已经存在。**

缺的是另一半：**没有任何条款规定这些取值必须来自评审者的真实答复**。执行体照样可以在评审者未表态时写下 `approved`——取值合法，来源无约束。

**这一发现收窄了本 step 的做法**：不需要重新定义取值，只需补来源要求与判定者。

**（3）四份人工闸门工件中，只有一份有「用户原话」小节。**

`template.md` 的小节划分表：

| 工件 | 有「用户原话」? |
| --- | --- |
| `acceptance.md`（人工验收） | **有** |
| `intent-review.md`（R1） | 无 |
| `design-review.md`（R2） | 无 |
| `task/review.md`（R3） | 无 |

**三个评审工件在结构上根本没有记录逐字原话的位置。** 本项目此前三次评审的原话都是执行体自行加在「结论」小节里的——那是实例的自发做法，控制面未要求、也未禁止。

**这是本 step 必须处理的一处结构不对称**：若来源要求只写"结论必须能追溯到原话"，而三份工件没有原话的落点，该要求在那三处无法执行。**具体处置由 R2 决定**，本节点只标出，不预判。
