### 需要你裁定

**一处：我往任务里加了一项设计稿没写的义务，需要你确认接受。**

- **起因**：其中一条任务要改的是那份"怎么向你提问"的呈现规范。**那份规范是经过完整测试的**——先证明不给规范时 Agent 确实会写砸、再证明给了规范就不会，测试记录逐条写明了每条规则是怎么验出来的。而**本次要新增的内容没经过同样测试**。
- **两种做法**：(a) 任务里要求同步更新测试记录——要么补测，要么如实标注"这节未经测试"；(b) 不加这项义务，新增内容直接写进去。
- **判错的后果**：选 (b) 的话，未测内容与已测内容在同一份文件里混同，后来者读测试记录会以为整份规范都验证过。**那是事实性误导**，而且这份规范恰恰是本需求用来减少"答一半"的工具——它自己的可靠性被误报，影响会传导。
- **我选了 (a) 并写进任务**，但它是任务层新增、不是上轮批准的设计内容，所以交你确认。

**无。** 四条任务全部可回溯到上一轮已批准的设计，没有引入任何新决定（上面那一项是义务而非结构决定，见「分类核查」第 2 条）。

> 批准

**录入说明——本条须完整读，它记录的是一次判断而非一次转述**：

本次投影**有一个与结论并列的裁定项**（「需要你裁定」一节列出，非"无"）。首次答复"批准"未单独就该项表态，Agent 据 `hard-enforcement-list.md` 第 3 项发起追问；**所有者明确拒绝追问并重复"批准"**。

Agent 据此把该答复读作：**批准 R3 结论，并接受该裁定项的 (a) 方案**（即投影中标注"我选了 (a) 并写进任务"的那一项）。

**这一读法的依据**：所有者在被明确告知"存在一个待裁定项、它有 (a)/(b) 两种做法、我选了 (a) 写进任务"之后，拒绝就该项另行表态并重申批准。在该语境下，"批准"覆盖投影所呈现的全部内容——包括其中已声明的选择。

**这一读法的性质须如实标出**：它**不是**评审者对该裁定项的逐字表态，而是 Agent 对一次拒绝追问行为的解释。**与本 spec 要修的"推断补足"存在形式上的相似**，两者的差别在于：

- 推断补足是**在评审者未被告知该项存在时**，替他补出一个未表达的结论；
- 本次是**评审者已被明确告知该项、并主动拒绝就其另行表态**后，按投影全文范围理解其批准。

**但这个差别不能自证。** 本条如实记录经过（含追问被拒这一事实），使下一次引用该结论的角色能自行判断该读法是否成立——**这正是本 step 正在建立的机制在其自身评审上的第一次实际适用**。若引用者认为该读法不成立，应回到评审者处澄清，而非采信本记录。
