# specify.md — authorization-traceability / step1

> 本文件是抽象设计（specify）节点的实例工件。本节点的前置闸门与产出见 `flow.md`「抽象设计（specify）」节；EARS 句式要求见该节所引 `SPEC-EARS-001`，`[basic]` 标识见 `rules.md` §5。以上各处只指向位置，本文件不复述其文字。
>
> **本 step 的判据有一处与前两个实例不同，须先说明。** 前两个实例改的是文件与目录，判据可写成"存在性/计数"这类命令直接判定的形态。本 step 改的是**条款语义**——"这条规则是否有判定者"、"这条规则是否声称了机器强制"，这类判断命令给不出答案。
>
> **处置**：每条判据拆成两部分——**可命令判定的结构部分**（条款存在、字段齐备、关键短语在位）由命令判；**语义部分**由指定角色判，并写明判定者。**不把语义判断伪装成命令判定**，那是本项目已记过的一类漂移（`hard-enforcement-list.md` 第 1 项防的是反向：把该跑命令的写成人判）。

## 行为条目

### SPEC-AUTHTRACE-001

`rules.md` 必须存在一节，规定人工闸门结论的**来源要求**：结论必须能追溯到评审者的逐字答复，评审者未就该结论表态时不得写入任何取值。

**验收判据**：

```bash
grep -c '^## §11' .themis/spec/rules.md
awk '/^## §11/,0' .themis/spec/rules.md | grep -cE '适用节点|判据|拒绝条件|判定者'
```

通过条件：第一条输出 `1`；第二条输出 `4`——四个固定字段齐备。

**范围写法的一处订正（落地时实测发现）**：本条初稿的第二条命令写作 `awk '/^## §11/,/^## §12|^$/'`，实跑输出 `0`。诊断（命令 D2）显示该范围**在标题后第一个空行即终止**，只取到标题行本身，四个字段一个也没取到——**§11 的内容是完整的，缺陷在命令**。因 §11 是文件末节，改用 `awk '/^## §11/,0'` 取到文件末。SPEC-AUTHTRACE-005 的对应命令同此订正。

**这是本 step 第三处判据缺陷**（前两处在抽象设计节点自查时改正：一处恒真无法证伪、一处正则区分不了声称与否定式陈述）。三处的共同点：**判据写下时未实跑，直到落地才暴露**——正是 `hard-enforcement-list.md` 第 1 项所记形态。本节点当场订正并如实记录，不掩饰。

**语义部分由 R2 评审者判定**：该节的「判据」是否真的表达了"结论须可追溯到逐字答复"，而非泛泛的"应当准确"。**命令只能证明四个字段在位，不能证明它们写对了。**

### SPEC-AUTHTRACE-002

该节的**判定者字段**必须指名"下一次引用该结论的角色"，且必须写明该判定在**何时**发生。

**验收判据**：

```bash
awk '/^## §11/,/^## §12|^$/' .themis/spec/rules.md | grep -c '判定者'
awk '/^## §11/,/^## §12|^$/' .themis/spec/rules.md | grep -cE '引用'
```

通过条件：两条均 ≥ `1`。

**语义部分由 R2 评审者判定**：判定者是否具体到可执行——`.themis/AGENTS.md`「判据必须有判定者」要求"判定者必须对每个适用节点都有真实存在、有权做该判定的角色，且该角色能在判定时刻拿到判定所需的证据"。**"下一次引用者"是否满足这一条，是本 step 最需要评审者盯的一处**（见「来源覆盖」末段）。

### SPEC-AUTHTRACE-003

三份评审工件（`intent-review.md`、`design-review.md`、`task/review.md`）必须有记录评审者逐字答复的落点。

**验收判据**：

```bash
grep -cE '^\| `(intent-review|design-review|task/review)\.md`' .themis/spec/template.md
grep -E '^\| `(intent-review|design-review|task/review)\.md`' .themis/spec/template.md | grep -c '原话'
```

通过条件：第一条 `3`；第二条 `3`——三份工件的小节划分中均含原话落点。

**为什么需要这条**：`scope.md` 核实到当前只有 `acceptance.md` 有「用户原话」小节，三份评审工件没有。若 001 的来源要求落地而此处不补，该要求在三个评审节点无法执行——**判据要求追溯到原话，而工件里没有放原话的地方**。

### SPEC-AUTHTRACE-004

`spec-review-presentation` 必须规定：授权与附带裁定分开提问，一次只问一个待决项。

**验收判据**：

```bash
awk '/^## 需要你裁定/,/^## 改变了原定方向/' .themis/skills/spec-review-presentation/SKILL.md | grep -c '独立成条'
awk '/^## 需要你裁定/,/^## 改变了原定方向/' .themis/skills/spec-review-presentation/SKILL.md | grep -cE '批准本身'
```

通过条件：两条均 ≥ `1`。

**关键词的一处订正（落地时实测发现）**：本条初稿的命令 grep 的是 `授权.*裁定` 与 `一次只问`，落地后实跑均输出 `0`。逐字读产出后确认——**条款写对了，是判据的关键词猜错了**：配方实际用词是"每个待决项独立成条"与"批准本身是其中一条"，而 `一次只问` 是本节点在写判据时对措辞的**预先猜测**，写判据在前、写条款在后，两者未对齐。

**为什么改判据而不是改条款**：条款的用词是该 Skill 的既有词汇（「需要你裁定」一节本就用"待决项"），改成 `一次只问` 反而与该节其余部分不协调。**判据要测的是语义（每项独立、批准不隐含），不是特定字串**——把命令锚到实际写下的短语上，语义不变。

**这是本 step 第四处判据缺陷**，且是新形态：前三处是判据本身写错（恒真、正则不可行、awk 范围错），**本处是判据与条款各自正确但互不对齐**。共同根因仍是判据写下时未实跑。

**语义部分由 R2 评审者判定**：该规定的**形态**是否与该 Skill 已验证的形态一致。该 Skill 的 `testing-notes.md` 记明其失败类型是"输出形状失败"，须用正面配方而非禁令——**新增内容若写成"不得合并提问"这类禁令，与该 Skill 已测过的形态相悖**，应写成配方（说清提问该是什么形状）。

### SPEC-AUTHTRACE-005

本 step 的产出**不得声称任何机器强制**。

**验收判据**：

```bash
awk '/^## §11/,/^## §12|^$/' .themis/spec/rules.md | grep -cE '机器|自动|CLI|校验器|拦截'
grep -c 'unavailable' .themis/spec/README.md
```

通过条件：第一条输出 `0`——新增节不含任何暗示机器执行的措辞；第二条 ≥ `1`——`README.md`「当前强制水平」的 unavailable 声明未被改动。

**这条是红线的可执行形态**：`docs/plan/README.md`「通用限制」明写不得用 Prompt/README/template/policy 的存在冒充 machine enforcement。

**本节点自查发现的一处判据缺陷，如实标出而非掩饰**：第一条命令**在落地前后都输出 `0`**——落地前 §11 根本不存在，`awk` 取不到内容，自然为 0。**它因此无法证伪：无论做没做对，都是 0。**

这与本项目已记过的形态同族——`hard-enforcement-list.md` 第 1 项要求判据必须能真判失败，而恒真的判据等于没有判据。

**修正**：第一条改为**先证存在、再证不含**的两步，把"§11 不存在"与"§11 存在且干净"区分开：

```bash
grep -c '^## §11' .themis/spec/rules.md
awk '/^## §11/,/^## §12|^$/' .themis/spec/rules.md | grep -cE '机器强制|自动拦截|由 CLI|校验器'
```

通过条件：第一条 `1`（§11 存在——落地前为 `0`，可证伪）；第二条 `0`。

**第二条的性质须改判——它不能是纯命令判据。** 本节点起初把关键词从 `机器|自动|CLI` 收窄为 `机器强制|自动拦截|由 CLI|校验器`，以为可避开误伤；**实跑证伪**：字符串 `本条不由机器强制` 仍命中 `机器强制`（命令 S3）。

**根因**：区分"声称机器强制"与"声明不由机器强制"是**语义判断**，正则做不到——`grep` 无后顾断言（命令 S3 实测），而穷举否定前缀（不由/不含/未/非/无）只会催生新的绕过写法。

**因此第二条改为「命令给候选、人判定」的两步形态**，并写明判定者：

```bash
awk '/^## §11/,/^## §12|^$/' .themis/spec/rules.md | grep -nE '机器|自动|CLI|校验|拦截'
```

命令**只负责列出全部候选命中行，不给通过/不通过**。**判定者：R2 评审者**，逐行读出每处命中是"声称机器执行"还是"声明不由机器执行"——**前者违规、后者正是应写的内容**。

**这一改动本身是本 step 主题的一次实例**：把语义判断伪装成命令判定，与把人类授权伪装成机器结论同型——**都是让一个实际由人做的判断，在文本上看起来像是机器做的**。本节点当场撞见并改正，如实记录。

**两项修正均在本节点当场完成，未留给下游。**

## 本节点标出、须 R2 重点判定的一处

**判定者"下一次引用该结论的角色"是否成立，是本 step 的最大不确定点。**

`.themis/AGENTS.md` 对判定者有三条要求：真实存在、有权做该判定、**能在判定时刻拿到判定所需的证据**。前两条"下一次引用者"满足；**第三条存疑**——引用者拿到的是工件文本，而"结论是否由推断补足而来"这件事，恰恰在工件文本上与真授权同形（这正是本需求的问题陈述）。

**若引用者只能读到同样的文本，他凭什么判？** 设计节点必须回答这一点，否则新增的这一节就是又一条没有实际判定者的判据——**正是 `.themis/AGENTS.md` 明令禁止、且 `hard-enforcement-list.md` 第 7 项记过四次的那种形态**。

本节点不预判答案，但明确标出：**这一条不解决，001 与 002 都是空的。**
