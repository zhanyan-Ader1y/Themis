# Intent.md — authorization-traceability

> 状态：Intake 已产出来源引用初始条目。**追问尚未开始**，本文件含三处明确标注的待确认项，未主张收敛（判据与判定者见 `rules.md` §2——确认权归 R1 评审者）。

## 问题

**流程唯一的授权点可以被 Agent 推断出来，而推断出的授权在工件文本上与真授权无法区分。**

`flow.md` 规定人工验收是整条流程唯一的授权点，评审闸门（R1/R2/R3）是仅有的放行判定。这些判定的记录形态是：工件的「结论」小节写 approved/accepted，「用户原话」小节写评审者原话。**两个小节都由执行体（Agent）写入**——控制面没有任何条款要求它们的内容必须来自评审者的真实答复。

后果：若执行体从一句不构成授权的话里"推断补足"出一个结论，产出的工件与真授权完全同形。事后无论谁读，都读不出那一步是补的。

**这不是假设，已实发五次**（来源见"来源引用"）：

- **两次在 `core-removal` 实例**（replay 走查）：一次是把 Agent 自己的推论包装成 R2 评审者的要求——引用格式完全合规（"R2 批复第 2 条"），只是批复原话里根本没有那个章节名；一次是人工验收，所有者首条答复是单字母 `a`，只回了残留项选项、不含验收结论，而 `a` 恰好也能读成"同意"。
- **三次在 `workspace-cleanup` 实例**：R2、R3、人工验收各一次，形态均为评审者给了结论未给并列的裁定项，或给了裁定项未给结论。

**五次全部由执行体自觉按住，未产生实际越权。** 但自觉不构成保障：五次中任何一次改为推断补足，本项目至今无人能从工件中发现。

**一处必须辨明的事实**：本项目**没有 `themis` Go CLI**（命令 1：`cmd/` 下只有 `themico`）。`.themis/spec/README.md`「当前强制水平」明写机器强制 unavailable、闸门靠 Agent 遵守。**因此本需求不可能实现"机器写入原话、执行体不可写"那一层**——那需要一个不存在的机器。

## 期望结果

**待追问确认**，当前只写已知边界与三处未定点。

已知边界：`hard-enforcement-list.md` 第 3 项给出的做法分三层，**只有第三层在当前强制水平下可落地**：

| 层 | 做法 | 当前可行性 |
| --- | --- | --- |
| 1 | 人类批复原话入库为不可变记录；机器从答复通道原样落盘，执行体不可写入 | **不可行**——需要 `themis` CLI，不存在 |
| 2 | 工件里每处"所有者要求 X"携带定位，机器做子串比对，追溯不到即拦 | **不可行**——同上 |
| 3 | 闸门只接受受限取值；结论字段为空即未授权，不得推断补足 | **可行**——这是判据层面的约束，可写进 `rules.md`，由评审角色与后续引用方判定 |

**三处未定，须由追问闭合**：

1. **本需求是否只做第三层。** 前两层需要 CLI；若现在只做第三层，将来 CLI 可用时前两层仍要单独做——是否接受这种分期，还是本需求就该等 CLI 一起做。
2. **第三层落到哪里、怎么落。** 候选是 `rules.md` 新增一节、`flow.md` 各人工节点补条款、`template.md` 约束小节形态，或组合。当前控制面对「结论」与「用户原话」两个小节**只规定了它们存在**（`template.md` 的小节划分），未规定内容来源。
3. **提问方式是否纳入范围。** 五次实发中至少三次的成因是**把授权与附带裁定合并提问**——`drift-log.md`「人工验收」条目明写"提问方式本身有份责任"。这属于呈现层（`.themis/skills/spec-review-presentation/`），不属于判据层；是否一并处理，未定。

## 核心链路

从当前状态（人工闸门的结论与原话两个小节由执行体自由写入，无任何来源约束）到目标状态（在不谎称机器强制的前提下，使"推断补足的授权"成为一种**可被下游发现**的越权，而不是不可检出）。

**本需求的性质须先说清**：它**不可能在 soft 执行器下真正阻止**推断补足——没有机器就没有拦截点。它能做到的是**改变失效形态**：从"不可检出"变为"可被发现"。具体机制待设计节点确定，但方向是让推断补足在工件上留下与真授权不同的痕迹。

**一条必须遵守的红线**：`docs/plan/README.md`「通用限制」明写"不得用 Prompt、README、template、policy 或 directory 的存在冒充 machine enforcement"。本需求若把第三层写成条款，**必须同时写明它由谁判、在何时判**——否则就是又一条没有判定者的判据，正是 `.themis/AGENTS.md`「判据必须有判定者」所禁止的形态。

## 范围与非做

**范围**（待 R1 确认后收窄）：

- `.themis/spec/` 控制面中与人工闸门结论、用户原话相关的条款。

**非做**：

- **不实现 `themis` Go CLI**，也不为其预留接口或占位。CLI 是独立的大需求。
- **不声称任何机器强制**。本需求产出的一切都在 soft 执行器下由人与 Agent 遵守。
- 不改 `mvp.md` §2 已批准的行为契约条目。若本需求需要契约变更，须单独提出并经批准，不在本 spec 内擅自改动。
- 不动 `templates/.themico/` 与 Go 代码。
- 不改写 `docs/` 下任何历史记录，含五次实发的原始记载。
