# QA.md — trace-number-scan

## 第 1 轮

### 问 1 — 横切保护判据要不要在 `specify.md` 里显式标出？

**背景**：`SPEC-WSCLEAN-005`（"Go 构建与既有测试必须仍然通过"）不映射到任何任务，这是对的——它是横切保护，不是某个任务的达成状态。但扫描规则无从知道这一点，只能看到"上游有、下游没有"。

**两条路**：

- **(a) 在条目上加显式标识**（例如 `[横切]`），扫描时排除带标识的条目。**代价**：`specify.md` 多一种标识，写条目时要判断该不该加。**好处**：扫描规则不需要猜，判定依据在工件里明写着。
- **(b) 不加标识，改由「来源覆盖」表推断**——该表已有一列写「无（横切保护，非达成状态之一）」。**代价**：扫描要解析表格，且该表的写法此前从未被规定过（是自发的）。**好处**：不新增标识。

**这一条不解决，本需求只能修一半**——缩写问题修完后，`workspace-cleanup` 那条仍会误报。

**Agent 推荐 (a)**，理由：`[basic]` 标识已是既有先例（`rules.md` §5），加一个同类标识不引入新概念；而 (b) 依赖一个从未被规定的自发写法，等于把一个未受治理的约定变成判定依据——**这正是本 spec 流程反复要避免的**。

**答**：「在条目上加显式标识」——与 Agent 推荐一致。

### 问 2 — 缩写写法要不要写进 `template.md` 成为受规定的写法？

**背景**：区间与逗号两种缩写都是自发的，控制面零规定。修扫描规则使其能识别它们，等于事后追认这两种写法。

**两条路**：

- **(a) 只改扫描规则，不规定写法**——扫描尽量宽容地识别，工件怎么写都行。**代价**：将来出现第三种写法（例如 `001-005` 连字符），扫描又会漏，同一缺口第三次实发。
- **(b) 同时在 `template.md` 规定允许的写法**——明确只有完整、区间、逗号三种，其余不合规。**代价**：多一条约束要执行者遵守；已有工件若有第四种写法要改（**本节点须先核实是否存在**）。

**Agent 推荐 (b)**，理由：`claim-command-evidence` 的经验直接适用——**该需求正是因为"写法自发、控制面零规定"才出的问题**，其 step1 的做法是"以既有自发写法为起点、写进控制面"。只改扫描不规定写法，是把同一个坑留给第三次。

**答**：「同时规定写法」——与 Agent 推荐一致。

### 问 3 — 环 3（`T-D` 编号）尚未出现缩写，要不要一并改？

**背景**：§12 同一段同时规定环 2 与环 3 的扫描形态，两者同形。核实结果：环 3 当前**零处**缩写。

**两条路**：

- **(a) 一并改**——两环用同一套识别规则。**代价**：改了一个当前没坏的东西。
- **(b) 只改环 2**——环 3 等它真出问题再说。**代价**：同一段文字里两环规则不一致，读者要分辨；且环 3 迟早会撞上同样的问题（`T-D1、T-D2` 是极自然的写法）。

**Agent 推荐 (a)**，理由：两环在 §12 里是同一句话规定的（"环 3 同形"），只改一环会让那句话不再成立，反而要多写文字去说明差异。**且这不是预留能力**——是让同一条规则在它已声明适用的两处都成立。

**答**：「一并改」——与 Agent 推荐一致。
