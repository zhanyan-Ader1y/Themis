# spec-review-presentation

## 这个 Skill 解决什么

`.themis/spec/rules.md` §3 规定了投影的**抽象层边界**——只含该层增量、不重复下层细节。它没有规定**可读性**：一份完全符合 §3 的投影，仍然可能让评审者读不懂、找不到重点、无法在不翻工件的情况下做出判定。

本 Skill 补的正是这一层。**它不改变任何判据**——某节点是否收敛、评审是否通过，判定规则全部在 `rules.md`，本 Skill 无权改动，只管这些内容"怎么呈现给人看"。

## 两个场合，同一套呈现

本 Skill 适用于两处，**内容应当一致**：

- **对话中**——回复评审项、请求批准或裁定、汇报待决事项。
- **工件中**——写入 `intent-review.md`、`design-review.md`、`task/review.md` 的「投影」小节，或 `acceptance.md` 的「交付视图」小节。

**先写工件、再据其组织对话**，两处说同一件事。对话里讲清楚了而工件里没有，后续引用者读不到；工件里写全了而对话里埋在长文中，评审者当场判不了。

**工件的其余小节不受本 Skill 约束**——「评审范围」「分类核查」「阻断核查」「命令证据」是给执行者与验证角色看的完整记录，按各自条款写，不必迁就可读性。

## 核心原则：默认读者零上下文

**写投影时假设评审者没有读过任何工件、不记得任何专有名词、不知道上文发生过什么。**

评审者是决策者，不是流程的参与者。他要在一屏之内判断"这个方向对不对"，而不是先做一轮考古。凡是需要他回头查证才能理解的东西，都是投影的缺陷，不是他的问题。

一个可操作的自检：**把这份投影单独发给一个从未参与本项目的人，他能不能做出同样的判定？** 不能，就还没写完。

## 八条规则

前五条来自初版的 RED-GREEN 测试（见 `testing-notes.md`）；后三条来自对本项目三个 spec 实例十二份真实投影的实测统计，每条都附证据。

### 1. 自上而下：先意图，后事实，最后细节

固定顺序，不可颠倒：

1. **这一步要达成什么**（一到两句，用人话，不含专有名词）
2. **需要你裁定什么**（如果有，放最前面——这是评审者唯一必须做的事）
3. **发现了什么改变原定方向的事**（如果有）
4. **其余供参考的事实**

**最容易偏离意图的项排在最前面。** 判断标准是"若此处判错，下游返工最大"——通常是范围边界、授权归属、与原定方向的偏离，而不是技术细节。

### 2. 专有名词首次出现即展开

**任何项目内部的标识符——spec-id、任务编号、条目编号、文件代号——首次出现时必须带一句说明它是什么。**

```text
不合格：core-removal 的 verify/detail 零漂移
合格：  上一个需求（删除旧的 core/ 目录）在独立验证环节没有发生偏差
```

```text
不合格：T-D3 无判据覆盖
合格：  第三个任务（把两份入口文件和一份写作规范迁到新位置）没有任何验收判据能检查它做对了没有
```

编号本身对评审者没有意义。**编号是给执行者用的，不是给决策者用的。** 投影里可以保留编号作为索引，但必须紧跟一句人话。

### 3. 事实要具体到可核对，但只给结论所需的那部分

评审者判断需要事实支撑，但不需要完整证据链。

- **给具体路径**：`AGENTS.md` 第 48–52 行那一节，而不是"某处文档"。
- **给内容摘要**：那一节写的是"安装包源在 templates/ 下、安装动作由 CLI 承担"——而不是只给行号让他自己去看。
- **不给完整原文**：粘贴整段是把核对工作推给评审者。

标准是：**读到这一条，他能判断"这个说法成立吗"，而不需要打开文件。**

### 4. 删掉规模数字，除非它改变判断

**"删除 45 个文件"、"改动 7 处文本"、"三份齐备"这类计量对评审者没有意义。** 他不关心工作量，关心的是方向对不对、边界在哪、有没有动到不该动的东西。

规模数字只在一种情况下保留：**它本身就是判断依据**。例如"这个改动会碰到 26 份属于另一个模块的文件"——此时数字说明的是越界范围，不是工作量。

同理删掉：
- 工件小节是否齐备（那是执行者的自检，不是评审内容）
- 命令跑了几条、输出多少行
- 「四节齐备」「五条判据均已产出」这类完备性陈述

### 5. 每条都要有前因后果

**孤立的结论无法判定。** 每一条呈现给评审者的项，都要能回答三个问题：

- **为什么会有这一条**（起因）
- **现在的处置是什么**（决定）
- **如果判错会怎样**（后果）

三者可以压缩在两三句里，但不能缺。缺了起因，评审者不知道这是不是必要的；缺了后果，他不知道该多认真对待。

```text
不合格：basic 段为空，判定成立。

合格：  这一步没有"内部准备工作"——每个任务都直接改变仓库里
        看得见的东西。原本的设计稿建议把前两步归为准备工作，
        但那不符合规则里"准备工作必须自己不产生可见改动"这
        一条。若照原稿分类，这一步会带着一个不成立的分段进入
        实现，实现完才会发现分错。
```

### 6. 投影控制在 250 词以内，超了就是没想清楚

**实测证据**：本项目三个实例的十二份投影，长度从 **21 词到 253 词**，无收敛。最长那份（253 词）把执行次序、任务清单、判据列表全复述了一遍；最短那份（21 词）反而是信息最全的之一——它只写了做完什么、验证结果、三处知情项。

**长度不是详尽程度的度量，是取舍程度的度量。** 写不短通常不是内容多，是没分清哪些影响批准、哪些不影响。

超了怎么办：**先删「其余要点」**（它的契约最容易被撑破，见结构模板），再删对下层细节的复述，最后才考虑压缩裁定点——**裁定点永远最后压**。

### 7. 不出现内部角色名与节点名

**实测证据**：本项目投影中「本节点」出现 42 次、「验证环节」11 次、「执行体」5 次。评审者不知道这些指谁。

| 不写 | 改写成 |
| --- | --- |
| 本节点 / 执行体 | 我 |
| 验证环节 / 验证角色 | 验证时 / 核对下来 |
| impl/detail、verify/basic | 落地时 / 验证时 |
| R2、R3 | 上一轮评审 / 上次批准时 |
| SPEC-XXX-001 | 那条要求（后跟一句它要求什么） |

**同理不写**：`rules.md §7`、`flow.md`「impl/detail」节这类条款定位。评审者不查条款，他判的是事情本身。**若某个判断确实依赖条款，就用一句话说清那条款要求什么**，不给编号。

### 8. 已确认过的事不再重复呈现，只列本轮新增

**实测证据**：本项目后期投影出现「上一轮已确认的三处缺口本轮不重复呈现」这类写法——**这是对的**，但它是执行者自发做的，此前没有规则。

评审者已经在上一轮批准过的内容，**本轮投影不重复**。它们不会因为不再提及而失效——已批准就是已批准。

需要重提的只有两种情况：**该项在本轮发生了变化**（说清变了什么），或**本轮的判断依赖它**（用一句话点出依赖关系，不复述其内容）。

「我知道但还没解决的」一节同理：只列**本轮新增或本轮才暴露**的缺口；上一轮已确认的旧缺口写一句"上轮已确认的 N 处仍然成立"即可，不逐条重述。

## 结构模板

每一节的内容由它的**契约**决定——写进去的东西必须满足该节那一句，不满足的不属于这一节。

```markdown
## 这一步要做什么
一到两句人话，零专有名词。读完能复述目标，就够了。

## 需要你裁定
每条：起因 → 可选做法 → 各自判错的后果。没有则写"无"。
**每个待决项独立成条**，一条只问一件事。
**批准本身是其中一条**，不隐含在别处——评审者应当能只回这一节就答完全部待决事项。

## 改变了原定方向的发现
每条：原本打算怎么做 → 核实到什么 → 现在改成怎么做。没有则整节省略。

## 其余要点
只放**影响批准与否、但不需要裁定**的事实。
每条一句，最多两句。

## 我知道但还没解决的
本次批准**没有**覆盖什么：已知缺口、无判据保护的部分、留待后续的开放项。
```

**「其余要点」的契约最容易被撑破**——它不是"把方案再讲一遍"的地方。判断标准只有一条:**这条事实如果去掉，评审者的批准/不批准会改变吗?** 不会改变就不属于这一节。执行次序、任务清单、判据列表通常都不属于——那些在工件里，评审者需要时会去看。

**最后一节不可省略。** 评审者有权知道这次批准的边界在哪。

## 交付前自检

逐条对照，每条都是**成品应有的样子**，不是禁令清单：

| 检查 | 通过的样子 |
| --- | --- |
| 首节 | 一到两句人话说清目标，零专有名词 |
| 裁定点 | 在第二节，每条带起因、可选做法、判错后果 |
| 每个编号 | 首次出现时紧跟一句它是什么 |
| 每个事实 | 有具体路径 + 内容摘要，读完能判断它成立与否 |
| 每个数字 | 是判断依据；纯工作量计量已删 |
| 「其余要点」 | 每条去掉后会改变批准与否 |
| 末节 | 写明本次批准没有覆盖什么 |
| **总长度** | **250 词以内** |
| **角色与节点名** | **无"本节点""验证环节""执行体"；无 `rules.md §N`、`SPEC-XXX-001` 这类定位** |
| **旧内容** | **上轮已确认的不重复呈现，只列本轮新增** |

**最强的一条自检**：把这份投影单独发给一个从未参与本项目的人——他能做出同样的判定吗？不能，就还没写完。

## 与判定规则的边界

**本 Skill 只管呈现，不管判定。**

- 某节点能否进入下一步 → `.themis/spec/flow.md`
- 某条判据是否满足、谁有权判 → `.themis/spec/rules.md`
- 工件有哪些小节 → `.themis/spec/template.md`

**投影可读性不是判据。** 评审者不会因为投影写得好就批准，也不该因为写得差就驳回——他驳回的是内容本身。本 Skill 的作用是让他**看得清内容本身**，不是让内容显得更好。

**尤其不得为了"呈现清晰"而修改事实**：不得省略不利的发现、不得把不确定写成确定、不得把越界描述成常规。如实呈现与清晰呈现冲突时，**如实优先**——但绝大多数情况下两者一致，冲突往往说明结论本身还没想清楚。
