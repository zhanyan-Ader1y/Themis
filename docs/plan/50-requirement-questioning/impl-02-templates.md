# P5 子模块：追问模板

## 覆盖任务

- 任务 2：编写 `spec-questioning.md`（四步 Prompt 模板）
- 任务 3：编写 `spec-adversarial-checklist.md`（攻击场景库）

## 设计依据

- **D3**：对抗验证以 Prompt 驱动，不实现确定性脚本 → 模板文件是 Prompt 工程产物
- **D2**：复杂度自适应 → 模板中嵌入 `complexity` 判定与跳转指令
- **D5**：Red Flags 嵌入 Prompt → 模板在全局约束段中嵌入防绕过规则

## 目标文件 1：`spec-questioning.md`

**路径**：`templates/.themis/core/templates/spec-questioning.md`

### 结构设计

```markdown
# Themis 需求追问模板

本文档定义 Specification 模块在 Draft → Specified 阶段的完整追问流程。
Agent 按复杂度自适应规则在不同 Step 之间跳转。

## 全局约束

在所有 Step 中遵守：

1. 一次只问一个问题。每个回答影响后续问题。
2. 优先使用选择题，降低用户认知负担。
3. 不得跳过 Spec 创建。简单需求可以短 Spec，但不能无 Spec。
4. 不得在看代码之前声称"需求已清楚"。
5. 关键决策必须引用数据、经验或约束作为支撑。
6. 必须主动提出至少一个用户可能未考虑的场景。

## 复杂度判定

在 Step 1 末尾判定复杂度：

- low: 单文件修改、无新增 API、无状态变更
- medium: 新增功能、跨模块修改、涉及数据模型
- high: 多子系统、架构变更、安全/性能敏感

判定结果需用户确认。如用户否决，以用户指定等级为准。

### 复杂度对应的流程

| Step | low | medium | high |
|---|---|---|---|
| Step 0 意图发现 | 精简版（1 轮） | 完整版 | 完整版 |
| Step 1 范围评估 | 完整版 | 完整版 | 完整版 |
| Step 2 上下文收集 | 跳过 | 完整版 | 完整版 |
| Step 3 设计收敛 | 精简版（1 方案） | 完整版 | 完整版 |
| Step 4 对抗验证 | 快速检查表 | 聚焦核心 AC | 全覆盖 |

---

## Step 0 — Intent Discovery（意图发现）

**角色**：协作者。你的任务是理解用户真正想解决的问题，
而不是接受表面需求。

### 行为指令

1. 接收用户的需求陈述。
2. 追问"为什么需要这个"，逐层深入直到触及根因。
3. 区分"用户要的"和"用户需要的"。
4. 如果根因与表面需求不同，提出一个可能更直接的替代方案。

### low 复杂度精简版

仅执行 1 轮为什么追问，快速确认核心意图。
不强制要求 Five Whys 的完整链条。

### 输出

- 一句话核心意图
- 根因陈述
- （如适用）替代方案建议

---

## Step 1 — Scope Assessment（范围评估）

**角色**：协作者。你的任务是评估需求的影响范围
并识别关键风险和假设。

### 行为指令

1. 判断是否涉及多个子系统或模块。
2. 若是，帮助分解为子项目，先追问第一个。
3. 执行 Pre-mortem："假设这个功能上线 3 个月后失败了，
   最可能的 3 个原因是什么？"
4. 识别当前理解中的关键假设（至少 2 个）。
5. 按 complexity 判定规则确定复杂度等级。
6. 要求用户确认复杂度等级。

### 输出

- 范围描述（单系统 / 多系统 → 分解方案）
- Pre-mortem 风险清单（3 项）
- 关键假设清单
- 复杂度等级（待用户确认）

---

## Step 2 — Context Gathering（上下文收集）

**角色**：协作者。你的任务是收集目标、约束、
成功标准和证据。

**仅在 medium 和 high 复杂度执行。**

### 行为指令

1. 明确目标：解决什么问题？给谁用？
2. 收集约束：技术栈、时间、依赖、兼容性。
3. 定义成功标准：要求可量化指标（如"P95 延迟 < 200ms"
   而非"更快"）。
4. 询问 Option Zero："能否不改代码解决这个问题？"
5. 列出当前方案依赖的关键假设（从 Step 1 扩展）。
6. 关键决策需要证据支撑——追问"这个判断的依据是什么？"

### 输出

- 目标陈述
- 约束清单
- 可量化的成功标准
- Option Zero 结论
- 完整假设清单（含验证方式）
- 关键证据链

---

## Step 3 — Design Convergence（设计收敛）

**角色**：协作者。你的任务是提出可选方案并收敛为
一份可执行的 Spec。

### 行为指令

1. 提出 2-3 种方案，明确说明取舍和推荐理由。
2. 对每个方案进行首轮对抗："这个方案最可能在什么场景下失败？"
3. 分段确认 AC：每段 1-3 个 AC，逐段要求用户确认。
4. 将完整设计写入 workspace/specs/<spec-id>/spec.md。
5. 执行 Spec 自检（见下方自检清单）。

### low 复杂度精简版

仅提出 1 个方案 + 1-2 个核心 AC。首轮对抗聚焦于
最可能出错的 1 个场景。

### Spec 自检清单

结构检查：
- [ ] 无 TODO、FIXME 等占位符
- [ ] 无内部矛盾（如"支持所有浏览器" + "仅 Chrome"）
- [ ] 无模糊术语（每个形容词有量化对应）
- [ ] 范围边界明确

对抗检查：
- [ ] 关键假设显式列出并标注验证方式
- [ ] 每个 AC 考虑了至少一个失败/边界场景
- [ ] 关键决策有证据支撑
- [ ] 对抗验证的已知限制记录在 Limitation 段
- [ ] 方案解决根因而非表面需求
- [ ] 回滚路径清晰

### 输出

- 已写入的 spec.md 草稿
- 自检结果

---

## Step 4 — Adversarial Validation（对抗验证）

**角色切换**：你现在是"攻击者"。你的任务是找出 Spec
中的漏洞、未覆盖的边界条件和隐藏假设。
不要太客气——简单需求往往隐藏最深的假设。

### 行为指令

1. 宣布角色切换："接下来我会尝试从不同角度挑战这个方案，
   目的是在编码前发现潜在问题。"
2. 按攻击维度逐一扫描 Spec 的每个 AC。
3. 每个攻击场景以选择题方式呈现：
   "如果 [场景]，系统应该：[A] / [B] / [C] 其他处理方式？"
4. 用户选择后：
   - 修改 Spec 覆盖该场景
   - 接受为已知限制（记录在 Limitation 段）
   - 标记为后续版本处理
5. 重复直到：
   - 无新的有效攻击场景，或
   - 达到指定的最大迭代轮次

### low 复杂度快速检查表

仅执行以下 5 项检查：

1. 空数据/缺失输入：如果输入为空或缺失，系统应该做什么？
2. 失败状态：如果操作失败，用户如何感知？系统如何恢复？
3. 并发冲突：两个用户同时执行此操作会发生什么？
4. 向后兼容：此变更是否影响现有功能？如何验证？
5. 回滚方案：如果需要撤销此变更，路径是否清晰？

### medium 复杂度聚焦模式

聚焦 Spec 中的核心 AC（优先级最高的 1-3 个），
使用完整攻击维度扫描。

### high 复杂度全覆盖模式

对所有 AC 做全维度扫描，视需要多轮迭代。

### 攻击维度

| 维度 | 关注点 |
|---|---|
| 边界条件 | 空值、null、最大值、最小值、超长输入、特殊字符、负值 |
| 并发与竞态 | 同时操作、重复提交、超时、部分成功、乱序到达 |
| 状态转换 | 非法状态、跳过步骤、状态回退、并发状态修改 |
| 权限与安全 | 未授权访问、数据泄露、注入攻击、越权操作 |
| 依赖失败 | 外部服务不可用、超时、返回异常格式、降级策略 |
| 数据完整性 | 部分写入、格式错误、编码问题、迁移中断 |

### 输出

- 已处理的所有攻击场景清单
- 每个场景的处理方式（覆盖 / 接受 / 延迟）
- Spec 中已更新的 Limitation 段（如有接受或延迟的场景）
```

## 目标文件 2：`spec-adversarial-checklist.md`

**路径**：`templates/.themis/core/templates/spec-adversarial-checklist.md`

### 结构设计

该文件是 Step 4 对抗验证的标准攻击场景库。与 `spec-questioning.md` 中的 Step 4 区别：
- `spec-questioning.md` 定义流程和角色切换
- `spec-adversarial-checklist.md` 提供具体可复用的攻击场景清单

```markdown
# Themis 对抗验证攻击场景库

本文档提供 Step 4 对抗验证的标准攻击场景。
Agent 按需引用相应维度，逐项扫描 Spec 的 AC。

## 使用说明

- **low 复杂度**：仅使用"快速检查表"段
- **medium 复杂度**：聚焦核心 AC，扫描全部 6 维度，
  每维度选择最相关的 2-3 个场景
- **high 复杂度**：覆盖所有 AC，扫描全部场景

---

## 快速检查表（5 项）

仅用于 low 复杂度需求。

1. **空数据/缺失输入**：输入为空时，系统行为是否已定义？
2. **失败状态**：操作失败时，用户通知和恢复机制是否已说明？
3. **并发冲突**：多用户同时操作的预期行为是否已描述？
4. **向后兼容**：对现有功能的影响和验证方法是否已考虑？
5. **回滚方案**：撤销路径是否清晰可行？

---

## 维度 1：边界条件

| # | 场景 | 攻击问题 |
|---|---|---|
| B1 | 空值输入 | 如果必填字段为空或 null，系统返回什么？ |
| B2 | 最大/最小值 | 如果输入值超出有效范围（极大值、负数、零），如何处理？ |
| B3 | 超长输入 | 如果字符串长度超出预期（如 10MB 的文本字段），系统是否安全降级？ |
| B4 | 特殊字符 | 如果输入含 SQL 注入、XSS、Unicode 控制字符、emoji，系统如何处理？ |
| B5 | 缺失依赖数据 | 如果引用的外键或关联数据已被删除，操作能否安全失败？ |
| B6 | 时区与国际化 | 如果涉及时间或格式化输出，不同时区和 locale 下行为是否一致？ |

## 维度 2：并发与竞态

| # | 场景 | 攻击问题 |
|---|---|---|
| C1 | 同时修改 | 两个用户同时修改同一资源，最终状态是什么？ |
| C2 | 重复提交 | 用户快速点击两次提交按钮，是否产生重复数据？ |
| C3 | 操作超时 | 如果操作超时但后端实际已执行，用户可以安全重试吗？ |
| C4 | 部分成功 | 批量操作中部分成功部分失败，整体状态如何呈现？ |
| C5 | 乱序到达 | 如果事件或消息以非预期顺序到达，状态机是否仍正确？ |

## 维度 3：状态转换

| # | 场景 | 攻击问题 |
|---|---|---|
| S1 | 非法状态 | 如果从当前状态执行不应允许的操作，系统如何拒绝？ |
| S2 | 跳过步骤 | 如果跳过工作流中的某个必需步骤，后续操作是否被阻止？ |
| S3 | 状态回退 | 是否允许从终态回退到中间态？在什么条件下允许？ |
| S4 | 并发状态修改 | 两个进程同时修改同一状态时，最终一致性如何保证？ |
| S5 | 初始状态 | 系统首次启动或数据为空时，初始状态是否正确？ |

## 维度 4：权限与安全

| # | 场景 | 攻击问题 |
|---|---|---|
| P1 | 未授权访问 | 未登录用户或低权限用户是否能访问该功能？ |
| P2 | 越权操作 | 用户 A 是否能操作用户 B 的数据？（横向越权） |
| P3 | 数据泄露 | 错误信息或日志中是否会泄露敏感数据（token、PII）？ |
| P4 | 注入攻击 | 是否有 SQL、命令、模板注入的输入点？ |
| P5 | CSRF/XSS | 是否存在跨站请求伪造或跨站脚本的风险？ |

## 维度 5：依赖失败

| # | 场景 | 攻击问题 |
|---|---|---|
| D1 | 外部服务不可用 | 如果依赖的 API、数据库、消息队列不可用，系统如何降级？ |
| D2 | 超时 | 如果外部调用超时（而非明确失败），重试策略是什么？ |
| D3 | 异常返回格式 | 如果外部服务返回非预期格式（500 错误带 HTML body），解析器能否安全失败？ |
| D4 | 降级策略 | 降级时返回缓存数据、默认值还是错误？用户是否感知降级？ |
| D5 | 恢复后状态 | 依赖恢复后，系统能否自动恢复正常？需要人工干预吗？ |

## 维度 6：数据完整性

| # | 场景 | 攻击问题 |
|---|---|---|
| I1 | 部分写入 | 如果写入操作在中间步骤失败，已有数据是否保持一致性？ |
| I2 | 格式错误 | 如果输入数据格式与 Schema 不匹配，错误信息是否可操作？ |
| I3 | 编码问题 | 涉及文件上传或导出时，编码（UTF-8/UTF-16/GBK）是否已处理？ |
| I4 | 迁移中断 | 如果数据迁移/转换在中途失败，是否可以安全回滚？ |
| I5 | 大文件处理 | 如果文件或数据量超过内存限制，是否采用流式处理？ |

---

## 攻击结果处理

每个攻击场景的终态必须是以下三种之一：

| 处理方式 | 记录位置 | 含义 |
|---|---|---|
| **Cover** | 修改 Spec 正文 | 将该场景纳入需求范围 |
| **Accept** | Spec→Limitation 段 | 承认该场景为已知限制，当前版本不处理 |
| **Defer** | Spec→Limitation 段 + 注明版本 | 标记为后续版本处理 |
```

## 验证要求

- `spec-questioning.md` 含 Step 0/1/2/3/4 五个独立段
- Step 4 段明确要求角色切换
- 复杂度跳转指令完整（low/medium/high 三档）
- `spec-adversarial-checklist.md` 含 6 个攻击维度
- 每维度至少 3 个具体场景
- 快速检查表独立可用（5 项）
