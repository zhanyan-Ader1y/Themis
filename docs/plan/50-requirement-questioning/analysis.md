# P5 需求追问策略优化 — 方法论对比分析

## 分析方法论概述

### 1. grill-me（aihero.dev）

grill-me 是一个"魔鬼代言人"式的需求追问 Skill，核心理念是：**在编码之前，先假设用户的需求是有缺陷的，然后通过对抗性提问来发现隐藏的假设、边界条件和失败模式。**

核心原则：

| 原则 | 说明 |
|---|---|
| 对抗性立场 | 不是"帮用户澄清需求"，而是"试图证明需求不完整或有矛盾" |
| 简单即可疑 | 听起来越简单的需求，越可能隐藏未陈述的假设 |
| 边界条件优先 | 先问"什么情况下会失败"，再问"正常情况怎么做" |
| 压力测试 | 用极端场景、并发、空数据、超时等边缘条件挑战需求 |
| 迭代攻防 | 提出方案 → 攻击方案 → 用户辩护或修正 → 再次攻击 → 收敛 |
| 拒绝"看起来对" | 不接受模糊的共识，要求具体、可验证的陈述 |

典型工作流：

```
1. 接收需求
2. 识别最薄弱的假设
3. 提出一个会破坏该假设的场景
4. 要求用户处理该场景（修改需求或承认限制）
5. 重复直到没有新的薄弱点
6. 输出加固后的需求文档
```

### 2. 苏格拉底式提问

源自苏格拉底教学法，六类核心提问：

| 类型 | 示例问题 |
|---|---|
| 澄清 | "你说的'快'具体指什么？" |
| 探测假设 | "你假设用户总是登录状态，这个假设成立吗？" |
| 探测证据 | "什么数据或经验支持这个方案是最优的？" |
| 追问观点 | "反对这个方案的人会说什么？" |
| 探测后果 | "如果这个功能上线后没人用，会怎样？" |
| 追问问题本身 | "为什么我们现在要解决这个问题而不是其他问题？" |

### 3. Five Whys（五问法）

丰田生产系统的根因分析技术：连续追问"为什么"直到触及根本原因，而非停留在表面需求。

```
用户: "我需要一个导出 CSV 的功能"
为什么？→ "因为运营团队需要分析数据"
为什么？→ "因为他们用 Excel 做报表"
为什么？→ "因为现有的 BI 看板不满足他们的需求"
为什么？→ "因为 BI 看板缺少自定义维度筛选"
为什么？→ "因为 BI 上线时没有收集运营部门的完整需求"

根因：BI 看板功能不完整 → 真正需要的是增强 BI 看板，而非新增 CSV 导出
```

### 4. Pre-mortem（事前验尸）

在项目开始前假设项目已经失败，倒推失败原因：

```
"假设这个功能上线 3 个月后失败了。是什么原因导致的？"
→ 强迫团队在开始前识别风险
→ 将模糊的担忧转化为具体的风险清单
```

### 5. superpowers brainstorming（已有参考）

P5 已引用，核心是"一次一问、选择题优先、硬门禁"的结构化收敛流程。

## 与现有 P5 设计的对比

### 现有 P5 的优势

| 优势 | 来源 |
|---|---|
| 结构化五阶段流程（Step 0–4） | superpowers、Five Whys、Pre-mortem 与 grill-me 的组合 |
| 一次一问，避免认知过载 | superpowers |
| 硬门禁：无 Spec 不写代码 | superpowers |
| 复杂度自适应（简单需求可跳过） | Themis 适配 |
| AC 分段确认 | superpowers |
| Red Flags 防绕过机制 | 自研 |
| Option Zero 考虑 | 自研 |

### 现有 P5 的缺失

| 缺失 | 相关方法论 | 严重程度 |
|---|---|---|
| **无对抗性压力测试**：只收集需求，不主动攻击需求的薄弱点 | grill-me | 高 |
| **无根因分析**：接受用户陈述的表面需求，不追问"为什么需要这个" | Five Whys | 高 |
| **无假设探测**：不系统性地列出并挑战隐藏假设 | 苏格拉底式提问 | 中 |
| **无失败模式分析**：只关注"怎么做对"，不关注"怎么可能会错" | Pre-mortem, grill-me | 中 |
| **无证据链要求**：不要求用户为关键决策提供数据或经验支撑 | 苏格拉底式提问 | 中 |
| **防绕过不够激进**：允许简单需求跳过，但 grill-me 认为简单需求最危险 | grill-me | 中 |
| **无"负面空间"探索**：不主动列举需求未覆盖的场景 | grill-me | 低 |
| **缺乏迭代攻防**：收敛是单向的，不经过"攻击→修正→再攻击"循环 | grill-me | 低 |

### 关键差距总结

P5 的流程本质上是 **"协作式需求澄清"**——AI 帮助用户把模糊的想法说清楚。

grill-me + 苏格拉底式提问的流程本质上是 **"对抗式需求验证"**——AI 试图证明用户的需求是错的，用户必须通过辩护来证明需求的正确性。

两者的核心区别在于**立场**：协作式假设需求是好的只是不够清晰，对抗式假设需求可能是有缺陷的需要被检验。

## 优化后的 P5 追问策略

### 设计原则

优化后的策略将 superpowers 的**协作式收敛**与 grill-me 的**对抗式验证**融合为两阶段流程：

- **阶段一（协作）**：理解用户意图，收集需求，形成候选方案
- **阶段二（对抗）**：主动攻击候选方案，暴露薄弱点，迫使修正

### 核心原则（扩充后）

| 原则 | 来源 | 说明 |
|---|---|---|
| 一次一问 | superpowers | 保留 |
| 优先选择题 | superpowers | 保留 |
| 先评估范围再深入 | superpowers | 保留 |
| 硬门禁 | superpowers | 保留，增强为"Spec 须通过对抗验证才能批准" |
| 设计分段验证 | superpowers | 保留 |
| **对抗性验证** | grill-me | **新增**：在方案收敛后，切换为攻击者立场 |
| **简单即危险** | grill-me | **新增**：简单需求不跳过验证，用更轻量的检查表 |
| **追问根因** | Five Whys | **新增**：在 Step 0 执行“为什么”链，区分表面方案与实际需要 |
| **探测假设** | 苏格拉底式 | **新增**：要求列出关键假设并逐一验证 |
| **事前验尸** | Pre-mortem | **新增**：在收敛前询问"如果这个方案失败了，会是什么原因" |
| **证据锚定** | 苏格拉底式 | **新增**：关键决策必须引用数据、经验或约束 |

### 优化后的五阶段流程（Step 0–4）

```
Step 0 — Intent Discovery（意图发现）【新增】
  ├── 用户的核心目标是什么？（不是"做什么"，而是"为什么做"）
  ├── Five Whys：连续追问"为什么"直到触及根因
  ├── 区分"用户要的"和"用户需要的"
  ├── 输出：一句话核心意图 + 根因陈述
  └── 若根因与表面需求不同，提出替代方案

Step 1 — Scope Assessment（范围评估）【保留 + 增强】
  ├── 识别是否多子系统
  ├── 若是：帮助分解为子项目，先追问第一个
  ├── 若否：进入详细追问
  ├── 【新增】Pre-mortem：如果这个功能 3 个月后失败了，可能原因是什么？
  └── 【新增】识别关键假设并标注需要验证的假设

Step 2 — Context Gathering（上下文收集）【保留 + 增强】
  ├── 目标：解决什么问题？给谁用？
  ├── 约束：技术栈、时间、依赖、兼容性
  ├── 成功标准：怎样算"做完"？【增强】要求可量化指标
  ├── "Option Zero"：能否不改代码解决？
  ├── 【新增】假设清单：列出当前方案依赖的关键假设
  └── 【新增】证据链：关键决策的支撑依据是什么？

Step 3 — Design Convergence（设计收敛）【保留 + 增强】
  ├── 提出 2-3 种方案 + 取舍 + 推荐
  ├── AC 分段确认（每段 1-3 个 AC）
  ├── 【新增】对每个方案进行首轮对抗：最可能失败的场景是什么？
  ├── 写入 workspace/specs/<spec-id>/spec.md
  ├── Spec 自检（占位符、矛盾、歧义、范围）

Step 4 — Adversarial Validation（对抗验证）【全新】
  ├── AI 切换为攻击者立场
  ├── 系统性攻击 Spec 的每个 AC：
  │     ├── 边界条件：最小值、最大值、空值、null、超长输入
  │     ├── 并发与竞态：同时操作、重复提交、超时
  │     ├── 状态转换：非法状态、跳过步骤、回退
  │     ├── 权限与安全：未授权访问、数据泄露、注入
  │     ├── 依赖失败：外部服务不可用、超时、返回异常
  │     └── 数据完整性：部分写入、格式错误、编码问题
  ├── 每个攻击场景：用户选择 ① 修改 Spec 覆盖 ② 接受为已知限制 ③ 标记为后续版本处理
  ├── 重复直到无新的有效攻击场景
  └── 用户批准后记录 Draft 审批证据；只有未来 P8 确定性执行器可以记录 `Draft → Specified`
```

### 复杂度自适应

| 需求复杂度 | 判定标准 | 追问策略 |
|---|---|---|
| 低 | 单文件修改、无新增 API、无状态变更 | Step 0（精简版）→ Step 1 → Step 3（精简版）→ Step 4（快速检查表） |
| 中 | 新增功能、跨模块修改、涉及数据模型 | 完整五阶段流程（Step 0–4），Step 4 聚焦核心 AC |
| 高 | 多子系统、架构变更、安全/性能敏感 | 完整五阶段流程（Step 0–4），Step 4 全覆盖，可能多轮迭代 |

> 关键改变：即使"简单"需求也必须经过 Step 4 的快速检查表，不能完全跳过验证。grill-me 的核心教训是：简单需求往往隐藏最深的假设。

### 对抗验证检查表（Step 4 快速模式）

低复杂度需求使用此检查表（AI 逐项提问，5 轮内完成）：

1. 空数据/缺失输入：如果输入为空，系统应该做什么？
2. 失败状态：如果操作失败，用户如何知道？系统如何恢复？
3. 并发冲突：如果两个用户同时执行这个操作，会发生什么？
4. 向后兼容：这个变更是否影响现有功能？如何验证？
5. 回滚方案：如果这个变更需要撤销，怎么操作？

### 防绕过机制（增强版）

| Agent 的想法 | 当前约束 | 优化后约束 |
|---|---|---|
| "这个需求很简单，直接写就行" | 没有 Spec 不进入 Implemented | 追加：简单需求必须通过快速对抗检查表（Step 4 轻量版） |
| "我先看看代码再理解需求" | 先读 Context，再追问，再看代码 | 追加：看代码之前必须先陈述"我要验证什么假设" |
| "这个不需要正式 Spec" | 所有变更都必须有 Spec | 追加：Spec 的最小长度由复杂度决定，但必须包含至少一个可验证的 AC |
| "用户已经说清楚了" | 防 Red Flags | 追加：AI 必须主动提出至少一个"用户可能没考虑到的场景" |
| "我先改一行试试" | Implemented 之前必须 Specified | 追加：任何代码变更前必须通过 Step 0（意图确认） |
| "这个方案显然是最好的" | — | **新增**：AI 必须至少提出一个可替代方案，即使它最终被否决 |

### 与 SDD 生命周期的整合（更新）

```
Draft
  │
  ├── Step 0: Intent Discovery（意图发现 + Five Whys）
  │     └── 确认根因，决定是否继续
  │
  ├── Step 1: Scope Assessment（范围评估 + Pre-mortem）
  │     └── 识别范围、假设和风险
  │
  ├── Step 2: Context Gathering（上下文收集 + 证据链）
  │     └── 收集约束、目标和证据
  │
  ├── Step 3: Design Convergence（设计收敛 + 首轮对抗）
  │     └── 形成候选方案，写入 Spec 草稿
  │
  ├── Step 4: Adversarial Validation（对抗验证）
  │     ├── 攻击 Spec 的每个 AC
  │     ├── 用户处理攻击场景
  │     └── 重复直到无新的有效攻击
  │
  ▼
Draft（已记录用户批准与 Gate 证据；P5 的最终状态）
  │
  ├── P8 确定性执行器（规划中）校验 `draft_to_specified` 条件并写入状态
  ▼
Specified
  │
  ▼
Planned（Planning 模块接管）
```

### Spec 自检清单（增强版）

原有自检项：
- 占位符检测
- 矛盾检测
- 歧义检测
- 范围检测

新增自检项：

| 检查项 | 说明 |
|---|---|
| 假设可追溯 | 每个关键假设是否被显式列出并标注了验证方式？ |
| 失败场景覆盖 | 每个 AC 是否考虑了至少一个失败/边界场景？ |
| 证据锚定 | 关键决策是否有数据、经验或约束作为支撑？ |
| 攻击残留 | 对抗验证中发现的已知限制是否被记录在 Spec 的 Limitation 段？ |
| 根因对齐 | 方案是否真正解决了 Step 0 中识别的根因，而非表面需求？ |
| 回滚可行 | 如果变更需要回滚，路径是否清晰？ |

### 新增目标文件

| 文件 | 说明 |
|---|---|
| `core/policies/specification.yaml` | 增加 `adversarial_validation` 配置段 |
| `core/templates/spec-questioning.md` | 增加 Step 0 和 Step 4 的提示词模板 |
| `core/templates/spec-adversarial-checklist.md` | **新增**：Step 4 对抗验证的标准攻击场景库 |
| `core/policies/transitions.yaml` | 更新硬门禁条件：增加"对抗验证通过" |

### 更新后的验收条件

- `Draft` 状态的 Spec 必须完成 Step 0–4 并记录全部 Gate 证据，未来 P8 执行器才可迁移到 `Specified`
- 对抗验证中发现的每个攻击场景都得到处理（覆盖、接受或延迟）
- 简单需求不跳过对抗验证，而是使用快速检查表
- Spec 包含显式的假设清单和已知限制
- 关键决策能追溯到数据、经验或约束
- 多子系统需求在范围评估阶段被识别并建议分解
- Agent 不能以"需求简单"为由跳过 Spec 创建
- Agent 必须主动提出至少一个用户可能未考虑的场景

### 风险与缓解

| 风险 | 级别 | 缓解 |
|---|---|---|
| 对抗验证过于激进，用户感到被冒犯 | 中 | 在 Step 4 开始前明确说明“接下来我会尝试挑战你的方案，目的是发现潜在问题，不是否定你的想法”；不得提供跳过对抗验证的旁路，低复杂度需求仍须完成五项快速检查。 |
| 简单需求的对抗验证显得多余 | 低 | 快速检查表仅 5 个问题，2-3 轮即可完成 |
| 对抗验证增加时间成本 | 中 | 复杂度自适应；对抗深度与需求复杂度成正比 |
| Five Whys 可能指向组织问题而非技术问题 | 低 | 当根因超出技术范围时，记录为已知限制，仍按技术需求处理 |
