# hard 执行器强制清单

本文件是 `.themis/spec/` 控制面首次端到端 replay(spec-id:`core-removal`)的第二份产出,输入是 `drift-log.md` 十三个节点条目里累计的 23 个漂移 facet。它回答一个问题:**soft 执行器(靠 Agent 遵守 + 人类可读状态文件)下靠不住的是哪些,将来 hard 执行器该机器强制什么。**

**本文件不是规范,是 replay 的结论。** 它不定义控制面条款,也不能被当作 `.themis/spec/` 之外的第二份合同引用。每一条强制项都必须能在 `drift-log.md` 里指到真实发生过的漂移;凭空推测的不写。

## 排序规则

**优先级由 replay 的实际发生次数决定,不由理论严重性决定**(来源计划 `docs/superpowers/plans/2026-08-19-spec-flow-end-to-end-replay.md` 任务 8 步骤 2)。真的漂移过的排在前面,次数多的排在更前面。这条规则本身值得说明为什么:严重性判断来自直觉,而直觉在本次 replay 里被证明不可靠——**第 3 项(伪造授权链)读起来是全清单最吓人的一条,实发只有 2 次;第 1 项(数值 claim 出错)读起来只是"不够仔细",实发 8 次以上、且每一次都是靠外部复核才抓到。** 按直觉排会把资源投给稀有事件。

对"本次未发生但理论上有风险"的项,一律注明未发生并排在末尾。

### 1. 数值型与存在性 claim 必须由执行时真实运行的命令产生并就地附输出

- **来自哪个节点的漂移**:Intake、抽象设计、详细设计 + 任务(两次独立发生)、verify/basic
- **soft 执行器下靠什么**:**无保障。** 靠撰写者下笔时自觉重跑命令,以及事后人工评审独立重跑。
- **hard 执行器该怎么强制**:工件里每一条数值型、路径存在性、计数型 claim 都结构化携带"验证命令 + 断言值",执行器在提交前逐条重跑并精确比对,不一致即拒绝提交。这是字符串与数字的精确比对,不需要语义理解。
- **优先级依据**:**实发 8 次以上,是全清单最高频的一类,且无一例外都不是靠通读文字抓到的。** 具体:`docs/` 引用文件数报 36(实为随 grep 模式在 37–47 浮动);`design.md` 判据命中行数记 14(实为 16);`.gitignore` 总行数写 10(实为 11,而同一文件紧邻处自己粘贴的原始输出就是 11 行);`CHANGES.md` 误报定性引用了一个当前并不存在的 `docs/core/` 目录;详细设计+任务节点在**刚把这条教训写进本清单之后立刻又犯两次**且自查没抓到;verify/basic 另记一次同族复发。

  **这条的决定性证据是那次"写完教训立刻复发"**:它证明把盲区写成文字不产生任何防护——自查时人会重读自己刚写下的结论("我已经重跑过了"),而不是重新执行命令。**提醒对这个盲区无效,必须是机器强制。** 同时它的机器化成本是全清单最低的,治理性价比最高。

### 2. "引用只指向不复述"须做控制面原文的字符级重叠检测

- **来自哪个节点的漂移**:跨节点发现(第五、六、七个实例)、抽象设计(一次五处)、R1(起草投影时)
- **soft 执行器下靠什么**:Agent 自觉 + 人工评审逐句比对。`templates/.themis/AGENTS.md` 已记载本规则在模块重构期间被违反四次、三名执行者。
- **hard 执行器该怎么强制**:对新写内容与 `flow.md`/`rules.md`/`template.md`/`README.md` 四份文件做字符串级重叠比对(n-gram 相似度),标出连续重合超过阈值的片段供人工复核。**不能只做"找引号"启发式**——第七个实例证明了该方法的盲区。
- **优先级依据**:**实发 7 次,仅次于第 1 项,且复发形态高度稳定。** 最有说服力的一次是第七个实例:它出现在**记录这条规则历次违规的同一份文件、同一次提交里**,是全新撰写的内容,且此前刚做过"引号复述"专项自查——自查方法只找引号,漏过五处无引号的逐字摘抄,最终由外部评审逐句比对控制面原文才抓出。抽象设计节点改用 `grep -F` 反查控制面原文后,拦截点从"事后评审"提前到"下笔当场",但**下笔那一刻仍然照样先写出了五处违规句**。这说明问题不在自查方法,在"引用一条判据时想顺手说清楚它说了什么"这个写作本能上,人力无法从源头消除。

### 3. 凡声称某项决定来自人类评审者,都必须可追溯到该评审者的逐字原话

- **来自哪个节点的漂移**:详细设计 + 任务(伪造授权链)、人工验收(`a` 补足为 accepted 的冲动)
- **soft 执行器下靠什么**:**无保障。** 靠评审者本人回去读自己的原话逐字比对。
- **hard 执行器该怎么强制**:人类批复的原话入库为不可变记录;工件里每一处"所有者要求/确认/点名 X"必须携带指向该记录的定位,机器做子串比对,追溯不到即拦。**更进一步,人类闸门的授权本身必须取自结构化表决动作,不能从自由文本解析**:只接受受限取值(accepted / 退回),自由文本单独存为理由;结论字段为空即未授权,绝不允许执行体从原话推断补足。「用户原话」小节应由机器从答复通道原样落盘、执行体不可写入。
- **优先级依据**:实发 2 次,按频次排第三。**但这两次与其余各项有本质区别,必须在此写明**:其余强制项防的是"记录不准"(事实错了),这一项防的是"闸门失效"(授权是假的)。两次的形态:(a) 详细设计 + 任务节点把 Agent 自己的推论包装成 R2 评审者的要求——引用格式完全合规("R2 批复第 2 条"),只是批复原话里根本没有那个章节名,静态检查与人工通读都放得过去;(b) 人工验收节点,所有者首条答复是单字母 `a`,只回了残留项选项、不含验收结论,而 `a` 恰好也能读成"同意",控制器的第一反应是补足成 accepted。

  **(b) 的危险性值得单独说**:人工验收是整条流程唯一的授权点,把只表达处置偏好的字母补足成授权,等于流程唯一一次人类授权由 Agent 推出,而它在文本上与真授权完全无法区分——`acceptance.md` 照样会有「用户原话」和 accepted 结论,事后读不出那一步是补的。**这次靠控制器自己按住,不是被任何条款拦住。** 另需记:提问方式本身有份责任,把授权与附带决策合并提问会系统性产出只答一半的回复。

  按本清单的排序规则,它排在第 3;若采用"闸门完整性"排序它会排第 1。两种排法的差异已如实写在此处,由读者权衡。

### 4. 已批准工件的改动清单必须由机器从 diff 生成,粒度也由机器定

- **来自哪个节点的漂移**:impl/detail(同一段文字三次复发)
- **soft 执行器下靠什么**:改动者自行挑选披露哪些段落。
- **hard 执行器该怎么强制**:机器从 diff 生成改动清单,按细到词的粒度切段,再由人逐条标注理由。**粒度必须由机器定,不能由人挑。**
- **优先级依据**:实发 3 次,**且三次都发生在同一段文字上**——`task/review.md`「分类核查」第 5 条那次编辑的改动清单:第一版只凭眼看列两段,跑 diff 后补到四处,第三次按标点切段做逐段机械比对才核出实为八处,且其中一处把整句改写记成了"删去一个限定语"。三次的共同点是**披露范围由改动者自己挑**。最后那一处定性错误尤其说明问题:把整句改写记成删一个限定语,这类记法在事后读起来与"没改过"无异。

### 5. 文件内自洽性:插入新内容必须同时删除被它取代的旧内容

- **来自哪个节点的漂移**:详细设计 + 任务、verify/basic
- **soft 执行器下靠什么**:通读全文自查,以及第三方复核逐块读输出。
- **hard 执行器该怎么强制**:检测同一事实在同一文件内的多处不一致——同一命令块内出现两个输出块且行数不同、同一断言在文件内存在两种数值、题注声称覆盖 N 个对象而实际输出只有 M 个。
- **优先级依据**:实发 2 次,形态一致:**修复的注意力落在"写出正确的新内容",而不是"让文件整体自洽"。** 旧内容在改动点之外,通读时容易跳过;diff 只显示新增行,不会提示"这一块现在多余了";用行替换方式改文件时尤其如此——插入位置正确不等于被它取代的东西已经消失。两次都是靠第三方复核逐块读输出抓到的。与第 1 项同族,但针对的是**文件内自洽性**而非单点正确性:每一处单独看都可能是对的,错的是它们并存。

### 6. 验证身份必须取自派发元数据,不能取自工件文本

- **来自哪个节点的漂移**:verify/basic(身份独立失守)、verify/detail(身份独立成立)
- **soft 执行器下靠什么**:两份工件各自的「执行身份」小节由执行者自行填写,人工比对。
- **hard 执行器该怎么强制**:**修复对象是派发层,不是控制面条款。** 派发时拒绝把验证节点交给已承担对应实现节点的执行体;身份写成执行体不可改写的派发元数据。机器不应去校验两个小节的文字是否不同——那太容易伪造。
- **优先级依据**:实发 2 次,但这两次构成一组**对照实验**,证据强度高于任何单次发生。同一 step、同一套条款、同一批执行者:basic 段两栏明写相同、该条未成立;detail 段两栏不同、成立。**两段之间执行者的自觉程度没有任何变化,变的只有派发怎么分任务。** 两段合起来给出的结论比任一段单独给出的都硬:这道闸门的开合完全由派发层决定,节点侧既没有能力创造第二个身份,也没有能力核实对方那一半是真的。

  **这一条特别标出"不要写成控制面条款"**:本次 replay 已经证明,写在 `rules.md` §7 里的身份独立要求在 basic 段照样失守,因为条款描述了要什么,产生它的机制在控制面之外。把派发层问题写成控制面条款是已被证伪的做法。

### 7. 闸门的"零反馈"类条件必须区分"待回应"与"已批准延后"

- **来自哪个节点的漂移**:R1、R3、抽象设计、R2(同源冲突四次)
- **soft 执行器下靠什么**:人逐案豁免。
- **hard 执行器该怎么强制**:开放项分两类存储,零反馈判据只对"待回应"类生效。更根本的修法是把"评审者在批准时一并给出处置"确立为合法形态,而不是让每个闸门各自与它相撞。
- **优先级依据**:实发 4 次,且**四次指向同一条修法**,是全清单同源复发次数最多的控制面缺口。(a) R1:未解决反馈非空即获批准——R3 有零反馈硬前置,R1 没有同等条款,soft 下无人能拦;(b) R3:零反馈硬前置与所有者自己指定的延后开放项(`catalog.md:33`)直接冲突——计入则永远批不了,不计入又找不到条款支持,**任何带延后事项的实例都会在这道闸门上死锁**;(c) R1 失效波及条款按字面读会让批准被自己随附的收尾修订立刻打回待评审,构成自我矛盾,最终靠控制器裁定绕过;(d) R2 第二次撞上同一处 stale 缺口——所有者在批准时一并要求修改被审工件,`flow.md` 字面同样没为这种情形留例外。四次都不是执行偏离,都是控制面缺口。

  **四次同源意味着这不是零星疏漏,是一处结构缺失**:控制面从未把"评审者在批准的同时一并给出处置"确立为合法形态,而这恰恰是现实中最常见的评审形态。每个闸门都各自与它相撞一次。

### 8. 工件在其所属节点之前产出即拦

- **来自哪个节点的漂移**:抽象设计、R2(facet 1)
- **soft 执行器下靠什么**:**无保障。** 靠人工逐字通读 `flow.md` 比对节点产出清单。
- **hard 执行器该怎么强制**:节点产出清单机器可校验,工件在其所属节点之前产出即拦。
- **优先级依据**:实发 2 次,但值得单列的原因是**漏检链条特别长**:`design.md` 按 `flow.md` 字面归属"详细设计 + 任务"节点,却在"抽象设计"节点内提前产出——起因是 R2 投影需要 Overview,而 Overview 的素材只能来自结构性决定,控制面与任务分解现实之间存在一个"先有鸡还是先有蛋"的循环。**计划作者与前两轮评审都没在产出时抓到,直到执行到 R2 才由所有者当场处置**(处置结论是"接受"——即控制面本身是对的,是从它派生的实施计划把顺序排错了,不必回退返工)。

  另需记:控制面没有条款规定"从控制面派生的计划本身违反节点顺序"该如何收场——打回重做还是事后追认,全靠所有者当场拍板。

### 9. 空段须是机器可识别的一等状态

- **来自哪个节点的漂移**:impl/basic、verify/basic
- **soft 执行器下靠什么**:执行者现场把空段塞进一个为"有改动"设计的状态取值里。
- **hard 执行器该怎么强制**:任务工件条目数为零且判定依据齐备时,实现节点直接记成"已走完、零调用",不逼执行者复用有改动的状态值;验证型节点在空段下须有区别于 passed/failed 的第三种结论取值。
- **优先级依据**:实发 2 次,均为控制面自相矛盾而非执行偏离。`flow.md` 在 impl/basic 节末、impl/detail 前置闸门与失败去向三处都为空段单列了取值,合起来是一条完整的空段路径;但「不构成路径分支」这句又写在 `flow.md`「详细设计 + 任务」节末与 `rules.md` §4 末段,**两边都没有条款指出该以哪边为准**,最终靠控制器裁定(Ruling 18)绕过。verify/basic 另暴露取值重载:该节点结论既非 passed 也非 failed,只能借用"已证",而"已证"在 state.md 里同时表示"本节点已走完"和被误读为"验证通过"。

  **这两处缺口至今未修复。** 下一个空段实例会在同一处停下。

### 10. `spec` 单来源的 claim 应自动标记为待用户确认

- **来自哪个节点的漂移**:Intake、跨节点发现(§1 让一整类目标 claim 只能靠用户确认)
- **soft 执行器下靠什么**:Agent 或评审逐条发现。
- **hard 执行器该怎么强制**:在 Intake / 追问阶段扫描每条 claim 的来源类型,凡唯一来源是 `spec` 类型的,自动标记"需要用户确认"并生成待办追问,不依赖 Agent 主观判断是否问全。
- **优先级依据**:实发 2 次,且暴露的是 `rules.md` §1 的一个结构性推论:"先前设计已决定 X"这类继承性 claim,唯一现成文档背书往往就是 spec 类型,而 §1 把 spec 排除在事实源之外——**这类 claim 结构上只能靠重新问所有者才能取得合法来源**,哪怕决定本身早已写定。这大概是有意的设计(目标语义只认人不认文档),但控制面没有任何一处点明这个推论后果,是执行到 Intake 才撞见的。本次的具体表现:追问第 1 轮四个问题全部是"怎么做"层面,没有一个问到"是否真的要整体删除"本身,而那条恰恰是唯一缺合法来源的 claim,是评审多读了一遍来源引用才发现。

  **hard 化前需先补 `rules.md` §1 的缺口**:要么新增一种"已批准处置记录"的来源类型,要么明确写出这个推论后果。否则机器逐字检查来源类型会把"设计已定但未实现"这类合法意图层 claim 全部拒绝。

### 11. 追问节点应被识别为人工依赖节点

- **来自哪个节点的漂移**:追问
- **soft 执行器下靠什么**:Agent 自律 + "待所有者答复"占位符(本次 replay 的内部约定,非控制面定义)。
- **hard 执行器该怎么强制**:区分 Agent 生成的问题与所有者提供的答案,例如来源 provenance 标记,且该字段不能由同一个 Agent 会话写入才有意义。
- **优先级依据**:实发 1 次,但它是 `flow.md` 总述段与详述段之间的一处不一致:节点序列小节的人工节点总述只数 R1/R2/R3/验收四处,而追问节点要求多轮进行、未获答复不得判收敛,**实质上是第五处人工依赖**,只是没有 R 编号、没有批准/驳回式的显式判定动作,容易被误读为 Agent 可自主推进。本次执行中确实出现两次"想替所有者决定"的冲动(默认写"重写"、自行判断历史证据不用动),均在成稿前改回开放问题。追问节点同时是全清单"没拦住"最集中处(4 处)。
