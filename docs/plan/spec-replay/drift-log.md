# spec 流程端到端 replay 漂移清单

本文件是 `.themis/spec/` 控制面首次端到端 replay 的漂移记录。载体是 `templates/.themis/core/` 删除（spec-id：`core-removal`），但载体本身不是本文件要交付的东西——**本文件才是这次 replay 的真正产品**。

来源计划：`docs/superpowers/plans/2026-08-19-spec-flow-end-to-end-replay.md`（拆分为六个任务，逐任务实施）。

每条固定五项：控制面怎么说 / 实际怎么做的 / 漂移（有/无及形态）/ 控制面拦住了吗 / 给 hard 执行器的启示。"无漂移"同样记录——十三个节点里哪些顺畅、哪些卡顿，对比本身是信息。

条目按走过的节点顺序追加，不回填、不事后合并。

### Intake

- **控制面怎么说**：`flow.md` "## Intake" 节——前置闸门"收到新用户请求"；产出"不可变来源记录；`Intent.md` 的来源引用小节获得初始条目"；用户确认 source-bound claims 之前不得进入任何设计或实现节点。`rules.md` §1——每条 claim 须显式记录 `<类型>#<定位>` 格式来源；按抽象层分层施加事实源要求，具体实现层必须以代码为据；`spec` 在任何层都只作补充，不得作为事实源。
- **实际怎么做的**：真实运行 `find`/`git grep`/`grep` 命令取得 98 个文件、`templates/.themis/` 范围内六处活跃引用、`.gitignore` 一行忽略规则，均以代码来源记入 `Intent.md`。过程中发现两处需要如实记录的偏离：（1）任务书给引用行号标注design.md"行 15 是冲突陈述，行 17 是处置（已定）"，但实际验证结果是第 13 行为冲突陈述、第 15 行才是"处置（已定）"，第 17 行是另一段无关内容；`Intent.md` 已按验证过的第 15 行记录，未按任务书原文照抄错误行号。（2）任务书按 `templates/.themis/` 范围点出"六处活跃引用"，但把 grep 范围放宽到 `docs/**` 后，另发现 36 个文件、396 行历史文档（主要是 Plan 35 的验收/迁移/回放证据记录）同样引用 `core/` 路径，这些不属于"六处"，已作为独立事实记入`Intent.md`"范围与非做"并转成 QA 问题。此外，"设计已定 core 在 spec 落地后删除"这条 claim（design.md:15）目前只找到 spec 来源，找不到代码或 Themico 来源可补充。
- **漂移**：有。主要形态是"规则字面表述与可行来源之间有缺口"——不是我判不动，是 §1 的文字本身对"未来处置决策、只记录在 spec 类文档里"这一类抽象层 claim 没有给出合法来源出路（它不是"当前实现事实"故不强制代码来源，但唯一能证明它的文档恰好是 §1 明文排除的 `spec` 类型）。次要漂移：任务书本身的引用行号有偏差（已用实际验证结果修正，未改写任务书原文，仅在此如实记录）。
- **控制面拦住了吗**：不适用于"spec 来源缺口"一项——`rules.md` §1 定义了拒绝条件，却没有为这类 claim 提供替代来源类型，是规则本身留了空当，不是执行时被绕过。任务书行号偏差与控制面无关（任务书不是 `.themis/spec/` 四份文件之一），不计入本条"控制面拦住"判断。
- **给 hard 执行器的启示**：机器强制若逐字检查"来源类型 ∈ {用户确认, Themico, 代码}"，会把"设计已定但未实现"这类合法意图层 claim 全部拒绝，除非新增一种"已批准处置记录"来源类型（例如"决策#<记录>"）。这是 hard 化前需要先补的 `rules.md` §1 具体缺口，不是执行器实现细节问题。

### 追问

- **控制面怎么说**：`flow.md` "## 追问" 节——前置闸门"Intake 已产出不可变来源"；产出"`QA.md` 追加第 N 轮问答；`Intent.md` 的问题/期望结果/核心链路小节被更新"；多轮进行，收敛判据见 `rules.md` §2。`rules.md` §2——判据是 Why/期望结果/核心链路三者均明确且不存在未回答的问题；判定者是 Agent 提出收敛主张、R1 评审者唯一有权确认收敛。
- **实际怎么做的**：写出四个真实开放问题（覆盖 Why、期望结果两项、核心链路/范围一项），"答"栏一律留"待所有者答复"，不代答；`state.md` 追问闸门记"进行中"而非"已证"，未主张收敛。过程中确实出现两次"想替所有者决定"的冲动：一是写 QA 问 2（六处引用断链后是重写还是整体退场）时，第一反应是直接在 `Intent.md` 写"重写"作为默认方案，因为这样看起来更省事、也更符合"删除应尽量保留可读性"的常识判断——意识到这是在替所有者做产品决策后改写为开放问题；二是写 QA 问 4（`docs/` 历史引用是否处理）时，第一反应是自行判断"历史证据不用动，属于常识"，同样是在替所有者划定范围，随后改为开放问题。
- **漂移**：有，且正是任务书最先点名的那种——追问节点本身停在人身上，却不在 `flow.md` 明文的四处人工节点之列。`flow.md` 写"人工节点固定四处——R1、R2、R3、验收"，但追问节点"多轮进行，未答不得判收敛"的要求实质上要求答案来自项目所有者，Agent 无法自答，因此追问事实上是第五处人工依赖，只是它没有 R 编号、没有"批准/驳回"式的显式判定动作，容易被误读为"Agent 可自主推进的环节"。次要漂移：`QA.md` 的"问/答/来源"三小节内部没有规定行内格式（多问题时是否按编号一一对应、无答复时"答"栏该写什么固定占位符），与 `state.md` 各闸门行格式是同一类缺口——本次以"待所有者答复"作为占位约定，属 replay 内部约定，非控制面定义。
- **控制面拦住了吗**：部分拦住。`flow.md`"未答不得判定为已收敛"这句话本身是有效的闸——它确实拦住了我把"已经问过"当成"已经收敛"，`state.md` 因此如实写"进行中"而非"已证"。拦不住的是"追问算不算人工节点"这一分类缺口：`flow.md` 的"人工节点固定四处"总述没有把追问计入，容易让读者（包括 Agent 自己）先入为主地把追问当成 Agent 独立可完成的环节，直到具体执行时才发现"答"必须来自所有者——这是 `flow.md` 总述段与追问节详述段之间的一处不一致，没有文字提示读者注意。
- **给 hard 执行器的启示**：hard 执行器若要在追问节点强制"不得代答"，必须有机制区分"Agent 生成的问题"与"所有者提供的答案"（例如来源 provenance 标记），否则机器无法判断 `QA.md` 里的"答"是真实所有者输入还是 Agent 自己填的；这个字段还不能由同一个 Agent 会话写入才有意义。目前 soft 执行器全靠 Agent 自律与"待所有者答复"占位符。这正是 `flow.md`"四处人工节点"清单遗漏追问的具体后果：追问若不算正式人工节点，就不会被纳入"人工节点需要机器识别真实人类输入"这一类未来设计考量。
