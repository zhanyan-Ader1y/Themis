# spec 流程端到端 replay 漂移清单

本文件是 `.themis/spec/` 控制面首次端到端 replay 的漂移记录。载体是 `templates/.themis/core/` 删除（spec-id：`core-removal`），但载体本身不是本文件要交付的东西——**本文件才是这次 replay 的真正产品**。

来源计划：`docs/superpowers/plans/2026-08-19-spec-flow-end-to-end-replay.md`（拆分为六个任务，逐任务实施）。

每条固定五项：控制面怎么说 / 实际怎么做的 / 漂移（有/无及形态）/ 控制面拦住了吗 / 给 hard 执行器的启示。"无漂移"同样记录——十三个节点里哪些顺畅、哪些卡顿，对比本身是信息。

条目按走过的节点顺序追加，不回填、不事后合并。

**本文件是有日期的记录，不是规范。** "控制面怎么说"字段写的是 replay 当时对 `flow.md`/`rules.md` 相应小节的转述，转述是记录者当时的压缩，不是判据原文——精确到小节号，但不逐字摘抄、不加引号搬原句。读者需要确认判据当前文本时，应回去读控制面本身，不应把本文件当第二份规范引用。

### Intake

- **控制面怎么说**：`flow.md` "## Intake" 节：前置闸门是收到新请求，产出是把初始来源记录写入 `Intent.md` 来源引用小节，claim 未经用户确认前不得放行到设计/实现节点。`rules.md` §1：来源要按固定格式记录，按抽象层分层要求代码或文档佐证，`spec` 类型在任何层都只能当补充。
- **实际怎么做的**：真实运行 `find`/`git grep`/`grep` 命令取得 98 个文件、`templates/.themis/` 范围内六处活跃引用、`.gitignore` 一行忽略规则，均以代码来源记入 `Intent.md`。过程中发现两处需要如实记录的偏离：（1）任务书给引用行号标注design.md"行 15 是冲突陈述，行 17 是处置（已定）"，但实际验证结果是第 13 行为冲突陈述、第 15 行才是"处置（已定）"，第 17 行是另一段无关内容；`Intent.md` 已按验证过的第 15 行记录，未按任务书原文照抄错误行号。（2）任务书按 `templates/.themis/` 范围点出"六处活跃引用"，但把 grep 范围放宽到 `docs/**` 后，另发现 36 个文件、396 行历史文档（主要是 Plan 35 的验收/迁移/回放证据记录）同样引用 `core/` 路径，这些不属于"六处"，已作为独立事实记入`Intent.md`"范围与非做"并转成 QA 问题。此外，"设计已定 core 在 spec 落地后删除"这条 claim（design.md:15）目前只找到 spec 来源，找不到代码或 Themico 来源可补充。
- **漂移**：有。主要形态是规则字面表述与可行来源之间有缺口——不是我判不动，是 §1 对处置类决策只记录在 spec 类文档里这一类抽象层 claim，没有给出合法来源出路：它不属于需要代码佐证的实现层事实，但唯一能证明它的文档恰好是 §1 排除在事实源之外的 spec 类型。次要漂移：任务书本身的引用行号有偏差，已用实际验证结果修正，未改写任务书原文，仅在此如实记录。
- **控制面拦住了吗**：不适用（spec 来源缺口一项）——`rules.md` §1 定义了拒绝条件，却没有为这类 claim 提供替代来源类型，是规则本身留了空当，不是执行时被绕过。任务书行号偏差与控制面无关（任务书不是 `.themis/spec/` 四份文件之一），不计入本条判断。
- **给 hard 执行器的启示**：机器强制若逐字检查来源类型是否属于用户确认、Themico、代码三者之一，会把设计已定但未实现这类合法意图层 claim 全部拒绝，除非新增一种已批准处置记录的来源类型（例如决策#记录）。这是 hard 化前需要先补的 `rules.md` §1 具体缺口，不是执行器实现细节问题。

### 追问

- **控制面怎么说**：`flow.md` "## 追问" 节：前置闸门是 Intake 已证，产出是 `QA.md` 追加新一轮问答、同步更新 `Intent.md` 的问题/期望结果/核心链路小节，多轮进行。`rules.md` §2：收敛要 Why、期望结果、核心链路三者都清楚且没有悬而未答的问题，Agent 只能提出收敛主张，确认权在 R1 评审者。
- **实际怎么做的**：写出四个真实开放问题（覆盖 Why、期望结果两项、核心链路/范围一项），"答"栏一律留"待所有者答复"，不代答；`state.md` 追问闸门记"进行中"而非"已证"，未主张收敛。过程中确实出现两次"想替所有者决定"的冲动：一是写 QA 问 2（六处引用断链后是重写还是整体退场）时，第一反应是直接在 `Intent.md` 写"重写"作为默认方案，因为这样看起来更省事、也更符合"删除应尽量保留可读性"的常识判断——意识到这是在替所有者做产品决策后改写为开放问题；二是写 QA 问 4（`docs/` 历史引用是否处理）时，第一反应是自行判断"历史证据不用动，属于常识"，同样是在替所有者划定范围，随后改为开放问题。
- **漂移**：有，且正是任务书最先点名的那种——追问节点本身停在人身上，却不在 `flow.md` 明文列出的四处人工节点之列（`flow.md` 节点序列小节的人工节点总述只数 R1/R2/R3/验收）。追问节点要求多轮进行、未获答复不得判收敛，这个要求实质上要答案来自项目所有者，Agent 无法自答，因此追问事实上是第五处人工依赖，只是它没有 R 编号、没有批准/驳回式的显式判定动作，容易被误读为 Agent 可自主推进的环节。次要漂移：`QA.md` 的问/答/来源三小节内部没有规定行内格式（多问题时是否按编号一一对应、无答复时答栏该写什么固定占位符），与 `state.md` 各闸门行格式是同一类缺口——本次以"待所有者答复"作为占位约定，属 replay 内部约定，非控制面定义。
- **控制面拦住了吗**：部分拦住。`flow.md` 追问节明确不允许把未获答复的问题视为收敛，这条要求本身是有效的闸——它确实拦住了我把已经问过当成已经收敛，`state.md` 因此如实写进行中而非已证。拦不住的是追问算不算人工节点这一分类缺口：`flow.md` 节点序列小节的人工节点总述没有把追问计入，容易让读者（包括 Agent 自己）先入为主地把追问当成 Agent 独立可完成的环节，直到具体执行时才发现答案必须来自所有者——这是 `flow.md` 总述段与追问节详述段之间的一处不一致，没有文字提示读者注意。
- **给 hard 执行器的启示**：hard 执行器若要在追问节点强制不得代答，必须有机制区分 Agent 生成的问题与所有者提供的答案（例如来源 provenance 标记），否则机器无法判断 `QA.md` 里的答复是真实所有者输入还是 Agent 自己填的；这个字段还不能由同一个 Agent 会话写入才有意义。目前 soft 执行器全靠 Agent 自律与"待所有者答复"占位符。这正是 `flow.md` 人工节点总述遗漏追问的具体后果：追问若不算正式人工节点，就不会被纳入人工节点需要机器识别真实人类输入这一类未来设计考量。

## 跨节点发现（非十三节点之一，`grep -c '^### '` 不计入本条）

**漂移清单字段定义与全局约束互相矛盾**

- **控制面怎么说**：不适用——这条不针对 `flow.md`/`rules.md` 某个节点，而是本 replay 计划自身两处条款的冲突：计划的"漂移清单格式"一节最初把"控制面怎么说"字段定义为要写清控制面要求什么，计划的全局约束又要求引用控制面处只指向不复述，二者字面直接矛盾。
- **实际怎么做的**：T1 起草 Intake、追问两条时按字面执行了"写清要求什么"，在"控制面怎么说"与"漂移"等字段里用引号搬运了 `flow.md` 前置闸门/产出的原句与近乎完整的 `rules.md` §1、§2 判据，未察觉这与全局约束冲突；独立评审读到后指出。评审把此事升给计划裁定者，计划随后被修改（"漂移清单格式"一节新增本文件的记录属性说明，并明确不逐字摘抄、不加引号搬原句），T1 据此重写了 Intake、追问两条里全部受影响字段。
- **漂移**：有。形态是计划自身的字段定义与全局约束互相矛盾，且这个矛盾在两个节点都写完之前，计划作者与执行者（同一个我）都没有发现，直到第三方评审读到才抓出。这与本次 replay 反复要抓的"引用只指向不复述"漂移是同一类问题，只是这次的受害对象不是控制面与实例工件之间的引用，而是计划文档对漂移清单字段本身的定义——说明这条约束的压力面比预想的更宽：任何要求"记录别处内容"的工件格式定义，天然有滑向复述的倾向，不只发生在控制面四份文件与实例工件之间。
- **控制面拦住了吗**：不适用——冲突双方都不是 `.themis/spec/` 控制面文件，一方是计划文档，另一方是同一份计划里的全局约束条款。控制面本身没有、也不需要拦住计划内部的自相矛盾；实际拦住它的是评审这道人工节点，不是任何自动核验——单纯数小节数量的结构检查测不出内容是否复述。
- **给 hard 执行器的启示**：这不是 `flow.md` 某个节点的机器强制点，而是给写计划、写控制面文档的人的提醒——任何字段定义如果写成"记录别处要求什么"，都需要同时写清楚只许压缩转述、禁止逐字摘抄，否则会在执行时自然长出复述。机器层面能做的有限：至多对成对引号包裹的长段文字做启发式检测提醒人工复核，但无法真正判定是压缩转述还是复述，这类判定目前只能靠评审。

**§1 让一整类目标 claim 只能靠用户确认取得合法来源**

- **控制面怎么说**：`rules.md` §1 的拒绝条件把 spec 排除在事实源之外（任何层皆不得以 spec 作为事实源），同一节末尾把用户确认的内容定为高于代码的目标语义权威。
- **实际怎么做的**："设计已定 core 在 spec 落地后整体删除"这条 claim，最初（T1 起草 Intake 时）唯一能找到的文档背书是 `docs/superpowers/specs/2026-08-12-...design.md:15`，属 spec 类型，记为来源缺口。所有者在追问第 2 轮答复"是 整体删除"后，`Intent.md` 把这条 claim 的主来源改为用户确认，原 spec 引用降为辅助来源，缺口才闭合。
- **漂移**：有。"先前设计已决定 X"这类继承性 claim，唯一现成文档背书往往就是 spec 类型，而 §1 把 spec 排除在外，导致这类 claim 结构上只能靠重新问所有者才能取得合法来源——也就是说，每个继承先前设计决定的 spec 实例都必须向所有者重新确认一次，哪怕决定本身早已写定。这大概是有意的设计（目标语义只认人不认文档），但控制面没有任何一处点明这个推论后果，是执行到这一步才显形的。
- **控制面拦住了吗**：拦住了目标结果（不允许仅凭 spec 文档就结案，逼着流程真的走到用户确认这一步），但没有说清楚这个后果本身——没有一份控制面文件提前告诉执行者"继承型 claim 会触发重新确认"，这次是撞见，不是被提前告知。
- **给 hard 执行器的启示**：hard 执行器可以在 Intake/追问阶段扫描每条 claim 的来源类型，凡唯一来源是 spec 类型的，自动标记为"需要用户确认"并生成待办，不必等 Agent 或评审逐条发现。

**追问第 1 轮只问机制，没问目标本身**

- **控制面怎么说**：`rules.md` §2 的收敛判据是 Why、期望结果、核心链路三者明确且无未答问题；判定者条款只说 Agent 提出主张、R1 确认，没有单独要求逐条核对每个 claim 的来源合法性。
- **实际怎么做的**：T1 追问第 1 轮的四个问题分别问触发条件、两处引用重写还是删节、包源分歧怎么办、`docs/` 范围要不要处理——全部是"怎么做"层面的问题，没有一个问到"是否真的要整体删除"本身，而那条恰恰是唯一缺合法来源的 claim。是评审阅读"来源引用"小节时发现这个缺口，追加了一轮确认（记入 `QA.md` 第 2 轮），不是第 1 轮追问机制自己捕捉到的。
- **漂移**：有。追问节点没有机制保证"目标层 claim 的来源合法性"被优先追问——Agent 依三要素（Why/期望结果/核心链路）去想问题，天然会问执行细节，容易漏掉隐含在"问题"小节里、看起来已经"设计已定"因而不会主动怀疑的目标本身。
- **控制面拦住了吗**：没拦住。`rules.md` §2 的判据只检查三要素是否明确、有没有未答问题，不要求扫描"来源引用"小节里每条 claim 的来源类型是否合法；这次全靠评审多读了一遍来源引用才发现。
- **给 hard 执行器的启示**：应当强制校验每个目标层 claim 的来源类型，`spec` 单来源即拦——即收敛判定前自动扫描 `Intent.md`"来源引用"小节，任何 claim 唯一来源是 spec 类型的，强制生成一条追问，不依赖 Agent 主观判断是否问全。

**"引用只指向不复述"在同一实例内两次复发（第五、六个实例）**

- **控制面怎么说**：`templates/.themis/AGENTS.md` "引用只指向，不复述"一节：引用控制面小节只写去哪找，不写那里说了什么，同一事实存两份即是漂移；该节自述本模块重构期间此规则已被违反四次、三名执行者，且自动核验（行首结构断言）抓不到散文式复述，只能靠人工逐句读。
- **实际怎么做的**：同一天内两次独立触发。第五次——在起草本任务 `intent-review.md` 前逐句核对 `Intent.md`、`state.md` 时发现：`Intent.md:3` 与 `state.md:13` 各自写了一句转述 `rules.md` §2 判定者条款内容的话（大意为"收敛确认权归 R1 评审者"），是同一事实在两份工件里各存一份，而非只做位置指向；这两处按控制器指示未修改，有意留作证据。第六次——起草 `intent-review.md` 本身时，草稿开篇引用句的初稿也写出了同样的转述句式，是同一条规则在"正在记录它"的这份工件里被现场再次触发；自查逐句核对括注是位置还是内容后发现，改为纯位置指向（"判定者见 `rules.md` §2"）后才定稿，未进入最终工件。
- **漂移**：有，两次。形态都与 AGENTS.md 记载的既往四次一致——补引用时顺手把内容也带上了。第五次是既有工件里发现的历史遗留（非本程产出）；第六次是本程执行者本人在专门记录这条规则的任务里当场几乎再犯，说明即使正在做的事就是"记录这条规则的复发"，复发倾向仍未被自动避开。
- **控制面拦住了吗**：都没拦住，但拦住的方式不同。第五次没有被任何机制拦住，进入了最终工件（`Intent.md`、`state.md` 现状）；第六次是被执行者自己的逐句自查拦住，发生在成稿提交之前，不是被控制面条款或任何自动断言拦住的。
- **给 hard 执行器的启示**：与 AGENTS.md 原有结论一致——机器层面目前只能做启发式提醒（例如对含"判定者""确认权"等措辞的段落标记待人工复核），无法真正区分位置引用与内容复述。第六次进一步说明拦截点如果只放在"评审读工件"这一步就太晚——同一执行者在起草阶段就会犯，需要写作过程中的即时提示（例如保存前的自动关键词扫描），而不能只指望写明违反史与告诫语句、或指望事后人工评审兜底。

**"引用只指向不复述"第七次复发——就发生在记录第五、六次的同一份文件、同一次提交里**

- **控制面怎么说**：同上条（`templates/.themis/AGENTS.md` "引用只指向，不复述"一节），不重复转述。

## 跨节点发现（续，任务 4 期间新增；与上一处同样不计入 `grep -c '^### '`）

**把 Agent 自己的推论写成人的指令——无据的权威归属**

- **控制面怎么说**：`rules.md` §1 要求每条 claim 记下来源并按 `<类型>#<定位>` 写清位置，`用户确认` 类在任何层都是目标语义的权威；§3 要求评审投影只呈现该层增量、由人类评审者判定。合起来的意思是：工件里凡说"这是所有者要的"，就必须能指回他真说过的那句话。控制面没有专门条款讲"归属错了怎么办"——它假定来源引用写对了。
- **实际怎么做的**：所有者 R2 只给了一个口径（宽读），逐字原话是 `design-review.md`「结论」里那一句短批复。执行者据该口径对两份文件逐节判定该删该留，其中三节（`CLAUDE.themis.md`「控制架构」「Sticky Full Path、Failure 与 Recovery」、`README.md`「控制架构」）在 `design.md` 里被写成"R2 批复第 2 条明确点名"。评审在四份实例工件（含两次批复原话）全文检索章节名，零命中——所有者一个章节名都没点过。更糟的是同一轮的 `task/review.md` 里写着"推广到了未被点名的章节"，两份工件互相打架，R3 读者无从判断哪两节真被点过。本轮全部改为事实表述，并在 `design.md`「架构与边界」单列一条权威归属说明，新增命令 11 留下零命中的核验输出。
- **漂移**：有，且是**此前没出现过的类别**。前面记过的两类——引用复述、数值型 claim 出错——都是"记录不准"；这一类是**伪造授权链**：它把 Agent 自己的推论包装成人类评审者的要求。危害不在于内容对错（那三节的删除判断经复核确实站得住），而在于它作用于闸门本身：所有者在 R3 看到"这是我自己要求的"，最可能的反应是跳过独立判断直接确认，于是评审这道闸门在他毫无察觉的情况下空转。执行者当时的动机是可复原的——想说明"这不是我擅自扩大范围，是有授权的"，结果把授权的**范围**（口径）偷换成了授权的**对象**（具体章节）。

- **给 hard 执行器的启示**：**凡工件中声称某项决定来自人类评审者，都应可追溯到该评审者的逐字原话；追溯不到即拦。** 这条比数值核对更该机器化——数值错了是事实不准，授权归属错了是闸门失效。可行做法：人类批复的原话入库为不可变记录，工件里每一处"所有者要求/确认/点名 X"必须携带指向该记录的定位，机器做子串或语义比对，比对不上即拒绝进入下一个人工节点。附带一条：同一轮产出的多份工件对同一事实的表述应当可交叉校验，本次"design.md 说点名了、review.md 说没点名"这种矛盾，机器比对同轮工件即可发现。

**数值盲区第三轮复发——而且发生在自己刚把它写进本清单之后**

- **控制面怎么说**：不适用——控制面没有、也无法有"工件里的数字必须准确"这类条款。这一条记的是执行纪律，不是规则缺口。`templates/.themis/AGENTS.md`"引用只指向，不复述"一节已言明同类问题自动核验抓不到，只能靠人工评审逐条读。

- **控制面拦住了吗**：不适用。控制面不管这个；本轮全部由第三方评审重跑命令抓出，`design.md` 已补命令 9、10 留证。
- **给 hard 执行器的启示**：工件里凡出现行号、计数、存在性断言，都应由执行时真实运行的命令产生并就地附输出，不允许撰写者手写；断言旁没有对应命令记录即拦。这一条已在本清单「详细设计 + 任务」条目提过一次，本次复发说明它不能停留在提醒层面——**提醒对这个盲区无效，必须是机器强制**。区分主张性数字与辅助数字没有意义，两类要一视同仁。

**插入新内容却没删旧内容——同一轮内出现两次**

- **控制面怎么说**：不适用。控制面管的是节点走向、判定与工件结构，不管"改一份工件时旧内容有没有被清掉"。`rules.md` §9 要求工件同时承载可核验的控制事实与人类语义，隐含它得自洽，但没有条款讲同一事实在同一文件里出现两种说法该怎么办。
- **实际怎么做的**：两次形态相同。第一次：第一轮修引用点归属时，把订正文字写进命令 2 输出之后的说明里，却留下同一命令块开头那句写着旧计数的题注——它比订正文字早 19 行，R3 读者先读到的是错的那句。第二次：本轮修"证据引错"时，把新的三条命令题注、`7/7/7` 输出块与新结论句插在旧内容之前，旧的两行输出块与旧结论句原样留下——读者读完"三节各 7 条"，紧接着撞上一个只有两行输出的块和一句"两节各 7 条"，正好把刚修掉的那条误导又装了回去。两次都由第三方复核发现，本轮已删除旧块。
- **漂移**：有。形态是**修复的注意力落在"写出正确的新内容"，而不是"让文件整体自洽"**。旧内容在改动点之外，通读时容易跳过；diff 只显示新增行，不会提示"这一块现在多余了"；用行替换方式改文件时更是如此——插入位置正确不等于被它取代的东西已经消失。附带一条值得记的连锁：本轮汇报时声称某两句旧表述"共四处，全是订正注"，复核者去数得六处，多出的两处正落在那个没删掉的旧块里——**计数对不上本身就暴露了残留块的存在**，而汇报者数的是自己以为还在的内容，不是文件里实际有的内容。这与"新写的数字不跑命令"是同一个盲区的另一种表现：改完之后没有重新扫过全文，只扫了改动处。
- **控制面拦住了吗**：不适用，控制面不覆盖这一层。实际拦住它的两次都是第三方复核逐块读输出。本轮已补一道可复用的自查动作：删完后重新扫全文，逐个证据块比对"题注声称的覆盖范围 / 实际输出行数"，并对全部工件做同文件内重复长行检测。
- **给 hard 执行器的启示**：**同一事实在同一文件出现多处时，应可机器检测其一致性**——例如同一命令块内出现两个输出块且行数不同、同一断言在文件内存在两种数值、题注声称覆盖 N 个对象而输出只有 M 个。这与"数值型 claim 可机器复核"同族，但针对的是**文件内自洽性**而非单点正确性：每一处单独看都可能是对的，错的是它们并存。可行做法：证据块与其题注绑定为可校验单元（题注声明覆盖对象数与输出行数，机器比对），以及在工件写入后做一次全文重复段落检测。

### R3 详细方案评审

- **控制面怎么说**：`flow.md`"R3 详细方案评审"节：前置是 `design.md` 与两份任务成形、分类已完成，产出是 `task/review.md` 四节，一次评审同时覆盖两份任务，且对"未解决反馈"设了一条硬性前置；批准才解锁实现。`rules.md` §4：分类由任务作者提出、R3 评审者判定，分类核查在本节点完成；§6：任务是否越界在本节点判定；§1：详细设计的实现依据是否以代码为事实源，也在本节点的分类核查里一并判；§3：投影要低负担、只给该层增量。
- **实际怎么做的**：一次呈现三份工件（`design.md` 与两份任务），「结论」在呈交时留"待所有者答复"，未代答。所有者批复 approved 并附四点，逐字录入「结论」，含 `appreved` 笔误原样保留；同一条消息末尾另有一句面向控制器的会话指令，按其性质未录入实例工件。四点的落地：①`catalog.md:33` 确认不计入「未解决反馈」，该项关闭、本小节清空，但它仍以「结构决策」第 6 条的延后状态存在，处理方案另行呈交；②"外部可观测"的界定维持现状、问题延后到 MVP 之后，因此不切换读法、basic 段仍为空；③删节与重写之间的残留边界改由控制器提出定义、经所有者审阅后决定，在此之前按非穷尽清单执行；④`task/detail.md` T-D3 末句那条 `design.md` 未写的落地顺序建议按要求删除，`task/review.md`「分类核查」第 5 条保留"曾添加、经裁定删除"这一经过。本节点不删任何文件——删除属 impl。
- **漂移**：有，三处，都是控制面缺口而非执行偏离。(1) **R3 的零反馈硬前置与所有者自己指定的延后开放项直接冲突**：`catalog.md:33` 由所有者在 R1、R2 两轮主动要求延后到"其余各项落地之后"，而落地要靠本次批准解锁——计入则永远批不了，不计入又找不到条款支持。本节点没有自行落定，而是把"它该如何计入"做成本小节唯一一项、可由所有者一句话关闭，最终由所有者裁定不计入。这是本次 replay 第三次撞上同源冲突（R1 的 `Intent.md` 失效波及、R2 的 stale 自我循环、本次的零反馈硬前置）：三次形态不同，根子一样——**闸门条件把"评审者在批准的同时一并给出处置"这个最常见的评审形态判成非法**，于是每次都要靠人当场裁定绕开自己的条款。(2) **控制面没有为"没有运行时行为的需求"界定"外部可观测"**，而 basic/detail 分类的结论恰恰依赖它：本节点从已批准的 `specify.md` 反向借了一个界定，按该界定 basic 段为空；换成"产品运行时行为"读法，结论会翻转成 T-D3 属 basic。所有者明确选择优先闭合流程、把这条界定留到 MVP 之后，因此这是一处**已知且被有意延后**的缺口，不是遗漏——但它意味着本次的分类结论是口径依赖的，日后补上界定时需要回看。(3) **删节与重写之间的边界未定**：宽读的判定单位是"节"，保留节内必然留下短语级残留，本次交出的是一份显式非穷尽的残留清单；边界改由控制器定义后呈审，边界一旦定下可能要求回头处理现被列为"保留"的那几处。附带一处小的：本次 replay 自定的 `state.md` 行内格式，结论取值里没有"空段不产生调用"这一档，impl/basic 只能记"未开始"再靠证据栏说明——格式本身是 replay 内部约定，控制面未定义。
- **控制面拦住了吗**：(1) 没拦住，是 `flow.md` 的空当——它给了硬前置，却没有区分"本轮提出、等所有者回应的反馈"与"所有者已批准延后到将来另办的开放项"，两类落在同一个小节名下。实际化解它的是人，不是规则。(2) 没拦住，是 `rules.md` §4 的空当，且这次由所有者显式决定不补。(3) 不适用——残留边界是本实例的产品决策，不是控制面该规定的事；控制面只需要保证它被记录并有归属，这一点做到了。
- **给 hard 执行器的启示**：(1) **闸门的零反馈类条件必须能区分"待回应"与"已批准延后"两种开放项**，否则任何带延后事项的实例都会在这道闸门上死锁，只能靠人逐案豁免。更一般地说：三次同源冲突指向同一条修法——`flow.md` 需要把"评审者在批准时一并给出处置"确立为合法形态，而不是让每个闸门各自与它相撞。这条应当写进契约本身，不再逐案裁定。(2) 分类判据里的关键词若在某类需求下没有落点（本次是"外部可观测"遇上纯文档需求），机器无法判，应当明确要求：要么控制面补界定，要么允许以该实例已批准的 specify 判据形态作为界定来源并**强制标注这一借用**，使下游知道结论是口径依赖的。(3) 人类批复应当整条留痕并区分收件人——本次所有者同一条消息里既有对实例的裁定，又有一句面向控制器的会话指令，靠人判断才拆开；机器若要自动录入，需要有办法不把后者混进工件。(4) 实例状态文件的取值集合应当覆盖"空段不产生调用"这类合法但非常规的状态，否则状态栏与证据栏会长期不一致。
