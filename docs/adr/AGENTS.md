# `docs/adr` 目录规范

本目录保存**已确定的重要决策记录**（ADR，Architecture Decision Record）。

它回答的是"**当初为什么这么定、为什么没选另一个**"——这件事在别处都不记：设计约束（`docs/design/`）记的是"不能怎么做"，流程契约（`.themis/spec/`）记的是"现在能不能走下一步"，计划（`docs/plan/`）记的是"在做什么"。**没有一处记决策的取舍过程**，而取舍恰恰是后来者最需要、也最容易失传的部分。

## 什么该写进来

**同时满足三条才写**：

1. **已确定**——已获项目所有者裁定或批准。悬而未决的不写，那属于 spec 实例的追问或评审工件。
2. **重要**——推翻它需要付出可观代价：已有代码依赖它、已有多份文档按它写、或它改变了某个模块的边界。
3. **有真实备选**——当时确实存在另一条路，且那条路不是明显更差。**只有一条路可走的事不是决策**，是事实，写进设计约束或流程契约即可。

**不写**：日常实现选择、可随时改回的措辞调整、以及任何尚未落地的设想。

## 每条 ADR 必须回答三个问题

| 问题 | 要求 |
| --- | --- |
| **对应什么功能** | 这个决策管的是哪一块——模块、流程节点、或某项能力。要具体到读者能定位。 |
| **做了什么决策** | 一句话说清定了什么。不写过程，只写结论。 |
| **为什么选它、不选其他** | **本目录存在的理由，也是最容易被写空的一节。** 必须列出当时真实考虑过的备选项，逐个说明为什么没选。**"其他方案更差"不是理由**，要写清差在哪、代价是什么。 |

**第三个问题的写法要求**：

- **备选项要照实写**，包括那些当时看起来也合理的。事后看显然错的备选项没有记录价值，读者不会想推翻它们。
- **理由要能被检验**——引用实测数据、已发生的问题、或与某条现有约束的冲突。**不写"更简洁""更清晰"这类无法核对的评价。**
- **若决策依据的是一次实测，写明那次实测**：跑了什么、得到什么、因此排除了哪条路。

## 文件命名与结构

一条决策一个文件：`NNNN-<短横线连接的主题>.md`，`NNNN` 从 `0001` 起顺序编号，**编号一经分配不复用**，即便该决策后来被推翻。

每份文件的固定小节：

```markdown
# NNNN. <决策标题>

- **日期**：YYYY-MM-DD
- **状态**：已生效 / 已被 NNNN 取代
- **裁定人**：谁批准的

## 对应功能
## 决策
## 为什么选它，不选其他
## 已知代价
```

**「已知代价」不可省略**——每个决策都有代价，写不出代价说明备选项没想清楚。

## 决策被推翻时

**不删除、不改写原文**。新写一条 ADR 说明新决策，并把旧那条的「状态」改为 `已被 NNNN 取代`。

理由与本项目对历史记录的一贯处置相同：原文记的是当时依据什么判断，改写它会把证据改成结论。**读者需要看到决策是如何演变的**，而不只是最终结果。
