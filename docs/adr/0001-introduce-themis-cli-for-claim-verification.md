# 0001. 引入 themis Go CLI 校验数字与存在性断言

- **日期**：2026-08-27
- **状态**：已生效
- **裁定人**：项目所有者（zhanyan）

## 对应功能

工件中**数字与存在性断言的准确性校验**——例如"该文件 116 行"、"命中 5 处"、"该目录不存在"这类写进 spec 流程工件的断言。

不涉及流程闸门、评审授权或其他环节的强制；那些仍由 Agent 遵守条款。

## 决策

**引入 `themis` Go CLI**，读取工件中结构化记录的「命令 + 断言值」对，提交前逐条重跑命令、比对真实输出与写下的值，**不一致即拒绝**。

三项配套裁定：

- **逐条比对数值**，不只检查"是否附了命令"。
- **全部数字一视同仁**，不按"主张性/辅助性"或小节位置区分。
- **分两步走**：先定断言的结构化形态并验收，再写 CLI。

## 为什么选它，不选其他

**当时有三条路，两条被排除。**

### 备选一：写一条提醒式条款（排除）

这是本项目此前三个需求一贯的做法——往 `.themis/spec/rules.md` 补一条判据，靠 Agent 遵守、下游角色核查。

**排除依据是一次实测，不是推断。** `docs/plan/spec-replay/drift-log.md` 第 139 行记载：执行者**刚把"新写的数字不跑命令"这条教训写进清单，同一形态立刻又犯了两次，且自查没抓到**。同处写明了失效机制：

> 自查时人会去重读自己刚写的结论（"我已经重跑过了"），而不是重新执行命令。

该条据此断言"**提醒对这个盲区无效，必须是机器强制**"。**补条款这条路已被本项目自己的实测证伪。**

### 备选二：写作形态约束 —— 要求数字与命令输出相邻成对（排除）

不引入工具，改为要求"数字必须与产生它的命令输出相邻出现"，赌注是"错值不可检出，但缺失可检出"——没跑的人写不出那个输出。

**排除依据也是实测反例**：某次执行者**在同一文件紧邻处粘贴了原始输出（11 行），结论里却写了 10**。命令在、输出也在，数字仍然错。**该形态只覆盖"根本没跑"，覆盖不了"跑了但抄错"**，而后者在已知实发中占相当比例。

### 选定：机器强制

它是三条中**唯一能拦住而不只是发现**的。同一份记录里另有一句常被忽略的事实：

> 真正抓到它的仍然是第三方评审重跑命令。

第三方重跑确实有效——13 次以上的实发全是这么发现的。**但"发现"发生在事后，且依赖第三方真的重跑而不是读。** 机器强制把发现点前移到提交前，且不依赖任何人的自觉。

### 与设计约束的关系

`docs/design/themis-design.md` 约束 1 规定"**只有在不可避免的情况下才引入 Go CLI 实现功能**"，判断标准是"该功能必须由机器执行才成立"。

本决策按该标准过检：靠条款 + 下游角色核查**只能发现、不能拦住**（上述两条备选各自的排除依据即证）。**满足"不可避免"。**

### 为什么分两步而非一次做完

格式（断言在工件中怎么记）与程序（读格式、重跑、比对）拆开做，理由有二：**格式一旦定错，程序全部白写**——程序读的就是那个格式；且两者验收方式不同——格式靠读条款判、程序靠跑测试判，合在一次验收里会互相干扰。分两步则前一步的验收正好成为后一步的输入契约。

## 已知代价

1. **这是本项目第一次给 Themis 写代码。** 此前所有需求只改 Markdown。引入后就有了编译、测试与长期维护成本，且每次改断言形态都要同步改代码。
2. **拦得住不等于用得上**——CLI 能拦住写错的数字，但拦不住"绕过 CLI 直接提交"。本决策不解决这一点。
3. **只覆盖数字与存在性断言这一块**，不做整份流程契约的机器强制；其余环节仍靠 Agent 遵守。
4. **`SPEC-ENFORCE-003` 要求 CLI 缺席时不得阻塞流程**，须自动降级回 soft——这意味着校验可以被"CLI 不可用"绕过，该降级路径本身是必须的（否则 CLI 故障会卡死整个流程），但它同时是一条天然的绕过通道。
