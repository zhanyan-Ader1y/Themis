# Themis 设计约束

本文件记录**设计 Themis 时必须遵守的约束**，以及每条约束的由来。

它回答的是"设计时不能怎么做、为什么"，不回答"流程怎么走"（那在 `.themis/spec/`）、也不回答"当前在做什么"（那在 `docs/plan/`）。

**每条约束都附解释。** 只列条文不列理由的约束，会在下一次有人觉得"这次情况不同"时被绕过——理由才是它真正的约束力所在。约束来自实际发生过的问题时，解释里写明那次问题。

## 约束

| # | 约束 | 解释 |
| --- | --- | --- |
| 1 | **只有在不可避免的情况下才引入 Go CLI 实现功能** | Go CLI 是本项目唯一的机器强制手段，也是唯一需要编译、测试、维护的部分。每引入一处 CLI 功能，就把一件原本靠 Markdown 契约与人类判断解决的事，变成需要长期维护的代码。**判断"不可避免"的标准**：该功能必须由机器执行才成立——例如提交前重跑命令并精确比对、拒绝不合规提交。凡靠条款约束 + 下游角色核查能达成的，不引入 CLI。 |
| 2 | **默认用自然语言 Markdown 描述产品语义、流程、状态、合同、模板与示例** | Markdown 是人与 Agent 共同可读可改的唯一形态。结构化格式一旦引入，就产生"谁是权威"的问题。 |
| 3 | **只有内容确实需要由 Go CLI 解析或执行时才允许使用 YAML** | YAML 必须对应明确的 Go 读取入口和执行用途，不能仅为结构化展示而存在；没有 CLI 消费者的 YAML 是需要迁移到 Markdown 的设计债务。**审查既有设计时不得因为 YAML 已存在就默认其合理。** |
| 4 | **不使用 Python；需要自动执行的脚本必须由 Themis Go CLI 提供** | 临时脚本会绕过约束 1 的判断——它让"引入执行能力"变得太容易，且不进入任何契约。CLI 能力尚未实现时应明确标记 unavailable，不得用 Python、Shell 或其他临时脚本替代。 |
| 5 | **不引入版本概念，不出现版本形式的目录** | 版本目录会让"当前哪份是权威"变成需要判断的问题，而本项目的核心是单一权威。 |
| 6 | **不需要 upgrade 与 migration** | 同上——有版本才需要迁移。不设版本即无迁移。 |
| 7 | **不得用 Prompt、README、template、policy 或 directory 的存在冒充机器强制** | **这条来自实测**：`docs/plan/spec-replay/drift-log.md` 记载，执行者刚把一条教训写进清单，同一形态立刻又犯两次且自查没抓到——"自查时人会重读自己刚写的结论，而不是重新执行命令"。**文字不产生强制力**。当前强制水平见 `.themis/spec/README.md`；任何文本不得声称闸门已由机器执行。 |
| 8 | **所有 Markdown 内容使用中文呈现** | 保留 `themis-*` identity、status、capability 等闭合词汇与代码标识符的英文原文。 |
| 9 | **WIKI 类文件不记录任务状态** | 状态属于实例（`.themis/workspace/spec/<spec-id>/state.md`），写进说明性文档就会与实例状态各说一套。 |

## 与其他文件的分界

| 问题 | 去哪找 |
| --- | --- |
| 设计时不能怎么做、为什么 | **本文件** |
| 流程现在能不能走到下一步 | `.themis/spec/flow.md` |
| 某条判据是否满足、谁有权判 | `.themis/spec/rules.md` |
| 工件长什么样、放在哪 | `.themis/spec/template.md` |
| 当前在做什么、下一步做什么 | `docs/plan/README.md` |
| 跨模块的仓库约定 | 仓库根 `AGENTS.md` |

本文件**不重复**上述各处的内容，只写设计约束本身。
