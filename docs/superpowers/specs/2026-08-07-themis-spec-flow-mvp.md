## 1. 范围与非目标

**范围:** Themis spec 流程运行时"系统必须表现为什么"的外部行为契约。契约**执行器无关(enforcer-agnostic)**:默认由 soft（软约束)执行器实现,未来可由 hard（硬约束,Go CLI）执行器实现同一契约。

**非目标(本 specify 不涉及,属后续阶段或其他模块):**
- Themico（知识库)的任何概念(knowledge_type、Zone、L1/L2/L3)。
- 失败次数预算、失败→经验学习(属 Themico)。
- **simple/full 路径区分**:Themis 不设简易/完整之分,流程是唯一单一路径,且**不为任何未来的双路径做预留、开关或切换**。(注:此与 §I 的 soft/hard 执行器无关——后者是执行机制演进,保留。)
- hard 执行器(Go CLI)的具体实现细节(行为契约在此,实现在后)。

## 2. 系统必须表现为什么(行为契约)

每条为 `SPEC-<主题>-<序号>`,含 EARS 句式与可验证验收判据(AC)。

### A. Intake（受理)与需求确认

**SPEC-INTAKE-001** — 当收到新用户请求时,系统必须先将其保存为不可变来源,并在用户确认 source-bound（来源绑定)claims（诉求)之前,不得进入任何设计或实现节点。
- AC1:未确认 claims 时尝试进入抽象设计 → 系统拒绝,停在需求确认。
- AC2:原始请求以不可变形式留存,可回溯。

**SPEC-INTAKE-002** — 每个进入 current-request（当前请求)的 claim（诉求)必须**显式记录来源引用并写入工件文件**,采用 `<类型>#<定位>` 形式,例如 `用户确认#<内容>`、`Themico#<记录>`、`代码#<路径>:<符号或行>`。需求确认阶段 claim 的**目标语义以"用户确认的内容"为权威**,可用 Themico 或其他文档作为支撑事实;**spec（规格)不得作为事实源,仅作补充**。(分层事实源规则见 SPEC-SOURCE-001。)
- AC1:每个 claim 带显式来源引用并写入 `record`(控制记录);缺来源不得进入 current-request。
- AC2:以 spec 为唯一来源的 claim 被拒绝;spec 只能作补充引用出现。
- AC3:Agent 推断但用户未确认的目标语义不得进入 current-request。

### B. 追问

**SPEC-QUESTION-001** — 在意图收敛前,系统必须支持多轮追问,每轮问答形成不可变记录;未回答的问题不得判定为"已收敛"。
- AC1:存在未回答的关键问题时,系统不允许进入 R1。

**SPEC-QUESTION-002** — 仅当 Why(为什么)、期望结果、核心链路三者均明确时,系统才可判定意图收敛。
- AC1:三者缺一 → 不得进入 R1。

### C. 三个评审闸门(低负担 ≠ 少评审)

**SPEC-REVIEW-R1** — 当意图收敛后,系统必须在进入抽象设计前,向 Human（人类)呈现低负担意图投影并要求批准;未批准前抽象设计节点不得开始。
- AC1:R1 未 approved（批准) → 抽象设计不可开始。

**SPEC-REVIEW-R2** — 当抽象设计成形后,系统必须在进入详细设计前,向 Human 呈现抽象设计投影(含架构/时序 Overview（概览))并要求批准。
- AC1:R2 未 approved → 详细设计不可开始。

**SPEC-REVIEW-R3** — 当详细设计与任务成形后,系统必须在进入实现前要求 Human 批准,且未解决反馈必须为空。
- AC1:存在未解决反馈或 R3 未 approved → 实现不可开始。

**SPEC-REVIEW-LOWBURDEN** — 每个评审投影必须由抽象到具体渐进呈现,只包含该抽象层的增量,不重复下层细节。
- AC1:R1 投影不含技术方案;R2 投影不含代码级任务细节。

### D. 闸门强制与失效级联(抗漂移核心)

**SPEC-GATE-001** — 系统必须阻止任一节点在其前置 gate（闸门)未满足时开始。
- AC1:跳过上游直接进入下游 → 拒绝。

**SPEC-INVALIDATION-001** — 当任一工件变为新 revision（修订),系统必须使其全部下游工件失效(stale),且失效工件不得被当作 current（最新)继续使用。失效级联作用于工件;已落地的 basic 代码不被自动失效,改由 SPEC-ACCEPT-002 阻断处理。
- AC1:修改 current-request 后,已有 plan 与三个评审标记 stale,实现不得基于 stale 工件继续。
- AC2:已落地 basic 代码不得因下游失效被自动回滚或自动删除。

### E. 工件、追溯与可验证性

**SPEC-ARTIFACT-001** — 每个语义工件必须是配对 `record`(控制)+`content`(人类语义)的不可变 revision;任一半缺失或 digest（摘要指纹)不一致 → 整个 revision 无效。

**SPEC-TRACE-001** — 系统必须维持贯穿全流程的 trace-ID（追溯标识)链:`claim → capability(抽象设计) → task(详细设计) → assert(验证) → 验收结论`。
- AC1:链中任一环断裂可被检出。

**SPEC-EARS-001** — 抽象验收与详细验收必须用 EARS 句式表达,使每条验收可判定通过/失败。
- AC1:不可测的"要快/要好"类表述不得作为验收条目。

**SPEC-SOURCE-001** — 系统必须按抽象层级施加事实源要求:意图、顶层设计、抽象设计等**抽象层**可以以 Themico 或其他文档作为事实;详细设计的实现依据、实现、验证等**具体实现层**必须以**代码**为事实源(文档仅作线索/补充)。`spec` 在任何层都只作补充;`用户确认的内容`在任何层都是目标语义权威。
- AC1:抽象设计的 claim 可引用 Themico/文档作为事实依据。
- AC2:实现或验证阶段以文档(而非代码)断言"当前实现事实" → 拒绝;当前实现事实必须以代码为据。
- AC3:任何层以 `spec` 作为事实源 → 拒绝。

### F. 实现与独立验证

**SPEC-IMPL-001** — 实现必须在 R3 批准范围内进行:不得修改 current-request、plan 或验收要求,不得做无关重构。

**SPEC-IMPL-002** — R3 批准的任务必须已分为有序两段 basic（基础)与 detail（详细实现);批准后,basic 段通过结构性验证前,detail 段不得开始。
- AC1:basic 未通过结构性验证时开始 detail → 拒绝。
- AC2:basic 段为空时不产生落地调用,且流程不因此分叉;两段恒定存在,空段不是路径分支。

**SPEC-IMPL-003** — basic 任务必须同时满足"被本 step 其他任务依赖"与"单独不产生外部可观测行为",判定依据必须写入 basic 任务工件。
- AC1:某 basic 任务单独产生外部可观测行为 → 分类无效,必须移入 detail。
- AC2:无任何消费者的 basic 任务 → 拒绝进入 R3。
- AC3:basic 任务工件引入详细设计未定的结构(字段、类型、签名、迁移方向、配置项) → 拒绝。

**SPEC-VERIFY-001** — 验证必须由独立于实现者的角色进行;实现者不得验证自身产出。
- AC1:同一执行身份既 impl（实现)又 verify（验证) → 拒绝。

**SPEC-VERIFY-002** — 验证必须依据实际实现与证据判定 `passed`/`failed`,不得依据文档、Agent 自述或文件存在判定通过。

**SPEC-VERIFY-003** — basic 段必须由独立于实现者的角色以结构性证据判定:结构存在、可构建、既有测试(若有)无回归。结论必须写入验证角色所有的工件,不得写入实现者所有的工件。
- AC1:以文档、Agent 自述或文件存在判定 basic 段通过 → 拒绝。
- AC2:basic 段验证不得声称交付任何外部行为。
- AC3:basic 段验证结论出现在实现者所有的落地工件中 → 拒绝。

### G. 验收与摘要

**SPEC-ACCEPT-001** — 仅当验证为 `passed` 时系统才可进入验收;仅当 Human `accepted`（接受)后才可进入摘要。

**SPEC-ACCEPT-002** — 存在已落地但无消费者的 basic 改动时,系统不得进入人工验收;必须由重规划显式处理(复用或删除)后才解除。
- AC1:detail 段被打回后直接进入验收 → 拒绝。
- AC2:fail-closed 停在 basic 段已证闸门,不自动回滚代码。

**SPEC-SUMMARY-001** — 摘要必须绑定实际交付;仅当验收 `accepted` 后 lifecycle（生命周期)才可标记完成。

### H. 失败处理

**SPEC-FAIL-001** — 节点失败(工具错误、验证不过、依赖缺失)时,系统必须 **fail-closed（失败即停)** 停在 last proven gate（最近已证闸门)并等待人类/Agent 决定;系统**不得**进行失败次数预算或失败→经验学习。

### I. 执行器(soft 默认 / hard 升级 / 降级安全)

**SPEC-ENFORCE-001** — 系统默认以 soft 执行器运行:无 CLI（命令行工具)时靠 Agent 遵守 gate,并以人类可读状态文件记录当前节点、各评审 pass/fail 与 currentness（当前性)。

**SPEC-ENFORCE-002** — 当 `themis` Go CLI 可用时,系统必须以 hard 执行器强制**同一份 flow 契约**;两个执行器执行同一契约,切换不改变流程语义,不产生两套内容漂移。

**SPEC-ENFORCE-003** — CLI 缺席不得阻塞流程;系统必须自动降级回 soft。

### J. Themico 松耦合边界

**SPEC-THEMICO-001** — 系统必须在无 Themico 时完整运行整条 spec 流程。

**SPEC-THEMICO-002** — 摘要点可产出与 Themico 无关的中性工件;是否喂给 Themico 由可选 adapter（适配器)决定,且不得成为流程运行前提。

## 4. 评审聚焦 B:最顶层的设计方案

> 这些是决定整个 MVP 形态的根本决策。以下五条已于 2026-08-08 审批通过并锁定为 MVP 地基;后续落地只能在其之内展开,若需变更必须重新审批本文件。

1. **执行器无关的单一契约 + soft/hard 双执行器**:flow 契约是唯一权威,默认 soft、CLI 可用时升级 hard、缺席降级。这是让"可执行"平滑落地、且不漂移的地基。
2. **三权分立 + 薄执行器厚语义**:Agent 只产提案、Human 只在评审/验收授权、执行器只保证闸门与状态。凡"不能信 Agent 自觉"的(gate、失效、身份、状态)才机器化。
3. **线性单一路径 + 三评审锚在抽象层跃迁 + 失效级联**:流程无简繁分档(无 simple/full 预留);越早拦截越省 token（词元);上游变则下游全失效。
4. **配对 revision + trace-ID + EARS + 事实源分层的抗漂移工件模型**:工件不可变、可追溯、可验证;抽象层以 Themico/文档为事实、实现层以代码为事实、spec 恒补充、用户确认恒为目标语义权威。
5. **Themis 与 Themico 松耦合**:spec 流程独立可执行,知识沉淀为可选外挂。
