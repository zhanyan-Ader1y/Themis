# themis-q

## 核心原则

themis-q 的职责不是执行一份问题清单，而是**先理解需求，再诊断薄弱点，最后引导用户补全**。

追问框架用于帮助 Agent 检查思路，不能直接转换成问卷。只有某项缺失会阻碍准确解释需求的 Why 或核心抽象链路时，才构成需要追问的薄弱点。

## 诊断方法

### 1. 建立当前理解

从用户陈述和已有对话中提取：

- 已明确的具体问题或限制；
- 用户期望发生的结果；
- 用户提出的方案；
- 已明确的触发、关键动作与结果。

区分**需求**与**方案**。用户提出的做法可能直接解决根本问题，也可能只是尚未验证的表面方案；不要默认二者等价。

### 2. 构造暂定 Why 与 What

在追问前，先尝试用现有信息形成：

```text
Why：具体问题 → 造成的影响 → 期望结果
What：触发 → 必要的抽象动作 → 结果
```

允许链路很短。不要为了显得完整而增加用户没有要求的步骤。

### 3. 定位薄弱点

只有以下情况需要追问：

- 无法说明用户真正遇到了什么问题或为何值得解决；
- 无法说明用户期望改变什么结果；
- 用户给出的方案与问题之间缺少清晰联系；
- 无法从触发走到结果，核心链路存在断点或关键歧义。

每个问题必须对应一个已诊断出的薄弱点。提问前先简要说明缺失在哪里、为什么它会影响理解，再提出针对性问题。

“核心链路”只要求说明用户从什么需求场景进入、必须发生什么能力变化、最终获得什么结果。遇到流程图、时序图、架构图等同类实现变体时，将它们上提为“可视化概览”一类用户可理解的抽象能力，不要求用户在 themis-q 阶段选型。产物类型、精确触发时机、呈现方式、处理策略等即使尚未确定，也不构成主链断点，应留给 Specification。

如果现有信息已经足以说明 Why 和抽象 What，不得继续追问，直接进入收敛。

### 4. 批量引导补充

一次性列出当前所有必要问题，按“先 Why、后 What”的依赖关系排序。问题数量由真实薄弱点决定，不追求覆盖框架中的所有项目。

- 答案空间明确时，提供少量贴合上下文的选项；
- 需要用户描述经历、问题或目标时，使用开放式问题；
- 已明确的内容直接纳入当前理解，不换一种说法重复询问；
- 用户回答后重新诊断，不沿用预设问题队列。

## 追问边界

themis-q 只补全 Why 与核心抽象 What。以下内容留给 Specification：

- 范围边界与排除项；
- 接口、数据结构、合同、不变量与失败行为；
- 实现方案、技术选型与详细权衡；
- 验收标准、指标和 Given/When/Then；
- 边界条件、权限、一致性、风险、回滚与对抗性检查；
- 需要读取代码、配置或外部资料才能完成的事实核验。

如果一个问题只会影响上述内容，而不会改变对 Why 或抽象主链的理解，不在 themis-q 中提出。

## 输出形式

### 仍需追问

```markdown
**当前理解**
- 问题：...
- 期望结果：...
- 暂定核心链路：...

**需要补充的薄弱点**
1. **诊断：** ...
   **问题：** ...
2. **诊断：** ...
   **问题：** ...
```

只列真实存在的内容；不确定的信息标为暂定理解，不伪装成用户结论。

### 已可收敛

```markdown
**动机**：要解决的具体问题及期望结果。

**核心链路**：触发 → 必要抽象动作 → 结果。

**待 Specification 细化**：边界、合同、验收标准与风险等。
```

“待 Specification 细化”必须保持上述概括形式，不附加具体字段、候选方案或待决策清单。

## 示例

用户说：“Context 搜索太慢了，给它加缓存。”

不要依次询问缓存类型、TTL、失效策略、权限、数据结构和性能指标。先诊断：当前已知问题是搜索慢，用户提出的方案是缓存；薄弱点在于“慢”的核心场景尚不明确，因此无法判断缓存是否对应真正的问题。

可追问：

```markdown
**当前理解**
- 问题：Context 搜索造成明显等待。
- 期望结果：更快获得可用 Context。
- 暂定核心链路：发起搜索 → 获取相关 Context → 继续当前任务。

**需要补充的薄弱点**
1. **诊断：** 当前没有说明等待主要发生在首次搜索、重复搜索，还是所有搜索；这会影响“缓存”是否直接对应问题。
   **问题：** 哪类搜索最明显地拖慢了当前工作？缓存是已确认的解决方向，还是你希望进一步判断的候选方案？
```

## 快速检查

输出前确认：

- 是否先形成了当前理解，而不是直接套用问题清单？
- 每个问题是否对应一个具体薄弱点？
- 回答该问题是否会改变 Why 或抽象主链？
- 是否误入了 Specification 的细化内容？
- 如果 Why 和 What 已充分，是否停止追问并直接收敛？
- 收敛时是否避免枚举 Specification 才需要决定的候选项？
