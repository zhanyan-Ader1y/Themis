# Themis 对抗验证攻击场景库

本文档为 Requirement Questioning Step 4 提供可复用场景。每个有效发现必须写入 `spec.yaml` 的 `ADV-*` 对象；`spec.md` 只展示投影，不接受直接编辑。

## 使用方式

- **low**：执行五项快速检查。
- **medium**：选择最高优先级的 1–3 个 AC，对每个维度选择相关场景。
- **high**：覆盖全部 AC 和全部六个维度，可按策略多轮攻击。
- `cover` 必须有非 Risk resolution refs；`accept`/`defer` 必须引用 `RSK-*`。
- critical 的安全、权限或数据完整性发现不能用 `defer` 通过 readiness。

## 快速检查表（5 项）

1. **空数据或缺失输入**：输入为空、null 或关联缺失时，行为是否明确？
2. **失败状态**：操作失败时，用户如何感知，系统如何恢复？
3. **并发冲突**：两个主体同时执行时，最终行为是否定义？
4. **向后兼容**：现有使用者、数据或接口受何影响，如何验证？
5. **回滚路径**：撤销时的操作、数据和用户影响是否清晰？

## 维度 1：边界条件

| ID | 场景 | 攻击问题 |
|---|---|---|
| B1 | 空值输入 | 必填字段为空或 null 时系统返回什么？ |
| B2 | 极值 | 超出范围、零或负数时如何处理？ |
| B3 | 超长输入 | 超大文本、文件或批次是否安全降级？ |
| B4 | 特殊字符 | SQL、XSS、Unicode 控制字符是否改变行为？ |
| B5 | 关联缺失 | 被引用资源删除时能否安全失败？ |
| B6 | 时区与国际化 | 时间、货币或格式在不同 locale 下是否一致？ |

## 维度 2：并发与竞态

| ID | 场景 | 攻击问题 |
|---|---|---|
| C1 | 同时修改 | 两个主体同时修改同一资源时最终状态是什么？ |
| C2 | 重复提交 | 重试是否造成重复副作用？ |
| C3 | 超时后成功 | 客户端超时但服务端完成后是否可安全重试？ |
| C4 | 部分成功 | 批量部分失败时如何呈现和恢复？ |
| C5 | 乱序到达 | 事件乱序时状态机是否仍正确？ |

## 维度 3：状态转换

| ID | 场景 | 攻击问题 |
|---|---|---|
| S1 | 非法状态 | 不允许的当前状态是否明确拒绝？ |
| S2 | 跳过步骤 | 绕过必需步骤时后续操作是否阻止？ |
| S3 | 状态回退 | 什么条件和证据允许回退？ |
| S4 | 并发修改 | 多进程更新状态时如何保证一致？ |
| S5 | 初始状态 | 首次启动或空数据时初始状态是否定义？ |

## 维度 4：权限与安全

| ID | 场景 | 攻击问题 |
|---|---|---|
| P1 | 未授权访问 | 未登录或低权限主体能否访问？ |
| P2 | 横向越权 | 主体 A 能否操作主体 B 的数据？ |
| P3 | 数据泄露 | 错误、日志或响应是否泄露秘密或 PII？ |
| P4 | 注入 | SQL、命令、模板或路径注入是否安全处理？ |
| P5 | 跨站攻击 | CSRF、XSS 或会话边界是否被考虑？ |

## 维度 5：依赖失败

| ID | 场景 | 攻击问题 |
|---|---|---|
| D1 | 服务不可用 | API、数据库或队列不可用时如何降级？ |
| D2 | 超时 | 超时与明确失败是否有可解释的不同策略？ |
| D3 | 异常格式 | 非预期状态码或错误体是否安全失败？ |
| D4 | 降级策略 | 使用缓存、默认值还是错误，用户是否知情？ |
| D5 | 恢复后状态 | 依赖恢复后如何恢复，需要人工介入吗？ |

## 维度 6：数据完整性

| ID | 场景 | 攻击问题 |
|---|---|---|
| I1 | 部分写入 | 中途失败后已有数据是否一致？ |
| I2 | 格式错误 | 不符合 Schema 的数据是否产生可操作错误？ |
| I3 | 编码问题 | 不同编码或二进制数据是否正确处理？ |
| I4 | 迁移中断 | 转换中断时能否恢复或回滚？ |
| I5 | 大数据量 | 超出内存时是否流式或分批处理？ |

## 结果记录

| 处置 | 必需引用 | 含义 |
|---|---|---|
| `cover` | `resolution_refs` 指向 AC、Requirement、Contract、Invariant 或 Decision | 当前交付明确覆盖场景。 |
| `accept` | 至少一个 `risk_refs` | 当前版本接受已知风险与残余影响。 |
| `defer` | 至少一个 `risk_refs`，含 owner 与后续处置 | 后续版本或责任方处理。 |

每个 `ADV-*` 必须有 AC 引用、攻击维度、severity、场景、终态和匹配引用。pending、无引用终态、超限延期或被策略禁止的 critical defer 都会使 `spec_adversarial_resolved` 失败。
