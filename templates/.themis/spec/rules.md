# Spec 判定规则（rules）

本文件只回答一个问题：**这一步怎么判过不过**。

节点顺序、前置闸门、失效波及不在本文件——那些在同目录 `flow.md`。本文件按主题分十节；每节固定四项，顺序一致，四项名称见各节小标题。判据与拒绝条件均逐字引自已审批的 `docs/superpowers/specs/2026-08-07-themis-spec-flow-mvp.md` §2（第 5 节另引自同批次设计增补文档 §3.3），不在本文件重新表述或简化措辞。

---

## 1. 来源与分层事实源

**适用节点：** Intake、追问、意图定稿、抽象设计、详细设计、落地、验证

**判据：**

**SPEC-INTAKE-002** — 每个进入 current-request（当前请求)的 claim（诉求)必须**显式记录来源引用并写入工件文件**,采用 `<类型>#<定位>` 形式,例如 `用户确认#<内容>`、`Themico#<记录>`、`代码#<路径>:<符号或行>`。需求确认阶段 claim 的**目标语义以"用户确认的内容"为权威**,可用 Themico 或其他文档作为支撑事实;**spec（规格)不得作为事实源,仅作补充**。(分层事实源规则见 SPEC-SOURCE-001。)

**SPEC-SOURCE-001** — 系统必须按抽象层级施加事实源要求:意图、顶层设计、抽象设计等**抽象层**可以以 Themico 或其他文档作为事实;详细设计的实现依据、实现、验证等**具体实现层**必须以**代码**为事实源(文档仅作线索/补充)。`spec` 在任何层都只作补充;`用户确认的内容`在任何层都是目标语义权威。

**拒绝条件：**

- SPEC-INTAKE-002/AC1:每个 claim 带显式来源引用并写入 `record`(控制记录);缺来源不得进入 current-request。
- SPEC-INTAKE-002/AC2:以 spec 为唯一来源的 claim 被拒绝;spec 只能作补充引用出现。
- SPEC-INTAKE-002/AC3:Agent 推断但用户未确认的目标语义不得进入 current-request。
- SPEC-SOURCE-001/AC1:抽象设计的 claim 可引用 Themico/文档作为事实依据。
- SPEC-SOURCE-001/AC2:实现或验证阶段以文档(而非代码)断言"当前实现事实" → 拒绝;当前实现事实必须以代码为据。
- SPEC-SOURCE-001/AC3:任何层以 `spec` 作为事实源 → 拒绝。

**判定者：** 各节点执行者，评审时受检

## 2. 意图收敛判据

**适用节点：** 追问、意图定稿

**判据：**

**SPEC-QUESTION-001** — 在意图收敛前,系统必须支持多轮追问,每轮问答形成不可变记录;未回答的问题不得判定为"已收敛"。

**SPEC-QUESTION-002** — 仅当 Why(为什么)、期望结果、核心链路三者均明确时,系统才可判定意图收敛。

**拒绝条件：**

- SPEC-QUESTION-001/AC1:存在未回答的关键问题时,系统不允许进入 R1。
- SPEC-QUESTION-002/AC1:三者缺一 → 不得进入 R1。

**判定者：** 意图定稿执行者

---

## 3. 评审投影的低负担要求

**适用节点：** R1、R2、R3

**判据：**

**SPEC-REVIEW-LOWBURDEN** — 每个评审投影必须由抽象到具体渐进呈现,只包含该抽象层的增量,不重复下层细节。

**拒绝条件：**

- AC1:R1 投影不含技术方案;R2 投影不含代码级任务细节。

**判定者：** 投影产出者，Human 在评审时受检

## 4. basic/detail 判定

**适用节点：** 任务分组、R3

**判据：**

**SPEC-IMPL-003** — basic 任务必须同时满足"被本 step 其他任务依赖"与"单独不产生外部可观测行为",判定依据必须写入 basic 任务工件。

**拒绝条件：**

- AC1:某 basic 任务单独产生外部可观测行为 → 分类无效,必须移入 detail。
- AC2:无任何消费者的 basic 任务 → 拒绝进入 R3。
- AC3:basic 任务工件引入详细设计未定的结构(字段、类型、签名、迁移方向、配置项) → 拒绝。

**判定者：** R3 评审（`review.md` 的分类核查）

## 5. `[basic]` 标识

**适用节点：** 抽象设计、任务分组、验证

**判据：**（引自 `docs/superpowers/specs/2026-08-10-spec-flow-basic-detail-split-design.md` §3.3）

specify 只写外部可观测行为,而 basic 按定义不产生行为,两者的交集需要明确:

- **对外契约性基础**(字段进入 API 响应或对外数据契约):可观测但不构成行为,属于**契约存在性条目**。这类条目出现在 `specify.md` 中并标 `[basic]`,验收方式是结构性断言。

因此 `[basic]` 的含义是"该条目为契约存在性、由基础落地承担",不是"这是一条基础行为"。specify 的定位不被破坏,且与基础段采用结构性验证相互对齐。

**拒绝条件：**（引自同上 §3.3）

- **纯内部基础**(数据库列、内部类型、私有签名):按模板 README 的定位(`是否包含数据库表:通常不包含`)**不进 specify**,只出现在 `design.md` 与 `task/basic.md`。

**判定者：** 抽象设计执行者，R2 受检

## 6. 结构决策归属

**适用节点：** 详细设计、任务分组

**判据：**

SPEC-IMPL-003/AC3 原文以"条件 → 拒绝"单句同时给出判据与拒绝结果,判据与拒绝条件两项因此引用同一原文:

SPEC-IMPL-003/AC3:basic 任务工件引入详细设计未定的结构(字段、类型、签名、迁移方向、配置项) → 拒绝。

**拒绝条件：**

- SPEC-IMPL-003/AC3:basic 任务工件引入详细设计未定的结构(字段、类型、签名、迁移方向、配置项) → 拒绝。

**判定者：** R3 评审

## 7. 验证

**适用节点：** verify/basic、verify/detail

**判据：**

**SPEC-VERIFY-001** — 验证必须由独立于实现者的角色进行;实现者不得验证自身产出。

**SPEC-VERIFY-002** — 验证必须依据实际实现与证据判定 `passed`/`failed`,不得依据文档、Agent 自述或文件存在判定通过。

**SPEC-VERIFY-003** — basic 段必须由独立于实现者的角色以结构性证据判定:结构存在、可构建、既有测试(若有)无回归。结论必须写入验证角色所有的工件,不得写入实现者所有的工件。

本轮补充：

- `verify/basic` 只判三项：结构存在、可构建、既有测试（若有）无回归。
- `verify/detail` 逐条对 `specify.md` 的验收判据断言；标 `[basic]` 的契约存在性条目由 `verify/basic` 以结构性断言覆盖，不重复计入行为断言。

**拒绝条件：**

- SPEC-VERIFY-001/AC1:同一执行身份既 impl（实现)又 verify（验证) → 拒绝。
- SPEC-VERIFY-002:不得依据文档、Agent 自述或文件存在判定通过。
- SPEC-VERIFY-003/AC1:以文档、Agent 自述或文件存在判定 basic 段通过 → 拒绝。
- SPEC-VERIFY-003/AC2:basic 段验证不得声称交付任何外部行为。
- SPEC-VERIFY-003/AC3:basic 段验证结论出现在实现者所有的落地工件中 → 拒绝。

本轮补充（不得弱化）：

- `verify/basic` 不得声称交付任何外部行为——此刻行为尚未实现，任何行为结论都是假的。
- `verify/basic` 的结论必须写入验证角色所有的工件，**不得写入 `impl/` 下任何文件**。

**判定者：** 独立于实现者的验证角色

## 8. 孤儿阻断

**适用节点：** verify/detail、人工验收

**判据：**

**SPEC-ACCEPT-002** — 存在已落地但无消费者的 basic 改动时,系统不得进入人工验收;必须由重规划显式处理(复用或删除)后才解除。

本轮补充：

- `verify/detail` 必须断言：每个 `task/basic.md` 声明的被依赖关系，其消费者在实际代码中存在。

**拒绝条件：**

- AC1:detail 段被打回后直接进入验收 → 拒绝。
- AC2:fail-closed 停在 basic 段已证闸门,不自动回滚代码。

本轮补充（不得弱化）：

- 要挡住的具体场景是 `SPEC-ACCEPT-002/AC1` 挡不住的那条：**detail 段重规划后消费者被删除**——此时剩余 detail 任务可以全部通过，basic 改动已成孤儿，且并不存在"被打回"这一事实。

**判定者：** **verify/detail**；验收只引用其结论，不自行判定。孤儿判定不由人承担，由 `verify/detail` 断言。三条已批准约束同时指向 `verify/detail`：闸门要成立必须有判定者；判定者必须独立于实现者（`SPEC-VERIFY-001`）；实现层判据必须以代码为事实源（`SPEC-SOURCE-001`）。

## 9. 工件阐述方式

**适用节点：** 全部产出工件的节点

**判据：**

**SPEC-ARTIFACT-001** — 每个语义工件必须是配对 `record`(控制)+`content`(人类语义)的不可变 revision

**拒绝条件：**

- 任一半缺失或 digest（摘要指纹)不一致 → 整个 revision 无效。

**判定者：** 各节点执行者，评审时受检

---

## 10. 失败处理

**适用节点：** 全部节点

**判据：**

**SPEC-FAIL-001** — 节点失败(工具错误、验证不过、依赖缺失)时,系统必须 **fail-closed（失败即停)** 停在 last proven gate（最近已证闸门)并等待人类/Agent 决定

**拒绝条件：**

- 系统**不得**进行失败次数预算或失败→经验学习。

**判定者：** 各节点执行者
